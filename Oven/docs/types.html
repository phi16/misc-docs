Oven ── 言語の記録

コア型理論

Oven の意味論的な核です。ざっくり言うと 依存型(MLTT)+ 帰納型 + QTT に GPU の表現可能性検査 を乗せたもの。QTT は次章、表現可能性は GPU 実行で扱い、この章はそれ以外の骨格を説明します。

宇宙:Type : Type

型にも型があります(Nat : Type、Bool : Type)。では Type の型は? Oven は一番単純な Type : Type を採用します。

これは 論理的に不健全 です。Girard のパラドックスにより、原理的には False すら証明できてしまいます(Agda の --type-in-type と同じ状況)。さらに正規化が強正規化でなくなるため、型検査器は病的入力で発散し得ます。それでも採用するのは、軽い証明・実用上の不変条件(「この添字は範囲内」など)には全く困らず、実装も使い勝手も圧倒的に楽だからです。本当に健全性が欲しくなったら宇宙階層(Type0 : Type1 : …)を導入します。発散は割り切って許容し、実用上の保険として timeout/fuel での打ち切りは任意で入れてよい、という立場です。

Type : Type の実利的な副産物として、型が第一級の値 になります。(Env : Type, env : Env, step : (Env, A) → (Env, B)) のように、型をフィールドに持つレコード(透明な存在型)がそのまま書けます。

Π 型(関数)── 適用は全面 curried

関数の型は Π 型で、戻り型が引数に依存できます:(x : A) → B(x)。

適用は全面 curried です(2026-06-11 に Σ-domain 方式から移行・確定)。(x : A, y : B) → C は curried な (x:A) → (y:B) → C であり、f(a, b) は f a b(= (f a) b)です。tight な f(a, b) も並置 f a b も同じ意味になります。

タプルを 1 個受け取りたいときだけ型を (p : (x:A, y:B)) → C と書き、f((a, b)) で渡します(f(a, b) とは別物)。タプルの分解は本体で let (x, y) = p; …(Σ は積であって inductive ではないため、case ではなく分解束縛)。

Σ型 / テレスコープ / レコード

Oven で最も重要な構造です。 「関数の引数の並び(テレスコープ)」と「レコード(名前付きの組)」を、同じ一つの Σ 型(依存和)で表します。

(x : A, y : B)      // 依存した名前付きの並び。後ろの型が前の値に依存できる
(a : Nat, b : Nat)  // 名前付き = レコード型。値は (a = 1, b = 2)、射影は r.a r.b
(Nat, Nat)          // 無名 = タプル。射影は p.0 p.1
()                  // 空 = Unit(型も値も ())
  • Σ = ∃(存在量化) でもあります。MLTT では依存和と存在型は同じ連結子で、別の道具は要りません。
  • 依存レコードなので 連想型 も自然に書けます:(Out : Type, mul : (A,B) → Out) のように、後のフィールドの型を前のフィールドに依存させられます。
  • この「Σ をあらゆる所に使う」方針により、typeclass 辞書・module・closure 環境・dispatch の任意個リソースが、新機構なしで全部 Σ で書けます。

帰納型は data 宣言

帰納型はユーザが data で宣言します(組み込みの Bool/Nat/Fin/Vec/Id も std/prelude.ov に Oven ソースの data 宣言として書かれており、処理系が起動時に取り込みます)。

data Nat : Type {
  zero : Nat,
  succ : (n : Nat) -> Nat,
}

// 線形 payload を入れられる cons-list。r = 要素の量(型に乗るので線形 Vec と純粋 Vec は別の型)
data Vec [r : Mult] (A : Type) : (n : Nat) -> Type {
  vnil  : Vec(zero),
  vcons : (m : Nat, x : 'r A, xs : 'r Vec(m)) -> Vec(succ(m)),
}

// 等式。GADT の典型 ── refl が index y を x に固定する
data Id [A : Type] (x : A) : (y : A) -> Type { refl : Id(x) }
  • parameter(: の左)は全 constructor で共有(uniform)。implicit [...] か explicit (...) かを選べます。
  • index(: の右)は constructor の戻り型で zero/succ(n) のように具体化されます。
  • constructor は GADT スタイルで完全な型を書きます。量注釈 'ρ は constructor の引数にだけ付きます。
  • strict positivity は「inductive 型であることの定義そのもの」 として要求されます。型構成子が共変 functor F であって初めてその initial algebra μF(帰納型)が存在する ── → の左などの負の位置に自己が出る宣言は受け付けません。

型ごとの eliminator(Nat-elim 等)は焼き込みません。分解・再帰は次の case 一本で、その型付け・計算規則(iota)・QTT 合流は宣言から一般的に導かれます。

当初は「帰納型はプリミティブとして固定し、型ごとの eliminator を焼き込む」方針でしたが、QTT の合流規則を型ごとに手で持つ羽目になったため、一般の data + case へ移行しました(→ 経緯)。

反復は case のみ ── 帰納仮説の括弧 ⟦⟧

ユーザの決定として、自由再帰も無限ループも言語に入れません。よって Oven は全域言語です。繰り返し計算は case 構文(構造的再帰)だけが提供します。

case は帰納型の値を constructor で 1 段分解し、各 branch でその部分構造に対する 帰納仮説 ⟦w⟧(その部分構造に対する case の結果)を使えます:

// n + m(⟦k⟧ : 「k に対する case の結果」)
case[λ(k) Nat](n) { zero => m,  succ(k) => succ(⟦k⟧) }

// Bool の分岐(⟦⟧ を使わない case = 非再帰)は同じ構文の特別な場合
case(b) { true => e1,  false => e2 }

// J(等式の eliminator)も case で導出できる。K(UIP)は入れない
J = λ[A](P, d, x, y, p) → case[λ(y, q) P(x, y, q)](p) { refl => d(x) }

⟦w⟧(意味論の denotation bracket。ASCII 代替は [[w]])は その branch の再帰パターン変数 w にしか適用できません。だから書けるのは構造的再帰だけで、停止性検査を別に持ち込まずに 全域性が構文的に自明 になります。生の eliminator の安全性をそのまま、Idris 風の書き味で使える、というのがこの構文の狙いです。

  • motive [P] は省略可能(非依存なら期待型から推論)。
  • iota(計算規則)は一般規則一つ:scrutinee が c(as) に簡約されたら branch c を選び、本体の ⟦w⟧ を「w に対する case の再帰結果」に置換して評価する。型ごとには持ちません。
  • case の QTT 使用量規則(再帰 branch と非再帰 branch の合流)は Oven の独自色が強い部分です。→ QTT の章

生の case は書きづらいので、実際のコードは iterate のようなコンビネータで書きます(iterate 自身が case による普通の定義です):

iterate : [A : '0 Type] (n : Nat, f : A → A, x0 : A) → A
iterate[A](n, f, x0) = case[λ(k) A](n) { zero => x0,  succ(k) => f(⟦k⟧) }

inductive でないもの:postulate

inductive でない組み込みは postulate name : T(型だけを持つ不透明定数)で宣言します。これも std/prelude.ov に Oven ソースとして書かれます。実行時の意味は処理系・ランタイムが供給し、原則 eval では簡約されません。ただし少数の 組み込み簡約つき postulate(数値演算、set/get の in-place 等)だけは実装が計算規則を与えます。

postulate F32 : Type                                  // 不透明な機械スカラ
postulate U32 : Type
postulate Buffer : (n : U32, A : Type) -> Type        // GPU 常駐・線形資源
postulate Array  : (n : U32, A : Type) -> Type        // host 常駐・可変配列
postulate World : Type                                // host IO の効果 token(零幅)
postulate GPU   : Type                                // GPU カーネルの効果 token(零幅)
postulate trustMe : [A : '0 Type] (u : Unit) -> A     // 消去される公理(脱出ハッチ)

trustMe は「面倒な証明義務を埋める」ための公理です。'0(消去)位置で使う限り実行時に残りません。値が要る位置で使うと実行時に stuck するので、本来の用途は証明位置に限られます。

ユーザも自分の抽象定数を postulate で宣言できます。

コアに固有の構成として postulate でなく直接持つのは:Type(宇宙)、Unit(Σ の終端)、第一級 Mult(multiplicity の半環 ── case 評価にすると QTT 検査が循環しうるため組み込み)の 3 つです。

nominal 型(newtype)

nominal R(params) = Body は 名目的型 を宣言します。R(a) は conversion では Body に展開されません(同形の Body を持つ Add(F32) と Mul(F32) が別の型として区別される)。一方、構築・適用・射影には透明で、値は Body の値そのもの(wrapper なし)です。

これは typeclass のクラス宣言に使われます。構造的な Σ レコードでクラスを表すと、同形のクラスが conversion で同一視されて instance 解決が曖昧になる ── その問題を名目性だけで解決する、最小の newtype 機構です。→ 表面言語

型検査の枠組み:双方向 + 使用ベクトル + NbE

  • 双方向(bidirectional):「期待型が分かっていて検査する(checking ⇐)」と「値から型を推論する(synthesis ⇒)」を行き来します。
  • 使用ベクトル:検査と同時に「どの変数を何回使ったか」(Δ)を計算して出力します(QTT のため。→ 次章)。
  • NbE(Normalization by Evaluation):依存型では「Array(2+3, A) と Array(5, A) は同じ型か」のような判定が要ります。項を一旦「意味の世界(値)」に評価してから項に書き戻す(quote)ことで正規形を求めて比較します。実装は elaboration-zoo の Rust 移植が骨格です。

conversion(定義の等しさ)の決定事項:

  • iota:case の branch 選択 + ⟦⟧ 置換、プリミティブの組み込み簡約(数値演算・set/get 等)、Mult の半環演算(1+1 ↝ ω 等)が計算します。scrutinee が neutral なら詰まります。
  • η は Π・Σ(レコード)・Unit でやります。inductive(Bool/Nat 等)ではやりません。
  • multiplicity は型構造の一部 として比較します('1 A→B と 'ω A→B は別の型)。Mult が第一級で半環演算を持つため、NbE が '(1+1) A ≡ 'ω A を計算します。使用量そのものは変換に無関係(計算に効かない)です。
  • GPU カーネルの中身(store/load 等)は計算規則を持たない不透明な定数(neutral)として比較し、命令的な意味は codegen だけに置きます。

メタ変数と implicit 推論

推論で未確定の項は メタ変数 ?m として置き、単一化(unification)が解きます。implicit 引数はメタ変数であり、埋め方は 2 通りです:

  1. 単一化 で構造的に決まる(型パラメータ A など)
  2. 文脈の implicit 値から型で拾う(typeclass の辞書 ── いわゆる instance 解決)

「instance 解決」は専用サブシステムではなく、「implicit 引数 = メタ変数」+「それを曖昧性なく埋める」だけの仕組みです。詳細は表面言語の章で扱います。
