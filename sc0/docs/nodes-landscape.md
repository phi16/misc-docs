# ノードベース環境の風景と SC0 の位置

「ノードベース」は一つのジャンルではありません。箱と線という見た目が共通しているだけで、
その下の意味論はツールごとにまるで違います。この文書は世の中のノードベース環境を
設計の軸で切り、その中で SC0 がどこに立つかを整理した読み物です（2026 年時点の観察。
各ツールは変化し続けるので、細部は古くなりえます）。

## 系統の見取り図

| 系統 | 代表 | グラフが意味するもの |
|---|---|---|
| cook 型 DAG（プロシージャル生成） | Houdini・Blender Geometry Nodes・Grasshopper・Substance Designer・Nuke / Fusion | データの依存関係。要求されたら上流から「cook」して結果を作る |
| 信号型（実時間ストリーム） | Max/MSP・Pure Data・TouchDesigner・vvvv・cables.gl | 常時流れる信号の配線。フレーム／サンプル駆動 |
| 制御フロー型 | Unreal Blueprints・PlayMaker | 命令の実行順。線は「次にこれを実行」であり、データフローですらない |
| パイプライン／バッチ型 | ComfyUI・KNIME・LabVIEW・Simulink | 処理工程の連結（機械学習・計測・工学系） |
| 言語両表現型 | Enso（旧 Luna）・vvvv gamma（VL） | **プログラムそのもの**。グラフとテキストが同じ実体の 2 表現 |

同じ「箱と線」がこれだけ違う意味を持つ——つまり**ノード UI は意味論を何も規定しません**。
「ノードベースにする」という決定は、実は何も決めていない。決めるべきは下の各軸です。

SC0 は体験としては cook 型（Houdini の隣人・incremental 再計算のエンジン名が Cook なのも
この系譜の言葉）、意味論としては言語両表現型に属します。

なお、信号型の系譜（Max/MSP・Pure Data）が他とやや離れた文化圏に見えるのは
偶然ではありません。あちらは IRCAM のコンピュータ音楽（Miller Puckette の Patcher、
1980 年代末）から来た**実時間演奏の道具**の系譜で、プロシージャル生成の系譜
（合成・コンポジット・3DCG）とはユーザーも会議も別でした。意味論も対照的です——
hot/cold インレットや右から左の評価順のような**操作的な**規約の上に成り立っていて、
「純粋な配線図」からはむしろいちばん遠い一族です。

## 軸 1：λ 問題——関数・反復・抽象をどう扱うか

ノードベース最大の急所はここです。線は「値の流れ」を描けますが、
「関数そのもの」を値として扱うことが構造的に苦手です。各ツールの対処が興味深い：

- **Houdini**：For-Each は特殊なサブネット構造。それでも足りない所は **VEX**——グラフの
  中に埋め込まれた**テキスト言語**——へ脱出する（wrangle ノード）。
- **Blender Geometry Nodes**：2021 年に **fields** を導入。field のソケットは値ではなく
  「文脈（ジオメトリ＋ドメイン）を受けて値を返すもの」を運びます。これは実質**暗黙の λ**
  です——ただし λ とは呼ばれず、第一級でもない（field を貯める・合成する操作は限定的）。
- **Grasshopper**：関数を渡す代わりに**暗黙の反復**。リスト長が合わなければ
  longest list / shortest list / cross reference という**マッチング規則**で自動的に
  繰り返します。便利ですが、規則は本質的に恣意的な既定の塊で、有名な混乱源です。
- **Max/MSP**：信号カーネルを書くための **gen~** という別言語を内蔵。ここでもグラフの
  限界をサブ言語で補っている。
- **vvvv gamma（VL）**：この系譜でもっとも言語に振り切った例。静的型・型推論・
  **generics・delegates（無名関数を値として渡す）**まで到達しています。
  ビジュアル言語を突き詰めると関数型言語に収斂する、という実例。

こうして並べると、**fields・暗黙反復・wrangle・gen~ は、どれも「λ と型が無いことへの
回避策」に見えてきます**。SC0 の立場は単純で、最初から λ 計算を土台に置く：

- fields に相当するものは、ただの関数 `Point j -> Vec 3 R`（メッシュ属性）。
- 暗黙反復に相当するものは、明示の `map` / `zipWith`（長さの整合は型が検査する。
  マッチング規則の暗記は要らない）。
- wrangle / gen~ に相当するものは**存在しない**——カーネルは同じ言語の部分評価から
  創発するので、脱出すべき「外」がそもそもない。

## 軸 2：真実はどこにあるか

- 大半のツールは**グラフ（バイナリや JSON）が真実**で、テキスト表現は無いか、
  一方向の書き出しだけです。帰結は実務に響きます：diff が読めない、merge できない、
  レビューできない、生成・変換のプログラムが書きにくい。
- 埋め込みテキスト言語（VEX・Python・C#）を持つツールは「グラフの真実＋テキストの島」
  という**二層構造**になり、島の中と外で世界のルールが変わります。
- **Enso（旧 Luna）** はここで際立った例外で、テキストとグラフの**双方向・無損失の
  同一表現**を最初から掲げた言語です（保存形式はテキスト＋位置マーカー）。
  SC0 はこの点で Enso と同じ側に立ちます——真実はプログラムひとつ、
  グラフはビュー、位置や view 指定は透明な注釈としてテキストに残る。

## 軸 3：型は何を守ってくれるか

- 多くのツールの型は**ドメイン単位の粗い分類**です（geometry / texture / signal / DAT…）。
  接続の可否はこの粒度で決まり、中身の整合（解像度・成分数・長さ）は実行時・cook 時に
  初めて壊れる。
- Blueprints や vvvv gamma は静的型を持ちます（gamma は generics まで）。
  それでも**形状・次元・トポロジを型で追うツールは見当たりません**。
- SC0 はここが依存型の出番です：`Vec n R`・`Buffer d shape T`・`Point j`。
  「解像度が合っていない」「別のトポロジの属性を混ぜた」が接続の時点で断られる。
  ノードベースの型検査を「ソケットの色が合うか」から「意味が合うか」へ引き上げる、
  と言い換えられます。

## 軸 4：ノードはどこから来るか

- 通常、ノードはツールベンダが実装した機能の一覧です。Houdini の SOP は数百個あり、
  それぞれの意味はマニュアルが定義します。ユーザーが同じ資格でノードを増やすことは
  できません（プラグイン API は別世界の話）。
- SC0 では**ノード＝宣言**です。Library パネルに並ぶのは標準ライブラリの関数そのもので、
  自分の `let` も同じ資格でノードになります。`render` すら普通のライブラリ定義なので、
  「組み込みノード」と「自作ノード」の区別が原理的にありません。

## 補遺：string diagram という見方

ノードグラフには、圏論由来のきれいな読み方があります——**string diagram**。
線が対象（型）、ノードが射（関数）、並置がテンソル積。この読みでは「配線図」は
見た目の比喩ではなく、モノイダル圏の射の正確な表記法です。

この観点で見ると、SC0 の Graph が λ や let を**入れ子の領域**として描く理由が
はっきりします。平らな string diagram で描けるのは単純な合成までで、λ 抽象のような
「文脈を拡張した世界の中の図」を描くには、**図の一部を箱で囲む**必要があります
（Melliès が *functorial box* と呼んだ装置——箱の内側は別の圏／関手の像の中）。
さらに依存型では、束縛のたびに文脈 Γ が伸びて「Γ 上のスライス」へ移るので、
**領域は装飾ではなく意味論上の必須の構造**になります。SC0 の Graph で
「包含（parent）」と「結線（in/body）」が別の概念なのは、この区別の実装です。

同じ束縛の使用が 1 つの var ノードを共有して描けることにも解釈があります。
領域の内側を「環境の Reader モナドの中」と読むと、束縛値は `ask` で**どこからでも**
取り出せるもので、しかも Reader は**可換**なモナドなので取り出しの順序を表現する
必要がありません。だから使用点に順序構造を持たせず、1 つの var から何本でも線を
引ける——今の描き方はこの読みと整合しています。

既存ツールにも部分的な対応物はあります。Houdini の Block Begin / End（For-Each）は
グラフの中に領域を区切る点でかなり近いことをやっています。ただしそれは反復のための
特殊構造であって、「束縛一般＝領域」という一様な原理にはなっていません。

## まとめ：SC0 の位置

3 つの潮流の合流点に立とうとしている、と要約できます。

1. **Houdini 的な制作体験**（cook 型 DAG・配置と接続・パラメータのライブ反映）
2. **Enso 的な単一真実**（テキスト＝グラフ＝同じプログラムの 2 ビュー）
3. **vvvv gamma が示した方向のさらに先**（ビジュアル環境の土台を本物の言語に——
   ただし generics で止まらず、純粋・依存型まで）

そして 4 つ目として、どの潮流にもまだ無いもの——**形状・次元・トポロジの静的な整合**——を
依存型で足しています。

ノードベースの歴史を「λ と型を少しずつ再発明してきた歴史」と読むなら、
SC0 はその再発明を最初から正規の形で置いてしまう試みです。
