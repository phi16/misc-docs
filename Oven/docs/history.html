Oven ── 言語の記録

経緯 ── 捨てた案の記録

Oven の設計は「これで綺麗にまとまった」と思っては穴が見つかる、の繰り返しで進んできました。捨てた案を消さずに残すのは、同じ穴に二度落ちないためです。この章は主要な撤回・転換を、当時の理由とともに記録します(一次資料は DESIGN.md)。

2LTT ── 層を構文で分ける案

案:Two-Level Type Theory。メタレベル(コンパイル時・フルパワーの依存型)とオブジェクトレベル(実行時 = GPU・制限された世界)を構文として分け、⟨A⟩ のような印で繋ぐ。理論的には綺麗な解。

却下の理由:「host 用と kernel 用のコードを構文的に書き分けたくない。一つの言語で、区別なく書きたい」。

その後:2LTT の発想そのもの(GPU で走る部分の隔離)は、'GPU modality として一度復活し(下記)、最終的には「dispatch 境界 + 表現可能性検査」だけに落ち着きました。「捨てたはずの案が形を変えて戻り、また消えた」二段の変遷です。

'GPU modality ── 誕生と全廃

案:'GPU T という型の印(modality)で「GPU で走る層」を隔離する。2LTT のオブジェクトレベルを、構文の層ではなく型の印として復活させたもの。「エラーが違反した場所にローカルに出る」という利点もあった。当初は「'GPU の内部は QTT オフ(線形性なし・命令的)」という整理も伴っていた。

全廃の理由(効果系 Phase 5、2026-06-14):

  1. 「GPU 内は QTT オフ・順序はプログラム順」という整理が撤回された(下記)。効果順序は host IO と同型の token threading で付けることになり、「QTT オフ」という modality の意味が消えた。
  2. 残った意味は「表現可能性を強制する phase」だけになり、純コードに 'GPU を書かせるのは「使える場所を減らすだけ」で利点が無くなった。

現在:純コードは world 多相(印なし)。GPU カーネル断片はただの純粋関数 A → B です。host/GPU の区別は dispatch 境界 + 表現可能性検査(実装上は in_kernel フラグ 1 個)だけが担い、store を host で誤って呼べない安全性は token の型(World ≠ GPU)が担います。

「カーネル内の順序はプログラム順」の撤回

案:カーネルの中身は 1 スレッドが上から順に実行する命令的コードなので、store/load の順序は素のプログラム順で保証すればよい(linearity 不要)。

撤回の理由(2026-06-12):これは 関数の純粋性を売っている。評価器が字面順を守ることに意味が依存する = eval/quote/inline/conversion で順序が動きうる = 参照透過でない。[&IO] を導入した動機そのものに反する。

現在:GPU の効果順序も host IO と同型の 零幅 token threading で付けます。buffer は 'ω(race・atomic は自由)のまま、順序だけを token の '1 チェーンが担います。

FnMut / apply ── 別建ての関数型

案:効果のある λ のために FnMut(A, B) = (Env : Type, env : Env, code : (Env, A) → (Env, B)) を、純粋な A → B と並ぶもう一つの組み込み関数型として立てる。呼び出しは apply、closure 値自体を '1 で threading する。

廃止の理由:

  • 「効果のある関数」は素の A → B で表せる(('1 S, A) → ('1 S, B) はただの Π)。
  • 「closure は 'ω だけ capture・'1 は引数で渡す」を徹底すると関数値は全部 'ω になり、関数と状態を束ねる FnMut の存在理由が消える。
  • creative coding の流儀(state-as-data:状態は Array(Particle) として持ち純粋関数で map)に、state-as-closure は合わない。

現在:関数型は A → B 一種類(確定)。状態を抱えた値が本当に要るなら手書きの Σ で書く ── foundation ではなくライブラリのパターン。

設計ノートの言葉:「以前『すべての closure は言語レベルの Σ 型』『env を ∃ で隠す必要がある』と何度も書いたが、全部誤りだった。純粋 closure は capture していてもただの A → B。」

WriteSet / disjoint merge

案:GPU カーネルの書き込みを「各スレッドが書き込み集合(WriteSet)を返す純粋関数」とモデル化し、dispatch がそれらを disjoint(重複なし)に merge する。書き込みが純粋な「結果の組み立て」になり、副作用が消える。

撤回の理由:GPU には atomic 演算があり、複数スレッドが同じ場所に正しく書き込むパターンが実在する。disjointness の要求は強すぎるし、検査も高コスト。

現在:カーネルは本当に effectful だと認め、race は型で追わない(compute-shader と同じ割り切り)。

effect row / Row kind / Res(ρ)

案:dispatch のカーネルが任意個のバッファを捕捉するのを型で表すため、「捕捉する借用の行(row)」を第一級の kind にし、closure を存在量化・dispatch を全称量化で多相にし、Res(ρ) で返すべき資源を計算する。

撤回の理由:「糖衣構文のために変なものを足すくらいなら、糖衣構文の方を捨てろ」に真っ向から反する重い機構だった。捨てた後に「任意個 = レコード 1 個に束ねる(既にある Σ で済む)」という解が見つかった。

教訓:closure に借用を捕捉させ、それを高階関数経由で取り戻そうとすると機構が爆発する。借用は closure に捕捉させず、引数として渡す。 ── これがその後の設計全体(dispatch の borrow-lift・ループの step・escape 防止)を貫く原則になりました。

なお effect row 自体(capability の個数の多相)は現在も却下のままです。単一・抽象の capability [&E](E は型変数)は今の依存量化で書けるため、「effect 多相は無いが単一抽象 [&E] はある」が正確な現状です。

region / lifetime

案(dispatch の capture 問題の試み 3):バッファを region 所有の 'ω ハンドルにし、「現在の瞬間」を表す線形トークンを threading して順序を作る。「効果 = 時間トークンの threading、linearity = 時間は分岐しない、dispatch = 時間の fork-join」という世界観。

撤回の理由:withRegion を λ で書くとその λ がまた永続バッファを capture して封印が再発する。region を新規ブロック構文にせざるを得ず、ネスト・region 多相の複雑さを抱え込む。過剰。

現在:dispatch を構文にして borrow-lift する、で解決(→ GPU 実行)。なお「コピー不可資源の同時読み取り共有」だけは QTT の threading で原理的に表せないため、region か fractional permission が将来必要になる可能性は残っています。

dispatch の形の変遷

  1. explicit-R(関数):触る全バッファをレコード R に束ねて引数で渡す。正しく動くが冗長 ──「ふつうに capture して書きたい」。
  2. capture(closure):'1 資源が closure に封印されて戻ってこない。「closure は '1 を capture できない」原則と衝突し破綻。
  3. region:上記の通り過剰で撤回。
  4. 構文 + borrow-lift(確定):capture のように書けるが closure 値を作らないので封印しない。借りる資源の集合が body 依存 = 関数型を持てない、という点でも構文であることが本質的。

綴りも dispatch(size) λ(i){}(関数形)は「そこに任意の関数を置けるかのような嘘の見た目」として退けられ、dispatch(i in size){ body }(並列 for 形)で確定しました。

eliminator 焼き込みから data + case へ

当初:帰納型はプリミティブとして固定し、型ごとの eliminator(Nat-elim/Bool-elim/Vec-case …)を処理系に焼き込む。「定義の一般機構は作らない」が M0 の方針だった。

転換の理由:QTT の合流規則(どの引数が '0/'ρ/'π か、⊔ と SUM の群分け)を型ごとに手で持つ羽目になった。一般の data 宣言から constructor・case・iota・QTT 合流を導出する方が、規則が一つで済む。

現在:帰納型はユーザ(と prelude)が data で宣言し、分解・再帰は case + ⟦⟧ 一本。専用 eliminator は全廃(J も case で導出)。strict positivity を「inductive であることの定義」として要求します。

同時期に「効果ありの分岐を自動で elaborate する分岐 padding」も撤回されました ── 全 branch に同じ [&R] を付ければ、使わない枝の素通しは [&R] 糖衣の末尾自動 return に吸収され、独立の機構が要らないためです。

Σ-domain 適用から全面 curried へ

当初:関数の引数テレスコープを Σ として一括で渡す(f(a, b) は組 (a, b) の適用)。

転換(2026-06-11):全面 curried へ移行(f(a, b) = (f a) b)。タプルを渡したいときだけ f((a, b))。全 190 テスト green のまま実装が 146 行減り、implicit のカリー化(各 implicit が独立のメタ変数)とも整合しました。型パラメータと辞書が別々に解決できることは instance 解決の前提です(Σ にまとめると「テレスコープの Σ」と「辞書そのものの Σ」が構造的に区別できず破綻する)。

FinArray / build / index の撤去

当初:遅延 pull 配列のためのプリミティブとして FinArray/build/index を持っていた。

撤去の理由(効果系 Phase 6):build f = f・index xs i = xs i ── つまり 素の関数 Fin(n) → A の偽装 で、実体がゼロだった。必要なら関数を直接書けばよい。materialized な可変配列は Array + newArray/set/get が別に担います。

まとめ:繰り返し現れた教訓

  • 借用は capture させず、引数で渡す(FnMut・effect row・region・dispatch、すべてに共通の核)。
  • 糖衣のために意味論を足さない。重い機構を作りかけたら、まず「既にある Σ / QTT で書けないか」を疑う。
  • 「順序」や「安全性」を評価器の挙動(字面順・名前の不可視性)に頼らない。型('1・token の型)に載せる。
  • 紙の上で「綺麗にまとまった」は信用しない。core を oracle にして実装で確かめる。
