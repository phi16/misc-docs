# SC0 とは — 狙いと指針

> この文書は全体のまとめです。個々の機能は [ユーザードキュメント](user/)、
> 実装は [開発ドキュメント](dev/)、原則の一次資料はリポジトリ直下の `philosophy.md` にあります。

## 何を作るためのものか

SC0 は、**メッシュ・画像・音・その他さまざまなものを、手続きではなく数学的な記述で
生成・編集するための言語と環境**です。目指す体験は Houdini に近いものです——
プロシージャルな生成、ノードを繋いだデータフロー、パラメータを動かすと結果が
ライブに追従する制作。対象として想定しているのは、メッシュのレンダリング、シームレス
テクスチャ、シミュレーション、効果音、曲作りなど。最終的には .png / .wav の入出力や
Unity へのアセット取り込みまでを見据えています。

ただし、その実現の仕方が既存のツールとは根本的に違います。

## 中心にある動機：正しく物事を表現する

SC0 の賭けはひとつです。**これまで粗雑に扱われてきたデータや意味を、丁寧に表現する
手段を用意する。そうすると窮屈になるのではなく、逆に柔軟で使いやすいインタフェースが
手に入る。**

厳密さと使いやすさは普通トレードオフと見なされます。しかし実際に道具を壊しているのは
粗雑な表現の側です——「画像はピクセルの配列」「無いときは -1」「型が合わなければ
黙って変換」といった雑な約束が、特殊ケース・暗黙の前提・組み合わせると壊れる UI を
生みます。正しく表現されたものは一様に合成できるので、機構は最小のまま能力が開きます。

この態度はあらゆる層に現れています：

- **画像はピクセル配列ではなく「関数＋実体化の仕様」**。だから解像度と領域から自由で、
  合成は関数合成そのもの。
- **添字（`N`）と座標（`R`）を混ぜない**。暗黙変換ゼロの数値の塔は面倒に見えて、
  次元推論とカーネル化が成立する土台。
- **メッシュの属性はただの関数、トポロジは型**。属性間の整合（同じトポロジに載っている
  こと）が型で保証され、特権的な「Mesh 型」が要らない。
- **「無い」は `Maybe`、「決まらない」は曖昧エラー、「未完成」はホール `?`、失敗した宣言は
  stuck メンバ**。番兵値・既定値・例外で誤魔化さない。隠さないから、穴のあいた
  プログラムでも編集とプレビューが止まらない。
- **書き手の意図も正しく持つ**。意味に効くもの（プログラム）と、意味に効かないが意図に
  効くもの（`@` 折り畳み・ブロックの書き方・`#[node]` の配置や view）を区別し、後者を
  透明な層として保存する。テキストとグラフの双方向編集が成立するのはこの区別のおかげ。

## なぜ依存型か——そしてなぜこういうツールが無かったか

この領域で「正しく表現」したいものは、ことごとく**値に依存する型**です。ベクトルの
長さ（`Vec n R`）、バッファの形状（`Buffer d shape T`）、メッシュのトポロジ
（`Point j`）、添字の範囲（`Fin k`）——次元や形の整合を型で言おうとした瞬間、
依存型は贅沢品ではなく**必須**になります。

一方で依存型は、もっぱら定理証明の道具と見なされ、制作の現場に持ち込めるものとは
考えられてきませんでした。この組み合わせのツールが存在しないのは、価値がないからでは
なく、成立しないと思われてきたからです。

SC0 は、依存型との付き合い方に**階段**を用意することでこれに答えます。

- **ノードを触る範囲**では、型は背後で整合を守る安全網であり、意識する対象ではありません。
  スライダを動かし、ノードを繋ぎ、型の合わない接続だけが正直に断られる——それだけです。
- **コードを書く場合**は依存型に触れることになりますが、証明を書く必要はありません。
  次元は推論され、implicit 引数は文脈から埋まり、リテラルは期待される型として生まれ、
  分からない場所にはホール `?` を置けば期待型が提示されます。日常の書き味は
  普通の関数型言語と大きくは変わりません。

この階段がどこまで滑らかになっているかは、まだ検証の途上です。

## 最大の現れ：関数と実体化

> 数学的な関数を第一級の値として書き、必要な所でだけバッファに**実体化**する。
> 実体化はそのまま並列実行の単位になる。

この整理自体は目新しいものではありません。ただ、「正しく表現する」ことの効果が
もっともよく見える場所なので、最初に挙げます。

SC0 には「画像型」「音型」「メッシュ型」という特権的な型がありません。

- `R² → R³` の純粋関数を書く。これはまだ画像ではない。
- 解像度と領域を指定して実体化（`rasterize`）すると `Buffer 2 [w,h] (Vec 3 R)` になる。
- それを**画像として見る**のはビューア（レンズ）の解釈にすぎない。同じ 1 次元バッファを
  音として再生することも、曲線として描くこともできる。

画像・音・メッシュの違いは「**どの定義域・値域の関数を、どんなサンプリング仕様で
実体化したか**」の違いにすぎない——これが核です。この一点から多くが導かれます：

- **次元・形状は型に現れる**（依存型）。`Vec 3 R` と `Vec 2 R` の混同、解像度の不一致は
  実行前に型エラーになる。厳密な型検査は制作ツールでは珍しいが、「数学的記述が
  そのまま通る」ためにはごまかしのない型が要る。
- **関数の世界とデータの世界が型で分かれる**。まだ計算していない（合成できる・遅延の）
  関数と、サンプル済みの（読める・重い）バッファは別の型で、行き来は明示の操作。
  暗黙にどちらかへ落ちることはない。
- **実体化は並列実行の単位**。`parallel` のカーネルは型消去された IR にコンパイルされて
  一括実行される（将来は GPU）。「速くしたい部分」を別言語で書き直すのではなく、
  同じ λ 計算の中の明示の境界がそのまま実行境界になる。

## もう一つの柱：真実は一つのプログラム

ノードエディタを持つ環境は普通、グラフかテキストのどちらかが真実で、もう片方は
書き出し（エクスポート）です。SC0 では **AST（プログラム）だけが真実**で、Source の
テキストも、Graph も、Workspace も、すべて同じ実体のビューです。どちらから編集しても
同じものに届き、往復で意味は変わりません。

これを成立させているのが「意味と意図の区別」です。プログラム（意味）と、意味に効かない
が書き手の意図に効くもの——ノードの配置・view の指定・`@` による折り畳み・ブロックの
書き方——を分け、後者を透明な層としてソースに保存する。ノードの**粒度**すら言語外の
機構ではなく、著者が `@` で選ぶものです。スライダを動かすと下流がライブに追従する体験も、
「真実がひとつだから、変わった宣言とその下流だけを再計算すればよい」という
この一本化の上に載っています。

## 小さな例

ここまでの話は、次の数行に全部入っています。

```
#[node] {view:{type:"slider", min:0.0, max:1.0, step:0.01}}
let amp : R = 0.5;

#[node] {view:"image", size:[120, 120]}
let pic = rasterize {lo = [0.0, 0.0], hi = [1.0, 1.0], res = [64, 64]}
            (λp. [p.0, p.1, amp]);
```

- `λp. [p.0, p.1, amp]` は `R² → R³` の**ただの関数**です。まだ画像ではありません。
- `rasterize` が領域 `[0,1]²` を 64×64 でサンプリングして `Buffer 2 [64,64] (Vec 3 R)` に
  実体化し、`image` view がそれを Workspace の箱の中に描きます。
- `amp` のスライダをドラッグすると、ソースの `0.5` というリテラル**だけ**が書き換わり、
  変わった宣言とその下流だけが再計算されて画像がライブに追従します。同じ変更は
  Source のテキストを直接編集しても起こせます——届く先が同じプログラムだからです。
- `#[node] {…}` の 2 行は意味には一切効きません。消しても値は同じで、表示だけが変わります。
- そして、ここまで型をほとんど書いていないのに——`p` が `Vec 2 R` であること、色が
  3 成分であること、解像度の形が領域の次元と合っていること——は全部検査されています。

## 既存のものとの違い

より深い比較は読み物ページにあります：
[ノードベース環境の風景](nodes-landscape.md)・
[配列とカーネルの言語（Dex / Futhark / Halide）](relatives-arrays.md)・
[真実と未完成の意味論（Unison / Hazel）](relatives-truth.md)。

### Houdini・ノードベース環境と比べて

ノードベース環境は普通、何百もの専用ノードを持ち、各ノードの意味はツールが個別に
定義します。SC0 は逆で、**言語がひとつあるだけ**です。ノードの中身は普通の関数・
普通の宣言で、専用ノードの動物園を作りません。Houdini 的な体験（配置・接続・スライダの
ライブ反映）は保ちつつ、その下に恣意的な意味論を持ち込まない、という構えです。

ノードベースの世界は実際には何系統もあり（cook 型・信号型・制御フロー型・言語両表現型…）、
それぞれとの比較は別ページにまとめました：
**[ノードベース環境の風景と SC0 の位置](nodes-landscape.md)**。

### シェーダ・クリエイティブコーディングと比べて

Shadertoy 的な「座標→色の関数を書く」体験は SC0 の一部ですが、

- 型が本物（依存型・形状追跡・暗黙変換なし）。`N`（添字）と `R`（座標）の混同のような
  「GPU コードにありがちな静かなバグ」が型で消える。
- ホスト言語とシェーダ言語の二層構造がない。カーネルは**部分評価の結果として創発**する
  ——λ の下の座標非依存部分は畳まれ、残差が IR になる。書くのは常にひとつの言語。
- 実体化の失敗（IR に乗らない）は黙って遅い経路に落ちず、正直にエラーになる。

### 定理証明系（Agda / Idris / Lean）と比べて

型システムの骨格（依存型・Π・NbE・ホール `?`）は証明支援系の系譜ですが、
**証明のためでなく制作のための依存型**です（前述）。運用が違います。

- 証明は書けるなら書く。ただし基底型（`N`/`R`）の性質は言語内で証明できないので
  postulate とし、面倒な証明は `trustMe` で「主張だけ正しく立てて正しさを引き受ける」。
  その代わり嘘の等式は**評価時に実行時検査で honest に落ちる**。
- **一般再帰がない**。反復は有界反復（`iterate`/`for`）のみ。停止性が構造で保証され、
  カーネル化（unroll / ループ IR）とも整合する。

### 汎用関数型言語（Haskell 等）と比べて

見た目は近いですが、設計の力点が「**恣意的な既定を一切持たない**」に置かれています。

- リテラルの型は文脈から決まり、決まらなければ**曖昧エラー**（defaulting はない）。
- 演算子の優先順位に既定はない。`+` の fixity すら標準ライブラリの宣言。
- 型クラスは専用機構ではなく「nominal なレコード＋値としてのインスタンス＋探索」だけ。
  変換も `From` 一本。`render` すら標準ライブラリの普通の `let`。
- 機構を最小に保ち、能力をライブラリとデータに開く。組み込みと自作が対等。

## 本質的な指針

`philosophy.md` の 7 原則が判断の拠り所です。どれも「正しく物事を表現する」を
設計判断の形にしたもので、言語・環境の随所はその帰結として導かれています。

1. **恣意的な選択をしない（No ad-hoc・最優先）** — 分岐しうる点はすべて表に出し、
   決定を持つ主体に委ねる。決まらないなら決まらないと言う。
   ↳ リテラルの曖昧エラー、fixity 無既定、レンズの自動判定なし、slider の min/max は著者が明示。
2. **正しさは構造で判断する** — 「テストが通る・今動く」で妥協せず、あるべき形に照らす。
   ↳ 対症療法でなく型分割（Surface/Core）や機構の一本化（From・build_decls）で
   バグのクラスごと消す、という開発の仕方そのもの。
3. **真実は一つ、表現はそのビュー** — 正準な実体をひとつ持ち、テキスト・グラフ・図は
   すべてビュー。意味に効かないが意図に効くもの（`@`・`#[node]`・ブロックの書き方）は
   透明な層として保存する。
4. **意味は局所的・決定論的に決まる** — 暗黙のグローバル状態を読まない。文脈は明示的に
   運ぶ。トップレベル宣言は自分だけで型が閉じる（これが incremental 再計算の前提でもある）。
5. **早すぎる特殊化をしない** — 特殊は一般の一例。画像型を作らない、Mesh 型を作らない、
   ネイティブ値も汎用の入れ物に載せる。固定した瞬間に選ばれなかった可能性が隠れる。
6. **不在・失敗・未完成を正規の状態にする** — ホール `?` を含むプログラムは編集も
   プレビューも続けられる。失敗した宣言があっても他の宣言は本物の型で検査が続く。
   消えたノードの popup は空になる（壊れない・捏造しない）。
7. **能力は明示的な境界の中でだけ与える** — 実体化・最適化・信頼（trustMe・Fin の供給）は
   明示の境界に閉じ、境界の外は単純で予測可能なまま保つ。

## どこまでやるか——境界と広がり

- **汎用プログラミング言語を目指してはいません**。ただし、正しく作られた土台は結果として
  広い範囲に届きうるとも考えています。射程の目安はゲームです——ゲームが作れる程度に
  汎用的であれば、この領域で必要になることの大半は表現できるはずです。
- **イラストやスカルプトのような手作業の編集**は、対象外ではなく将来の拡張先として
  視野に入っています。ただし持ち込み方は SC0 の流儀に従います：手続き的編集は
  **その過程すべてをデータとして持つ**べきです。線の軌跡なら、ハードウェアからの
  生の入力列がそのままデータとして残り、描かれた線は**その解釈**として導かれる——
  手作業すら「真実は一つ、表現はビュー」の中に入ります。ストロークを画像に焼き込んで
  情報を捨てるのではなく、入力という真実を保存し、解釈を後からいくらでも変えられる形です。

## 現在地と向かう先

動いているもの：言語コア（依存型・クラス・モジュール・nominal・enum・Id/J）、
実体化とカーネル IR、メッシュ（ハーフエッジ・属性＝関数）、Web 環境（双方向編集・
view 埋め込み・スライダのライブ反映・incremental 再計算）、CLI・LSP。

これからのもの：効果システム（乱数・シミュレーション・I/O を型に現れる効果として）、
GPU バックエンド、実行系の汎用 IR への一本化、Unity 連携、ファイル I/O の拡充。
言語名も暫定です（SC0 は仮称）。
