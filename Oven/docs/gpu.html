Oven ── 言語の記録

GPU 実行 ── dispatch と lowering

言語の二枚看板の片方です(もう片方は効果系)。GPU 上で明示的に並列計算を走らせます。

データ所在:Array と Buffer

データが host(CPU)側か device(GPU)側かを型で区別します:

Array  : (n : U32, A : Type) -> Type    // host 常駐・materialized。in-place 可変(&Array 借用の set/get)
Buffer : (n : U32, A : Type) -> Type    // device 常駐。線形資源('1)── 勝手にコピー/破棄できない

newBuffer : [A : Type] (n : U32) -> Buffer(n, A)                    // 出力バッファ確保('1 資源)
readback  : [A : Type] (n : U32, buf : '1 Buffer(n, A)) -> Array(n, A)  // device → host(buffer を消費)

長さ・添字はともに 機械整数 U32 です(unary な Nat の O(n) コストを排除し、GPU の現実に合わせる)。添字は生の U32 で境界証明を持ちません ── 将来、値 i : U32 に消去証明 '0 Lt(i, n) を添える形で境界安全を復活させる構想があります(→ 現状)。

遅延した pull 配列が欲しければ素の関数 Fin(n) → A を書きます。かつて存在した lazy generator(FinArray/build/index)は「build f = f・index xs i = xs i で済む偽装」だったため撤去されました。

dispatch ── 関数ではなく構文

GPU の並列カーネルは専用構文です:

dispatch(i in size) { body };  cont
//   size : U32³(グリッド = スレッド数)、i : U32³(スレッド ID。body 内で束縛)
//   body : GPU の命令的コード([&GPU] 効果)。全スレッドについて並列に走る

let と並ぶ束縛文で、core では Tm::Dispatch(size, body, borrows, cont) という専用ノードです。なぜ関数ではないのか:

  • カーネルは「任意個のリソース(入出力バッファ)」に触りたい。関数にすると closure が '1 資源を capture することになり、「closure は '1 を capture できない」原則と衝突する(capture した線形資源が封印されて戻ってこない)。
  • 明示的にリソースをレコードで渡す形(explicit-R)は動くが冗長。region 機構は過剰。──と回り道した末に、「capture は書く。でも封印しない。そのために構文にする」に落ち着きました(→ 経緯)。
  • 借りる資源の集合が body の中身で決まる = 型が body に依存するので、そもそも関数型を持てない という事情もあります。

borrow-lift

dispatch の型検査は、body が参照する 自由な host 線形('1)変数 を走査して集め、host 側で「1 回消費 → 継続へ fresh に返す」borrow(consume-and-return)を行います。これが borrow-lift です。

let '1 out : Buffer(n, F32) = newBuffer(n);
dispatch(i in (n, 1[U32], 1[U32])) {
  store(out, i.0, f(u32ToF32(i.0)))     // out は自由な '1 変数 → 構文が borrow-lift
};
readback(n, out)                         // out は dispatch 後も生きている
  • host の QTT はカーネル内部の使用回数を数えません。借りた資源を境界で各 1 回消費するだけです。
  • release(out); dispatch { store(out,…) } のような use-after-free は、外側の '1 束縛検査(消費済みの変数を借りに行けない)が弾きます。
  • '0/'ω の自由変数(サイズ・関数)は単相化・コピーで GPU コードに焼き込まれます。
  • 構文なので closure 値が存在せず、カーネルは脱出も封印もしません。代償として「カーネルを値として持ち回る」ことはできません。

カーネル内の効果順序

カーネル内の store/load は [&GPU] 効果です。零幅の GPU token を '1 で threading して順序をデータ依存として型に載せます(→ 効果系)。ユーザは token を書かず store(buf, i, x) とだけ書き、elaboration が縫います。

buffer 自体は 'ω(並列読み書き自由)で、race は型で追いません。スレッド間競合の正しさ(atomic・書き込み先の重複回避)は compute-shader と同じくプログラマの責任です。

かつては「カーネル内は QTT オフの命令的コードで、順序は素のプログラム順」という整理でしたが、これは「評価器が字面順を守ることに意味が依存する = 参照透過でない」ため撤回され、host IO と同型の token threading に統一されました(2026-06-12。→ 経緯)。

表現可能性

GPU で走る断片に現れる型は「GPU でデータとして表現可能」でなければなりません。この検査は dispatch の境界(入出力 + borrow-lift される資源)と、kernel 本体の実行時 binder(λ 引数・let・case パターン・split)で課されます。実装上は型検査文脈の in_kernel: bool フラグ(dispatch body の検査中だけ立つ)が駆動します。

  • representable:スカラ(F32/U32/U8)、Buffer(n, A)(要素は storable)、Σ(struct。Unit は空 struct)、同型スカラのタプル(= ベクトル。下記)、有限 enum。
  • storable(buffer の要素にできる plain データ):スカラ・Σ・Unit のみ。Buffer は不可 ── 実 GPU 同様、buffer に buffer ハンドルを格納させません。これは美観ではなく soundness の要件です:カーネル内で '1 資源を別 buffer に store して host へ別名つきで返せば、線形資源が複製できてしまう ── この抜け道は敵対的レビューで実際に発見され、storable 制限で塞がれました(tests/soundness.rs)。
  • 不可:Nat・Vec・関数型・Type など。case のパターンフィールドにも representable を課すので、Nat/Vec のような再帰型は succ/vcons のフィールド型で自動的に弾かれます(動的回数の再帰の排除)。
  • 有限 enum(全 constructor が引数なし:Bool、data Dir { east, west } 等)は u32 タグとして representable かつ storable です。case は WGSL の switch(Bool は if/else)に lower されます。引数つき sum(tag + payload)は未対応。
  • '0 の消去値(サイズ・型)は自由に境界を越えられます。

将来は binder ごとの検査を Repr(A) witness(「A は GPU-native な担体の retract」という証拠を instance として表明する)に置き換え、representability を「境界 + witness」へ寄せる構想があります。prelude には既に nominal Repr (A : Type) = (Carrier : Type, into : A -> Carrier, out : '0 …, coh : '0 …) が置かれ、witnessed な inductive の fold が GPU の for ループに lower される縦串も実験済みです。

ベクトル型 ── 同型スカラのタプルがそのまま vecN

F32²/F32³/F32⁴ は 別の型ではありません。同型スカラの 2〜4 成分タプル (F32, F32, …) が、GPU lowering でそのままネイティブ vecN<f32> になります(U32 も同様)。

  • 構築はタプル (a, b, c)、成分アクセスは射影 .0/.1/.2(WGSL の .x/.y/.z に対応)。
  • 型位置の無名タプル (F32, F32, F32) は Σ 型に解釈されるので、(x:F32, y:F32, z:F32) と書かなくてもよい。色 (r,g,b) も自然に vec3 になります。
  • 演算はネイティブ WGSL に lower されます:+ - *(成分演算・instance 経由)、dotF32xN/lengthF32xN/normalizeF32xN など。これらは src/builtins.rs::vec_builtins() のレジストリに宣言的にまとまっています。
  • CPU emulation は成分を分解して計算します(値の表現は普通のタプルのまま)。
  • std430 のアラインメント(vec3 のストライドが 16 バイト等)は「WGSL の都合」なので gpu.rs の buffer I/O だけに閉じ込め、コア型・runtime・言語には漏らしません。

narrow 型:U8 と U8⁴(RGBA8)

U8 は整数バイト [0,255] の一級スカラです(算術・比較・変換つき。GPU に u8 は無いので u32 表現 + & 255u マスク)。U8⁴ = (U8,U8,U8,U8) は RGBA8 として 1 個の u32 に bit パック されます(vec4<u32> の 16 バイトではなく 4 バイト)。PNG・テクスチャに native な形です。パックは GPU lowering と読み戻しのデコードだけで行い、CPU emulation は U8 タプルのまま扱います ── std430 と同じ「GPU の都合の局所化」です。正規化色 UNorm8 は別の型として将来入れます。

数値 primitive レジストリ

純スカラの数値 builtin(算術 addF32…divU32・変換 u32ToF32 等・比較 ltF32 等・math sinF32/sqrtF32/clampF32 等)は、単一の表 src/builtins.rs::NUM_BUILTINS に「名前・引数型・戻り型・CPU 計算・WGSL 形」を宣言的に持ちます。prelude の postulate 型はこの表から自動生成され、NbE の畳み込み・CPU emulation・GPU lowering も同じ表を引きます。新しい数値 primitive の追加は表に 1 行 で済みます(かつては 5 箇所の同期が必要でした)。

CPU 計算は WGSL のセマンティクスに合わせます(fract = x−floor(x)、log = 自然対数)。超越関数は実 GPU と libm とで ULP 差がありうるため、GPU テストは許容誤差で比較します。

lowering パイプライン

表面構文 ── parse ──▶ surface AST ── elaborate ──▶ 型付き core Tm
                                                      │
                    ┌─────────────────────────────────┤
                    ▼(CPU 経路)                       ▼(GPU 経路・dispatch body)
              erasure('0 を消す)                lower(型主導)
                    ▼                                  ▼
              Rt(実行時 IR)                      KernelIR(一階・全式に型)
                    ▼                                  ▼
              tree-walking 実行                    WGSL テキスト
             (CPU emulation)                          ▼
                                                  wgpu(feature `gpu`)で実行

要点:

  • GPU lowering は無型の Rt からではなく、型付き elaborated Tm から行います。GPU は全式に型が要るためです(CPU emulation の Rt は無型・高階・構造的再帰ありで、GPU と性質が真逆)。
  • shader になるのは dispatch の body だけで、host 部(newBuffer/dispatch/readback のオーケストレーション)は CPU 側ドライバに残ります。実 GPU 実行時、データは GPU 常駐 ── buffer は storage buffer として確保し、readback のときだけ CPU へ写します。
  • CPU emulation がリファレンス・オラクル です。同じプログラムを CPU 経路(依存ゼロ・既定)と GPU 経路(feature gpu)の両方で走らせ、同じ結果になることをテストが確認します。
  • カーネル境界の inliner がヘルパ関数呼び出しを展開し、静的回数の iterate は(共有つきの)静的アンロールに落ちます。第一級関数は GPU に無いため、特殊化で消えます。

host 特殊化 ── 「値 = 関数。GPU はそれを実行するだけ」

カーネルを関数でパラメタ化する汎用パターンが動きます(examples/sound.ov):

// n サンプルを GPU で並列レンダリング。f はコンパイル時に確定した closure で、
// lowering 時にカーネルへ展開される(第一級関数は GPU に無い ── 特殊化で消える)
render : (n : U32, f : F32 -> F32) -> Array(n, F32)
  = λ(n, f) let '1 out : Buffer(n, F32) = newBuffer(n);
            dispatch(i in (n, 1[U32], 1[U32])) {
              store(out, i.0, f(u32ToF32(i.0) / 8.0))
            };
            readback(n, out);

render(8[U32], λ(t) sinF32(t))

render の関数引数 f は、inliner の host β 簡約(閉じた引数の適用をコンパイル時に展開)によってカーネルへ特殊化されます。「音も画像もアセットも、値 = 関数として書き、GPU はそれを実行するだけ」という言語の狙いの土台です。

共有を保つ quote(指数爆発の回避)

escape(c) = (iterate(...)).cnt のようにラッパ越しに反復を呼ぶと、GPU lowering の quote(eval(…)) が NbE の共有 DAG を木に展開して指数爆発する(反復あたり13倍・30GB 到達)問題がありました。nbe::quote_shared ── eval の Rc-DAG を let 配列に平坦化し、GVN で共有を保ったまま quote する ── で解決済みです。showcase の 16 回反復マンデルブロが CPU/GPU 両経路で完走します。

case→for(witnessed fold)

fromU32 : (n : U32) -> Nat は機械整数を「回数」に橋渡しします(論理的には succ^n(zero) だが、実行時は担体 u32 のまま)。これにより iterate(fromU32(n), f, init) の case(fold)が for ループ に lower されます ── 「functional を for に翻訳する」対象の最初の実例です。どの u32 も Nat なので全域です。
