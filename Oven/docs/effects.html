Oven ── 言語の記録

効果系 ── 借りて返す

Oven は純粋言語ですが、IO・可変状態・GPU への書き込みを書けます。核となる考え方は一つだけです:

副作用も借用も「線形に借りて返す」(&)で表す。

モナドはありません。print や store のような効果は、その世界の token(World・GPU などの不透明な型)を 借りて(消費して)・返す 関数として型が付きます。token は線形('1)なので「一度使ったら次の token に進む」── 効果の順序がデータ依存として型で強制されます。そして token は暗黙に供給されるため、ユーザは書きません。

2026-06-14 に設計確定し、Phase 1〜6 前半まで実装済みです(→ 現状)。

& の核:consume-and-return

& は型の頭に付く borrow 注釈です。意味は「線形に消費し、結果で返す」:

// あなたが書く型:
set : [A : Type] [n : '0 U32] (&Array(n, A), i : U32, x : A) -> Unit

// 脱糖後(借りた Array を結果タプルで返す):
set : … ('1 Array(n, A), i : U32, x : A) -> (Array(n, A), Unit)

呼び出し側 set(&arr, i, v) は arr を消費し、更新後の配列を 同じ名前に再束縛 します(パーサが let (arr, _) = set(arr, i, v) へ脱糖)。呼び出し以降の arr は更新後を指します。

Rust の &mut に相当しますが、lifetime は要りません。「消費して返す」threading 符号化なので、借用の有効範囲はデータの流れそのもので決まります。安全性を担保するのは linearity です ── token や資源を明示的に名前で書いても構いませんが、二度使えば QTT の線形検査が弾きます。「名前で書けないから安全」ではなく「'1 だから安全」が正しい筋、と設計は明言しています。

2×2:& は括弧と直交する

borrow は「implicit([])か explicit(())か」と独立の装飾です:

非 borrowborrow(&)
explicit ()普通の引数 (x : A)a : &X = 明示借用(可変資源)
implicit []辞書/型 [d : C][&X] = 効果(暗黙借用 token)
  • 明示借用 a : &X:資源を名前で渡す(set(&arr, …))。host の可変 Array がこれ。
  • 暗黙借用 [&X]:資源を型で暗黙解決する(ambient から拾う)。効果 token がこれ。

脱糖の核('1 引数 + 結果へ資源を返す)は両者で同一で、違うのは解決方法(名前で引くか型で引くか)だけです。既存の implicit/explicit の二択を、そのまま borrow に流用した形になっています。

効果 former [&X]

効果は capability 型 X : Type で表します。World(host IO)・GPU(カーネル)・将来の Log・State S など。token は零幅でも(World/GPU)、データ持ちでも(State S)構いません ── 単なる線形値です。

[&X] A        ≝  '1 X → (X, A)
[&X, &Y] A    ≝  '1 X → '1 Y → (X, Y, A)    // 相異型なので独立に threading

prelude の効果プリミティブ:

postulate assert : (b : '1 Bool) -> [&World] Unit
postulate print  : [A : Type] (x : '1 A) -> [&World] Unit
postulate store  : [A : Type] [n : '0 U32] (buf : Buffer(n, A), i : U32, x : A) -> [&GPU] Unit
postulate load   : [A : Type] [n : '0 U32] (buf : Buffer(n, A), i : U32) -> [&GPU] A

World と GPU が 別の型 であることが安全性を担います:host で store を呼ぼうとしても、host の ambient には GPU token が無いので型不一致で弾かれます。かつてこの安全性を担っていた 'GPU modality(型に付く world 印)は全廃されました(→ 経緯)。

assert/print の引数が '1 なのは細かいが実際的な設計です:assert(eqArray(readback(a), readback(b))) のように線形 buffer 由来の値を渡すとき、引数が 'ω だと引数式の使用量が ω 倍にスケールされて線形性違反になってしまうためです。

ambient と threading 規則

elaboration の文脈は「いま使用可能な '1 効果束縛」(ambient)を持ちます。同型の ambient は常に一意です(同型二重取りは禁止 ── 解決の曖昧性を断つため)。

  • entry:[&X] _ ブロックに入ると fresh な w₀ : '1 X を据える(main は World、dispatch body は GPU)。
  • consume + rebind:効果呼び出し c : [&X] A は token を即時供給 → 返る (X, A) を分解し、新しい token を ambient に、値を文の値とする。
  • exit:ブロック値 r と最終 ambient wₙ を組にして返す。
  • case:各枝を同じ入り ambient で elaborate し、同型の出 token を合流(「同じ world を各排他枝へ」)。

つまりユーザが

main : [&World] Unit
main = { print("hello"); print("world") }

と書くと、elaboration が λ(w0) let (w1, _) = print("hello", w0); print("world", w1) 相当の core 項(実際は implicit 供給形)へ縫い上げます。効果の順序は「字面の順」= token のデータ依存の順です。core に出る形は素の Π と Σ の分解束縛の連鎖なので、実行系は効果を知りません。

≤1 効果/文 の規則があります:load を関数引数に直接ネストせず、let v = load(…) で束縛してから使います(1 つの式に効果ある部分式は 1 つまで。順序は ;/let だけが作る)。

多 capability

[&X, &Y] ブロックでは、各効果呼び出しの capability 列を ambient から 型(structural equality)で対応づけ、該当する token だけを消費・再束縛します。それぞれの効果が独立の線形チェーンを成すため、[&World, &Log] Unit のようにビルトイン効果とユーザ効果を同じブロックで合成できます。零幅(World)か実値(Log)かは threading に無関係です ── token は単なる線形値なので。

resolution の統一 ── ω 辞書と linear token は同じ規則

typeclass の辞書(implicit)と効果 token(implicit borrow)を別機構にしません。一つの規則:

implicit/borrow 引数の解決 = wanted 型の「使用可能な束縛/プール項」を文脈から見つけ、usage を消費する。

  • ω 辞書(Mul(A) 等):使用が尽きない=再利用可。型が ground でないことがあるため 遅延 解決(メタ変数 + pending)。
  • linear token('1 X):一度で消費。型は ground(World/GPU)なので 即時 解決。

ω/linear の差は multiplicity から、遅延/即時の差は「型が ground か」から落ちる ── どちらも別扱いではありません。実際に「implicit w0 : X = init を置けば既存の instance 解決が [&X] の token を型で自動供給する」ことが実装で確認されています(discharge が新機構ゼロで書ける、ということ)。

escape は 2 規則から閉じる

threading された token(io 等)がスコープ外へ漏れないことは、closure 設計の 2 規則(QTT の章)だけから出ます:

  1. closure は '1 を capture できない → token を閉包に持ち出せない。
  2. '1 引数の部分適用ができない → let k = print(io0) で token を握れない。

加えて '1 は複製不可(2 回使用は違反)、token は drop 不可(返り型 (X, …) を満たせず握り潰せない)。よって token は 1 本の線形スレッドに閉じ、必ず caller に戻ります。一方 capability 関数([&X] A→B)自体は 'ω 値で token を抱えない(呼ぶたび引数で受ける)ので、自由に持ち回れます。escape 防止のための新しい機構はゼロです。

効果つきの分岐と反復

分岐も反復も case 一本です(専用の if はありません)。branch は '1 を capture できないので、threaded 資源は branch の 引数 で受けます = motive を [&R] 付きの関数型にするだけ:

case[λ(_) [&World] () → ()](b) {
  true  => λ[&World]() print("yes"),
  false => λ[&World]() (),          // token を使わない枝も、[&R] 糖衣が末尾で token を自動で返す
}

「使わない枝で token を素通しする(padding)」は独立の機構ではなく、[&R] の「宣言した capability を末尾で必ず返す」性質に吸収されます。線形性も既存規則のまま:両枝が token を 1 回ずつ使うので ⊔(1,1)=1 で生存します。

反復は motive に threaded 型を載せ、⟦⟧(帰納仮説)に資源を通します(iterateEff。→ QTT)。succ 枝は 'ω なので '1 を capture できず、資源は ⟦⟧ を通すしかない ── これも型から自動で強制されます。

部分借用 &r.field = lens

&r.a とフィールドへ絞って借りられます(設計確定・実装は今後)。これは Rust の(エイリアスと lifetime を気にする)部分借用ではなく、線形 lens(getter と putback の対)です:

Lens(S, A) = (s : '1 S) → ('1 A, ('1 A) → S)   // 焦点 A と「埋め戻し」関数を返す

レコードのフィールドや配列要素には lens が構造的に導出でき、合成もできます(&r.a.b は lens の合成)。呼び出し側の脱糖は「get → 関数で thread → putback で再構成 → 元の名前へ再束縛」。純粋・全域なので線形性と矛盾しません。lens にできる path(フィールド/要素)に限られ、&(任意の式) は書けません。

discharge(handler)

効果はどこかの境界で discharge されます:

  • World(host IO):プログラムのトップレベルが host ブロック(chain に host 効果がある)だと、コンパイラが自動で runHost(λ[w] …) に包みます。runtime の iota が初期 token を供給して走らせ、assert の失敗は panic 報告、最終 token は捨てられます。built-in。
  • GPU:dispatch が body の GPU 効果を discharge します(スレッドごとに fresh token を供給してカーネル実行)。built-in。
  • ユーザ効果(Log / State 等):「explicit な値を ambient token として供給する」は既存機構(implicit w0 : X = init + instance 解決)で既に書けます。効果操作はただの [&X] 関数、可変資源版は &T 借用関数 ── 「ユーザ handler」の大半は既存機能の組み合わせで済むことが分かっています。残っているのはトップレベルで合成ブロック([&World, &Log])を discharge する runner の配線です(runHost は [&World] Unit 専用)。

buffer は効果の外

GPU の Buffer は [&Buffer] にも &Buffer にもしません。カーネル内の buffer は 'ω(並列読み書き自由・race は型で追わない) で、命令の順序づけは GPU token が一手に担います。host→kernel の移動は dispatch の borrow-lift(明示借用の built-in 特例)が処理します。&Array の明示借用が活きるのは host 側の 逐次 可変配列(set/get)です。

// examples/setget.ov の要素:host の可変配列を借用で更新する
let '1 a : Array(4[U32], U32) = newArray(4[U32], 0[U32]);
set(&a, 2[U32], 7[U32]);        // a を消費し、更新後の a を同名に再束縛
let v = get(&a, 2[U32]);        // 読み出しも借用
