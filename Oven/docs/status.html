既知の割り切り(意図的)

  • Type : Type:論理的不健全 + 型検査器の発散可能性を受容(timeout/fuel は任意の保険)。
  • race は型で追わない:スレッド間競合の正しさはプログラマの責任(compute-shader と同じ)。
  • カーネルは値にならない:dispatch は構文。カーネルのライブラリ化はできない。
  • effect row はない:capability の個数の多相は却下。単一抽象 [&E] で書ける範囲まで。
  • 同型 ambient の二重取り禁止:解決の曖昧性を断つため。

未解決・不安(疑い続けるところ)

設計ノートが「まだ考え切れていない」と明示しているものです:

  1. &/ブロック threading の desugar の全体像。個別規則(入力は表面順・返りは thread-first、& は Π の直接テレスコープのみ、≤1 効果/文、lens、case は [&R] motive)は確定したが、parse 時の借用脱糖と typecheck 時の効果 threading が別実装のままで、一本化が残っている。再束縛のスコープ(shadowing)の厳密な扱いも。
  2. case 使用量規則の一般化:非再帰 constructor が動的回数走る型(二分木の葉)では「⟦⟧ 無し = 高々 1 回」の前提が崩れる。組み込み型は健全だが、ユーザ定義の分岐木に穴。群の決め方を「高々 1 回か動的回数か」へ一般化する必要。
  3. 線形 payload × 帰納 family:「再帰時に尾を '0 にする」は既知の patch の再現であって原理から出た解ではない、と自覚されている。case(尾 'ρ)と再帰(尾 '0)の 2 系統割れ・Vec の「Nat で回す」が一般 inductive に一般化しない、など。一般 inductive の eliminator 生成を形式化する段で設計し直す可能性が高い。文献的にも(Idris 2 含め)未解決寄りの領域。
  4. dispatch の特権性の健全性:「境界は線形な借用・内部は race 非検査」が host の純粋性を壊していないことの完全な論証。具体的な抜け道(buffer 経由の線形資源複製)は 1 件発見・修正済み ── 敵対的レビューは今後も必要。
  5. '1 読み取り壁:実値の状態 token(State S)を ω 的な算術で読む問題。Idris 2 の QTT 設計を参照予定。
  6. world 境界をまたぐ量の精密化:'0 消去値の越境などの端。
  7. NbE の発散:Type : Type の帰結として受容済みだが、timeout/fuel をいつ入れるか。
