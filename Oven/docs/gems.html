Oven ── 言語の記録

珍しい機能カタログ

Oven には、他の言語ではあまり見ない機能や設計判断が多くあります。この章はそのカタログですが、単なる一覧ではなく、それぞれについて「なぜこういう選択をしたのか」を語る ことを目的にします。多くの項目は「もっと普通の選択肢」がまずあって、それが何かの理由で採れなかった、という物語を持っています。仕様としての正確な定義は各リンク先の章にあり、ここでは動機と、実装がどうそれを支えているかを書きます。

型理論まわり

⟦w⟧ ── 帰納仮説を書くための括弧

Oven の再帰は、case の branch 内で ⟦w⟧(ASCII では [[w]])と書きます。「部分構造 w に対するこの case 自身の結果」── 数学の帰納法でいう帰納仮説です。

case[λ(k) Nat](n) { zero => m,  succ(k) => succ(⟦k⟧) }   // n + m

なぜこの形か。 全域言語で再帰を書く方法は、大きく 2 つ知られています。ひとつは生の eliminator(Nat-elim のような畳み込み関数)で、安全性は自明ですが、実際に書くと motive やメソッドの受け渡しが煩雑で、人間が日常的に書く形ではありません。もうひとつは Idris や Agda のように一般再帰を許して 停止性検査器 を後付けする方法で、書き味は自然ですが、検査器そのものが複雑な機構になり、「なぜこのプログラムは全域なのか」の根拠が構文から見えなくなります。

⟦⟧ はその中間を狙った選択です。⟦w⟧ は その branch の再帰パターン変数にしか適用できない ── この構文制約ひとつで、書けるのは構造的再帰だけになり、全域性が構文的に自明 になります。停止性検査器は存在しません。意味論としては生の eliminator と等価(安全性はそのまま)でありながら、見た目は「branch の中で再帰結果を参照する」という直観的な形です。denotation bracket(意味論の ⟦⟧)を借りた記法で、「これは項ではなく『意味』を参照している」というニュアンスも込められています。

実装に踏み込むと、core の項は Tm::Ih(idx, w) で、idx は「どの recursor に属する帰納仮説か」を指す recursor スタックへの index です。この index は当初存在せず、「⟦⟧ は最内の case のもの」と暗黙に決めていたのですが、それでは壊れるケースが見つかりました:再帰関数の 値 を quote(正規形へ書き戻し)すると、別の再帰が入れ子に展開されることがあります。たとえば mult(乗算)が本体で plus(加算)を呼ぶと、quote の途中で plus の recursor が mult の recursor の内側に現れ、「最内」の指す先がずれて quote∘eval が恒等でなくなる(実際に無限展開しました)。⟦⟧ を正しい recursor に固定する index を持たせることで解決しています。「束縛の参照は名前でも『最内』でもなく、de Bruijn 的に数えろ」という教訓が、変数だけでなく帰納仮説にも当てはまった、という話です。

case の使用量規則 ── なぜ ⊔ 一本ではだめだったか

QTT の言語で分岐の使用量を合流させる標準的な方法は「各枝の使用量の上限 ⊔ を取る」です。実行時に通る枝は一つなので、これで健全です。Oven も最初、case の全 branch をこの一つの ⊔ プールで測っていました。

これには 穴ではなく、逆向きの問題 がありました:正しいプログラムを弾いてしまうのです。線形資源 s0 : '1 S を fold の初期値に入れ、帰納仮説で threading するループ(iterateEff)を考えると、zero 枝は s0 を 1 回使い、succ 枝は 0 回使います。これを ⊔ すると ⊔(1,0) = ω ── 線形資源が ω に化けて、完全に正当な線形ループが型検査を通りません。

原因を突き詰めると、「分岐」と「fold」では枝の関係が違うことに行き着きます。分岐の枝は排他的ですが、fold の基底と step は両方走ります。両方走るものの使用量は ⊔(どちらか)ではなく SUM(合計)で測るべきです。そこで branch を ⟦⟧ を使うか否かで 2 群に分け:

Δ(case) = π_scrut·Δ_scrut + ⊔(⟦⟧ 無しの branch) + ω·⊔(⟦⟧ ありの branch)

再帰群に ω を掛けるのは、step が動的な回数走るためです。これで「線形資源は帰納仮説を通せば fold を生き延び、closure に capture したら弾かれる」という、望んだ通りの挙動が規則から出ます。

面白いのは Idris 2 との対比です。Idris 2 は一般再帰 + 停止性検査の言語なので、再帰呼び出しはただの関数適用 1 回と数えられ、この問題自体が発生しません(線形 fold が素直に書けます)。Oven は「反復を case の構造的再帰に限定する」選択をした 代償として この群分け規則を持ちますが、SUM 規則によって表現力は Idris の線形 fold と等価になっています。設計の選択が別の場所に請求書を回してくる、その請求書をきちんと払った例です。

実装では typecheck.rs の combine_case がこの式そのものです。実装上の注意がひとつコメントに残っています:⊔ には単位元がありません(⊔(0,1) = ω なので、ゼロから ⊔ を始めると壊れる)。だから各群は「最初の branch の使用量で初期化し、2 個目以降を ⊔」します。また ⟦⟧ の有無の判定(uses_ih)は入れ子の case の branch には降りません ── そこの ⟦⟧ は内側の case に属するからです。

→ 規則の全体は QTT

第一級 multiplicity ── 1 + 1 が ω になるのも instance

多くの QTT 実装で multiplicity は型の注釈に住む特別な存在です。Oven では Mult : Type ── multiplicity は普通の値であり、'p の p に変数も式も書けます。

なぜ第一級にしたか。 直接の動機は multiplicity 多相です。たとえば map は、純粋なデータ('ω)にも線形な資源の列('1)にも使いたい。multiplicity が言語の外の注釈だと、この多相のために別の量化機構が要ります。Mult がただの型なら、mult 多相はただの依存量化 (p : Mult, x : 'p A) → A になり、新しい機構がゼロ で済みます。半環が 3 値で有限なので、多相関数の検査も原理的には全 valuation の列挙で決定可能 ── 「特別な solver が要るのでは」という当初の心配は、有限性を活かせば杞憂だと分かりました。

そして第一級にした以上、半環演算 +/·/⊔ も言語の中の演算です。ここで Oven らしい徹底が入ります:1 + 1 と書いたときの + は、パーサにも型検査器にも特別扱いされていません。ambient prelude の Add(Mult) instance(中身は組み込みの addMult)が、F32 の加算と全く同じ経路 ── mixfix 脱糖 → instance 解決 ── で選ばれ、NbE が半環を畳んで ω になります。「乗法 * を特別扱いせず、multiplicity の半環すら instance で賄う」は明示的な設計方針でした。動機は一貫性です:* が文脈によって「言語の一部」だったり「ライブラリ」だったりする言語は、ユーザに 2 つのルールを覚えさせます。Oven はルールを 1 つにしました。

実装では core に MultT/M0/M1/MW と演算ノード MAdd/MMul/MJoin があり、NbE の iota が畳みます。multiplicity は 型構造の一部として conversion で比較される ため、'(1+1) A ≡ 'ω A が定義の等しさとして成立します。一方、使用量(どの変数を何回使ったか)は conversion に一切効きません ── 「量は型の形には出るが、計算には出ない」という分離が保たれています。

trustMe ── 消去される公理という脱出ハッチ

postulate trustMe : [A : '0 Type] (u : Unit) -> A

任意の型 A の値を出す公理です。当然、論理としてはこれ一つで崩壊します。それでも置いてあるのは、証明義務を「あとで」にできる言語のほうが実用で生き残る からです。たとえば並列 reduce は演算の結合性に正しさが依存するので、結合性の証明 '0 Assoc(op) を引数に取る設計です。しかし「reduce を使うたびに結合性を証明せよ」では誰も使いません。trustMe() で埋めて先へ進み、必要になったら本物の証明に差し替える ── 証明の負債を型に見える形で残しながら、開発は止めない、という運用です。

この公理が壊れにくいのには理由があります。使ってよい場所が '0(消去)位置 ── 実行時に値が要らない証明の位置 ── である限り、trustMe の値は erasure で消え、実行時コストも実行時の嘘もゼロです。逆に値が本当に要る位置で使うと、trustMe には計算規則がないので評価が stuck して(GPU なら lowering エラーとして)すぐ露見します。「証明位置では安全に嘘をつけて、値位置では嘘がつけない」という性質が、機構なしで公理の悪用を防いでいます。Type : Type の不健全性を承知で採用した言語なので、「証明の健全性は絶対」ではなく「証明は実用上の不変条件チェック」という割り切りとも整合しています。

効果まわり

モナドなしの効果 ── なぜ token threading なのか

Haskell 系の純粋言語で効果といえばモナドです。Oven はモナドを持たず、効果を「零幅の token を線形に借りて返す」で表します:

[&X] A  ≝  '1 X → (X, A)

なぜモナドでないか。 第一に、Oven には QTT が すでに あります。線形性は「資源を一度だけ正しく使う」ことを型で言える機構で、これは効果の順序づけそのものです。モナドを足すと、順序づけの機構が 2 つ(bind の入れ子と線形性)になり、しかも GPU カーネルへ lowering する際に高階の bind 構造を解体する仕事が増えます。[&X] A の実体はただの Π と Σ なので、効果のための意味論は core にゼロ ── 実行系も lowering も効果を知りません。

第二に、この形は host と GPU を同型に扱えます。print は World token を、store は GPU token を借りて返す ── 同じ形です。実は GPU 側には一度「カーネル内は 1 スレッドが上から順に実行する命令的コードなのだから、順序は素のプログラム順でよい(linearity 不要)」という整理が存在しました。これは撤回されます。「評価器が字面の順序を守ること」に意味が依存するなら、eval・inline・正規化で順序が動き得る ── つまり 関数の純粋性(参照透過性)を売り渡している。純粋性のために [&X] を導入したのに、GPU だけ例外にしては本末転倒だ、という理屈です(→ 経緯)。結果として「効果の順序はすべて token のデータ依存で表す。零幅 token なら実行時コストはゼロ」に統一されました。

第三に、モナドが得意とする「効果の抽象化・合成」の大部分が、この設計ではただの機能の組み合わせで出ます。State も Writer も IO も「[&X] の X が違うだけ」。効果多相は [&E](E は型変数)というただの依存量化。複数効果は [&X, &Y]。monad transformer に相当する階層は最初から存在しません。

実装では core に Tm::Eff(caps, A) という former があり、eval で '1 X → (X, A) に unfold されます。おもしろいのは、シグネチャの宣言型では Eff のまま保たれる(eval されない)ことです。elaboration は「この呼び出しは効果か」を、callee の宣言型の codomain が構文的に Eff かどうかで検出します ── unfold してしまうと素の Π と区別が付かなくなるからです。効果と判定された文は、token を implicit で注入し、返る (X, A) を Split(Σ の分解束縛)で開いて token を差し替える、という形に脱糖されます。ユーザが store(out, i, x); let v = load(in, i) と書くだけで、この配管がすべて暗黙に縫われます。

→ 効果系

辞書と token が同じ規則で解決される

typeclass の辞書(Mul(F32) の instance)と効果 token('1 World)は、見た目も役割も全然違いますが、Oven では 同じ一つの解決規則 で埋まります:「implicit/borrow 引数の解決とは、wanted 型に合う『使用可能な束縛』を文脈から見つけて usage を消費すること」。

これは美観のための統一ではなく、差分がすべて 既存の概念から導出される ことに気づいた結果です。辞書は 'ω なので何度でも引ける、token は '1 なので一度で消費される ── これは multiplicity の差にすぎません。辞書は型がまだメタ変数を含むことがあるので遅延解決、token は型が常に ground(World/GPU)なので即時解決 ── これも「型が ground か」という条件から機械的に決まります。つまり「instance 解決」と「効果 token の供給」を別のサブシステムにする理由が、調べてみたら何もなかった。

この統一の配当は handler の実装時に現れました。ユーザ効果の discharge(handler が効果ブロックに初期状態を供給する)を実装しようとしたら、新しい機構が何も要らなかった のです。implicit w0 : X = init と書けば、既存の instance 解決が [&X] ブロックの token を型で拾って供給します。「効果 handler の土台は、typeclass の instance 解決そのものだった」というのは、設計時には意図していなかった収穫です。

→ 効果系

escape 防止に専用機構がない

線形な token や借用した資源が closure に隠れて生き延びる ── 効果系の設計で必ず塞ぐべき穴です。Rust はこれを lifetime で、多くの効果系は handler のスコープ規則で塞ぎます。Oven には escape を防ぐための規則が存在しません。それでも漏れないことが、closure の 2 規則から演繹できます:

  1. closure は '1 を capture できない(capture は 'ω のみ)
  2. '1 引数の部分適用ができない

token を閉包に入れる経路が (1) で、let k = print(io) のように部分適用で握る経路が (2) で塞がれ、複製は '1 の 2 回使用として、握り潰しは「返り型 (X, …) を満たせない」として、いずれも既存の QTT 検査に引っかかります。よって token は 1 本の線形スレッドに閉じ、必ず caller に返ります。

重要なのは、この 2 規則が escape のために 導入されたのではない ことです。これらは「関数型を A → B 一種類にする」ために(FnMut を捨てる過程で)確定した規則で、escape 防止はその副産物でした。逆にいえば、「closure に借用を capture させたい」という要求を一度でも受け入れると、region や effect row のような重い機構が芋づるで必要になる ── 実際に設計はその 2 つを作りかけて捨てています(→ 経緯)。「借用は capture させず引数で渡す」という一つの原則を守り抜くと、escape 問題ごと消滅する、というのがこの言語で最も気持ちのよい定理のひとつです。

→ 効果系

部分借用は Rust の borrow ではなく lens

set(&arr.field, …) のようにレコードの一部だけ借りたい、という要求は自然です。Rust はこれを部分借用(disjoint borrows)で解きますが、その裏には「&mut r.a と &mut r.b は重ならない」を追跡するエイリアス解析と lifetime があります。

Oven の答えは Haskell の lens です。&r.a は「r を消費して、焦点 a と『埋め戻し関数』を返す」に脱糖されます:

Lens(S, A) = (s : '1 S) → ('1 A, ('1 A) → S)

get で分解し、焦点を関数に通し、putback で再構成して元の名前に再束縛する ── 全過程が純粋な関数適用です。エイリアスという概念自体が現れないので、解析も lifetime も要りません。「Oven の & はそもそも参照ではなく consume-and-return の糖衣である」という一貫した見立てが、部分借用まで素直に延長された形です。lens は合成できるので &r.a.b も 2 つの lens の合成で済みます。制約はひとつ:lens が構造的に導出できる path(フィールド・配列要素)に限られ、&(任意の式) は書けません。

GPU まわり

dispatch はなぜ関数ではないのか

GPU カーネルの起動 dispatch(i in size){ body } は、Oven で数少ない「本物の構文」です。関数でも eliminator でもありません。ここには長い回り道があります(→ 経緯)。

カーネルは任意個のバッファ('1 資源)に触りたい。最初の案は「触る資源を全部レコードに束ねて引数で渡す」(explicit-R)で、これは 正しく動きます。しかし手で束ねるのは冗長で、「ふつうに closure として out や in を capture して書きたい」という書き味の要求がありました。ところが capture を許すと、'1 資源が closure の環境に取り込まれて 封印 されます ── 使い終わっても返ってこない。これを救うために region システム(バッファを region 所有にして時間 token を threading する)まで検討されましたが、複雑さが過剰で撤回。

最終的な洞察は「capture は書く。でも closure 値を作らなければ封印は起きない」でした。dispatch を構文にすれば、body はその場にインラインで書かれるだけで、関数値として存在しません。値にならないものは脱出も封印もしない。body が参照する自由な '1 変数は、構文が borrow-lift ── 消費して継続に返す ── します。外から見れば「借りて、走らせて、返した」だけです。

もうひとつ、構文であることには消極的でない理由があります。borrow-lift する資源の集合は body の中身(どの自由変数を使うか)で決まります。つまり dispatch の「型」が body に依存する ── これはもはや関数型で書けません。関数にできないから構文にした、という必然です。

実装では core に Tm::Dispatch(size, body, borrows, elem_tys, cont) という 5 つ組のノードがあります。borrows は elaboration が body を kernel モードで型検査したときに集めた自由 '1 変数のリスト。継続 cont は「借用が返ってきた後」の世界なので、redirect_cont が de Bruijn index の付け替え(借用された変数への参照を fresh な binder へ張り替え、他の外側参照をシフトする)を行います。線形性の帳簿はこの refresh を通して繋がるので、release(out); dispatch { store(out, …) } のような use-after-free は普通の '1 検査として弾かれます。

→ GPU 実行

ベクトル型が「無い」── タプルがそのまま vecN

GPU 言語には必ず vec3<f32> があります。Oven に「ベクトル型」という新しい型はありません。F32³ は ただのタプル (F32, F32, F32) の表記 で、GPU lowering がこれをネイティブ vec3 にします。

なぜ型を足さなかったか。 新しい型を core に足すと、影響は型検査だけでは済みません。conversion の規則、NbE の値表現、runtime の値、pretty-printer、パーサ ── 言語のすべての層に「vec という新概念」が波及します。一方、よく見ると vecN は「同型スカラの 2〜4 成分の組」であり、Σ 型として既に表現できる構造 です。だったら「同型スカラのタプルは GPU lowering で vecN になる」という 解釈 を lowering に置くだけでよい ── 言語の意味論には何も足さない。構築はタプル構文、成分アクセスは既存の射影 .0/.1/.2(WGSL の .x/.y/.z に対応)、色 (r,g,b) を作れば自然に vec3 です。CPU emulation は成分を分解して計算するだけで、値表現の変更もありません。

この設計のもうひとつの柱は 「WGSL の都合を言語に漏らさない」 です。GPU の std430 レイアウトでは vec3 のストライドが 16 バイトになる等、メモリ上の姿には GPU 固有の事情があります。これをコア型や runtime に持ち込むと、「タプル = vec」という綺麗な同一視が壊れます。そこでアラインメントの処理は gpu.rs の buffer I/O(実 GPU との境界)だけに閉じ込めました。言語から見える意味論は常に「ただのタプル」です。

ベクトル演算(+・dot・length・normalize)は src/builtins.rs::vec_builtins() のレジストリに宣言的に並んでいて、それぞれ CPU の成分計算と WGSL のネイティブ呼び出し(dot()/length()/normalize())の両方を持ちます。演算の追加はレジストリのループに 1 行です。

→ GPU 実行

U8⁴ ── RGBA8 を u32 1 個にパックする

画像の 1 画素は RGBA 各 8 bit、合計 32 bit というのが標準です。Oven では U8⁴ = (U8, U8, U8, U8) がこれに当たり、GPU 上では 1 個の u32 に bit パック されます。

背景には 2 つの決定があります。まず U8 を一級のスカラ型として立てたこと。「色は F32 を 255 倍すればいい」でも動きますが、PNG やテクスチャの native な形式は整数バイトであり、正規化色(UNorm8)と整数バイト(U8)は 意味の違う別の型 だ、という判断がありました(UNorm8 は将来の別型)。GPU には u8 スカラが無いので、実行上は u32 で担いで算術に & 255u のマスクを入れます。

次にパッキング。ベクトルの一般則に従えば U8⁴ は vec4<u32> = 16 バイトになりますが、RGBA8 の意義は 4 バイトに詰まっていることです。そこで lowering に GTy::PackedU8(n) という表現を持たせ、構築は bit シフト、射影は bit 抽出、読み戻しは unpack にしました。ここでも「GPU の都合の局所化」が守られています:パックは GPU lowering と readback のデコードだけで行い、CPU emulation は U8 のタプルのまま 計算します。言語の意味論はどちらの経路でも同一で、メモリ上の姿だけが違う、という分離です。

実装の細部にひとつ教訓が残っています。値が「自分は U8 だ」と知っている必要があったこと(Scalar::U8 という担体の区別)。u32 で担いだまま型情報を落とすと、lowering が (U8,U8,U8,U8) を見ても vec4<u32>(16 バイト)と区別できず、誤判定します。消去と単相化の言語でも、リテラルの「幅」は値に自己記述させる必要がありました。

→ GPU 実行

buffer に buffer を格納できない ── soundness の穴を塞いだ話

「buffer の要素にできる型(storable)」からは Buffer 自身が除外されています。これは好みの制限ではなく、線形性の健全性がこの一点に掛かっていた ことが分かったためです。

発見の経緯が示唆的です。dispatch の設計(「境界は線形な借用・内部は race 非検査」)が本当に健全か、敵対的にレビューしたときに、具体的な攻撃が見つかりました:カーネル内(当時の整理では線形性の検査が無い)で '1 の buffer ハンドルを 別の buffer に store し、borrow-lift で host へ返すと、host は同じ資源を指す名前を 2 つ持つことになる ── 線形資源の複製です。複製できれば二重解放も use-after-free も型を通ります。

塞ぎ方は「storable をスカラと Σ に限定し、Buffer を弾く」。これが救いのある解だったのは、実 GPU の制約と一致していた からです。実際の GPU でも storage buffer に buffer ハンドルは格納できません(ポインタが無い世界です)。つまりこの制限は表現力を何も失っておらず、「GPU が物理的に許さないことを型でも許さない」だけでした。回帰テストは tests/soundness.rs に残っています。

「境界の線形規律さえ守れば内部は自由」という dispatch の設計思想は、この修正で「境界を 迂回する経路が無いこと も検査対象」に補強されました。同種の穴が他にないかは、未解決として今も監視対象です。

→ GPU 実行

表現不能は「その場でローカルにエラー」

GPU に載らないもの(Nat、関数値、動的サイズのデータ)がカーネルに紛れたとき、Oven は lowering の失敗ではなく 型検査の時点で、違反した binder の場所に エラーを出します。

これは当初、'GPU modality(型に付く「GPU で走る」という印)の売りとして導入された性質です。「とりあえずコンパイルしてみて、最後に GPU に載らなかったらエラー」という方式は、エラーが lowering の内部表現の言葉で、しかも問題の根源から遠い場所に出ます。型の印で層を分ければ、「まさに違反した構文の場所」でローカルに報告できる ── 2LTT の「GPU 断片の隔離」という発想の、実用上いちばん嬉しい配当がこの診断品質でした。

その後 'GPU modality 自体は全廃されます(印の意味が「表現可能性の強制」だけに痩せ、純コードに印を書かせるのは使える場所を減らすだけになったため)。しかし診断のローカル性は残りました。現在の実装は、型検査文脈の in_kernel: bool フラグ(dispatch body の検査中だけ立つ)が、実行時 binder(λ 引数・let・case パターン・split)の型に representable 検査を課す形です。modality という重い機構が bool 1 個に縮約されてなお、ユーザから見える価値(その場でエラー)は変わらない ── 機構と価値が別物であることの好例です。

再帰型の弾かれ方も綺麗です。Nat を名指しで禁止するルールはなく、case のパターンフィールドに representable を課すと、succ のフィールド型 Nat が再帰的に検査されて自動的に弾かれます。一方、全 constructor が引数なしの有限 enum(Bool や data Dir { east, west })は同じ検査を通り、u32 タグとして GPU に載ります(sig::is_finite_enum)。当初は「enum も手動で U32 エンコードせよ」でしたが、タグ化は機械的なのでコンパイラが引き受けました。

→ GPU 実行

CPU emulation が GPU のオラクル

Oven のプログラムは 2 つの経路で実行できます。既定の CPU emulation(依存ゼロ・tree-walking)と、feature gpu の実 GPU 実行(wgpu)です。両者は独立の実装で、テストは両経路の結果一致を検証します。

なぜ 2 経路を維持するのか。 GPU 実行は本質的に検証しづらいからです。結果はドライバ・GPU 世代・浮動小数の実装に依存し、失敗はシェーダコンパイルエラーや黙った誤答として現れます。「言語の意味論として正しい答え」を GPU 自身に語らせることはできません。そこで、言語の全機能が動く、依存ゼロで決定的な実行系を先に作り、それを正とする 方針が採られました(M0 の目標が「GPU より先に CPU で画像を計算する」だったのはこのためです)。GPU バックエンドを書く仕事は「オラクルと同じ答えを出すこと」という明確なゴールを持つ機械的な作業になります。

実装上、2 経路は消費する中間表現からして違います。CPU 経路は erasure 後の 無型 の実行時 IR Rt(高階 OK・構造的再帰 OK)を tree-walking し、GPU 経路は 型付き の core Tm から一階の KernelIR へ lower します(GPU は全式に型が要るため)。性質が真逆の 2 つの消費者を同じ core から派生させていて、共有しているのは数値プリミティブの意味(NUM_BUILTINS の同じ表を両者が引く)だけです。CPU 側の数値計算は意図的に WGSL のセマンティクスに合わせてあり(fract = x−floor(x)、log = 自然対数)、それでも避けられない超越関数の ULP 差だけをテストの許容誤差が吸収します。

表面言語まわり

演算子が全部「ただの instance」

a * b は _*_(a, b) に脱糖され、_*_ は「Mul(A) の辞書 d を implicit で取り、d(x, y) を呼ぶだけの普通の関数」です。パーサが知っているのは fixity 宣言(infixl 7 _*_)だけで、* の意味はスコープ内の instance が決めます。

動機は徹底した一貫性です。演算子に組み込みの意味を持たせると、「組み込みの *」と「ユーザの演算子」の 2 種類のルールができ、さらに「Mult の * は型検査の一部、F32 の * はライブラリ」のような層の混在が生じます。Oven はここを 1 つに潰しました:乗法 * は Mult でも F32 でも「ただの instance」。multiplicity の半環演算すら特別な構文を持ちません(→ 第一級 multiplicity)。

この一般化を成立させるために解いた実際的な問題が 2 つ記録に残っています。ひとつは リテラルとのデッドロック。2.0 * 3.0 の型検査では、被演算子はリテラルで型が未確定、instance も未解決 ── クラスの結果型を連想型(d.Out)にすると、型パラメータ A を確定させる手がかりがどこにも無く、推論が膠着します。そこで標準の演算子クラスは結果型を A(homogeneous)にしました。期待型(F32 が欲しい文脈)が A を直に解き、リテラルも辞書も連鎖的に解けます。もうひとつは 総称関数内の演算子。square [A, d : Mul(A)] (x : A) = x * x の本体で * を使うには、仮引数 d が instance プールに入っている必要があります。ここは「nominal 型を持つ束縛は自動的に instance になる」という規則(pool_if_nominal)で解決され、Agda の instance 引数に相当するものが「クラス = nominal 型」から自然に出ました。

lexer にも一点だけ支えがあります。記号の連なり(+ - * < > …)を 1 つの Op トークンにまとめ、_op_/op_ を通常の識別子として組み立てる ── 演算子そのものを定義・参照できるのはこのためです。

→ 表面言語

nominal ── 名目性だけを足した最小の newtype

typeclass のクラス本体は nominal 型です:

nominal Add (A : Type) = (x : A, y : A) -> A
nominal Mul (A : Type) = (x : A, y : A) -> A

Add(F32) と Mul(F32) の中身はどちらも (F32, F32) → F32 で、構造的には同じ型です。Oven の conversion は構造的なので、素の Σ でクラスを表すと 加算の instance が乗算の解決候補になってしまう ── instance 解決は型一致で辞書を拾うので、同形クラスの共存が即座に曖昧エラーになります。これが nominal を導入した理由の全てです。名前で型を区別する(名目的な)壁を、この一箇所のためだけに立てました。

面白いのは透明性の設計です。普通の newtype(Haskell の newtype、Rust のタプル構造体)は構築と分解にラッパの出し入れが要ります。Oven の nominal は conversion でだけ不透明で、それ以外には完全に透明 です:d : Mul(A) はラップなしの素の関数値で、d(x, y) と直接呼べます。実装では typecheck.rs の peel_nominal が「構築・除去(適用・射影)のときだけ body へ展開し、conversion では決して展開しない」という片側だけの unfold を行います。「instance 解決が曖昧にならない」という一点のためにどれだけ小さい機構で済むか、を突き詰めた結果が「conv だけ見えない壁」でした。

なお、初期実装ではタグ付きレコードで区別する ad-hoc な方法を使っていて、後に nominal 型として原理的に整理し直した経緯があります。「動くけれど原理から出ていない解を、原理のある形に置き直す」という、この開発で繰り返されるパターンのひとつです。

module ── レコードを返すただの関数

module Vec3 (n : U32) {
  zero : U32 = 0[U32];
  scale (s : U32, v : U32) : U32 = mulU32(s, v);
}
Vec3(3[U32]).scale(2[U32], 5[U32])

ML 系言語のパラメータ付きモジュール(functor)に見えますが、専用機構は存在しません。module M (params) { … } は let M = λ(params) let f = …; let g = …; (f = f, g = g) ── 引数を取って名前付きレコードを返す関数 への純粋な糖衣です。

これが可能なのは、言語の 2 つの基礎的な選択の配当です。第一に Type : Type:型がただの値なので、レコードのフィールドに型を入れられ、モジュールが型を輸出することも(必要なら)普通の依存 Σ で書けます。第二に Σ backbone:「名前付きの束」という概念がレコードとして既にあり、モジュールのために新しい名前空間機構を作る理由がありません。内部が nested let なので後の定義が前の定義を参照できる(共有される)ことも、糖衣の展開形から自明に出ます。

「モジュールシステム」は言語設計の中でも際立って重くなりがちな部分(ML の functor・シグネチャ・sealing はそれ自体が研究分野です)ですが、依存型があるとその大部分が「関数とレコード」に還元される ── Oven はその教科書的な事実を、実際に専用機構ゼロで実装した形です。open(無修飾の取り込み)だけは構文の仕事なので、将来の課題として残っています。

tight/loose ── 空白が意味を持つ適用

f(x, y) と f (x, y) は違う意味です。前者(tight:f と ( が密着)は curried 適用 (f x) y、後者(loose:空白あり)はタプル (x, y) を 1 個渡す適用です。

空白に意味を持たせるのはリスクのある選択で、それでも採ったのには経緯があります。Oven の適用は当初、引数テレスコープを Σ として一括で渡す方式(Σ-domain)でした。Σ backbone の思想には合うのですが、implicit 推論と衝突します:型パラメータ A と辞書 d を 1 つの Σ に束ねると、単一化が「テレスコープの Σ」と「辞書そのものの Σ 型」を構造的に区別できず、instance 解決が壊れました。それで適用は全面 curried へ移行(このとき実装が 146 行減っています)。しかし「関数がタプルを受け取る」形は依然として正当な型なので、curried 適用とタプル適用の 両方を書き分ける記法 が必要になり、tight/loose の区別に落ち着きました。

つまりこれは美観の選択ではなく、「curried(推論に必要)とタプル(Σ backbone に必要)の両立」という制約の解です。f(a, b) = f a b = 並置、と教われば規則自体は単純ですが、f (x, y) の空白 1 個が意味を変えることには慣れが要ります。設計もそれは自覚していて、パーサ詳細の未確定項目として記録されています。

→ 表面言語

リテラルは型の指標 ── 既定型を持たない

0 は文脈によって Nat の zero、F32 の 0.0、Mult の '0 になります。期待型がリテラルを解決し、期待型が無い場所(注釈なしの let x = 5)では エラー です(5[Nat] のように注釈します)。

多くの言語はここで既定型を持ちます(Haskell の defaulting、Rust の i32 フォールバック)。Oven がそれを拒否したのは、「その場で勝手に既定の型を決める」のが ad-hoc だから、という明確な方針によります。defaulting は「なぜ i32 なのか」に原理的な答えがなく、しかも推論の他の部分と相互作用して驚きを生みます(Haskell の defaulting 規則の複雑さは有名です)。書き手に 1 つ注釈を要求するほうが、暗黙の規則を 1 つ覚えさせるより安い、という判断です。

実装として面白いのは、Tm::Lit が 「elaboration で消える契約」の項 であることです。パーサは 0 を Lit のまま core に入れ、型検査が期待型を見て M0 や succ^n zero や機械スカラ Scalar へ置き換えます。解決後の木に Lit は残らず、万一 eval や erasure に届いたら panic で契約違反が顕在化します。名前付き射影 ProjN(r.field ── 型を見ないと位置に解決できない)も同じ「型検査で消える surface 項」で、「parse の時点では決められないものは、専用ノードで型検査まで運ぶ」という一貫したパターンになっています。

→ 表面言語

assert の引数が '1 である理由

postulate assert : (b : '1 Bool) -> [&World] Unit

Bool を「1 回だけ使う」と宣言する意味はあるのか、と一見不思議な型です。これは QTT の適用規則から来る、実際的な設計です。

適用 f(a) の使用量は「引数式 a の使用量 × binder の multiplicity」で計算されます。もし assert の引数が 'ω だと、引数式の中で使われた資源の使用量が ω 倍 されます。テストの典型形 assert(eqArray(readback(a), readback(b))) では、引数式が線形 buffer a, b を消費(readback)しています。ω 倍されると「線形資源を ω 回使った」ことになり、完全に正当なこのコードが線形性違反で弾かれてしまう。引数を '1 にすれば使用量は 1 倍のまま通ります。

この型が入る前、自己検証テストは複数の条件を and で束ねた 1 つの式にしていて、まさにこのスケーリング問題に踏んでいました(and : (Bool, Bool) → Bool の引数が 'ω で、線形 readback が弾かれる)。assert を効果つき・'1 引数の文として導入したことで解消しています。「引数の multiplicity は『callee が何回使うか』だけでなく『引数式に何を書けるか』を決める」という、QTT の言語に固有の API 設計の一面です。

→ 効果系

実装まわり

Bool も Nat も処理系にハードコードされていない

Bool/Nat/Fin/Vec/Id は、処理系の Rust コードに焼き込まれた特別な型ではなく、std/prelude.ov に Oven の data 宣言として 書かれています。処理系は起動時にこのファイル(include_str! で埋め込み)をパースしてシグネチャを作ります。Buffer や store のような真のプリミティブも同様に postulate 宣言としてこのファイルにあります。

こうなったのは初めからではありません。M0 の当初方針は逆で、「inductive の一般機構は作らない。組み込み型と eliminator をプリミティブ表に焼き込む」でした。転換の直接の理由は QTT です:型ごとの eliminator は、型ごとに使用量の合流規則(どの引数が '0/'ρ/'π か)を手で持つことを意味し、これが誤りの温床になりました(実際に旧規則には線形 fold を弾く穴があった)。data 宣言から constructor・case・iota・QTT 合流を 一般規則で導出 するほうが、規則が 1 つで済み、しかも検証も 1 回で済みます。

一般機構ができれば、組み込み型を特別扱いする理由は消えます。prelude を Oven ソースにしたのはその帰結で、副産物として言語の dogfooding(data/postulate/nominal 宣言・借用記法・効果 former が、処理系の起動のたびに実データでパースされる)にもなっています。数値プリミティブはさらに一段自動化されていて、postulate addF32 : … のような宣言は prelude にすら書かれず、src/builtins.rs::NUM_BUILTINS の表(名前・型・CPU 計算・WGSL 形)から自動生成されます。数値関数の追加は表 1 行です。

→ 処理系の内部

quote_shared ── 30GB のメモリ爆発から生まれた quote

NbE の quote(値を項に書き戻す操作)は、素朴には値の木構造を辿ります。しかし eval が作る値は Rc で共有された DAG です。共有を無視して辿ると、DAG は木に展開されます ── 指数爆発の古典的な形です。

これが実際に火を噴いたのが showcase(マンデルブロ)でした。escape(c) = (iterate(16, …)).cnt のように反復をラッパ関数越しに呼ぶと、GPU lowering のインライン展開が quote(eval(…)) を通り、共有されていた反復の中間状態が反復ごとに複製されます。計測では 1 反復あたり項サイズ 13 倍、16 反復でメモリ 30GB に達して完走しませんでした。普通のプログラムがコンパイルできないのは言語として致命的です。

解決が nbe::quote_shared です。通常の quote と違い、eval の Rc-DAG を辿りながら 同一ノード(ポインタ等価)を検出して let 束縛の列に平坦化 し、2 回目以降の出現を変数参照にします(GVN:同じ計算に同じ名前を与える)。出力は「let の連鎖 + 本体」という形の項で、共有が構文上の共有(let)として保存されます。健全性の注意点として、分岐の下で評価された値をどこまで持ち上げてよいかがあり、branch 評価のキャッシュで扱っています。この修正で showcase は CPU/GPU 両経路とも完走し、回帰テスト(反復カーネルの項サイズが爆発しないこと)が置かれました。

「正規化は正しいがサイズが爆発する」は依存型処理系の定番の罠で、Oven の場合は GPU lowering(全展開が避けられない)がそれを増幅しました。「意味論の正しさ(quote∘eval = id)と計算量の正しさ(共有の保存)は別の要件」という教訓の実物です。

fromU32 ── 機械整数から「回数」への全域な橋

postulate fromU32 : (n : U32) -> Nat

型理論の Nat は succ(succ(…zero)) という unary 表現で、「n 回繰り返す」という 概念 の担い手です。しかし実行時に unary の数を持つのは O(n) の無駄で、GPU では論外です。一方、実行時の数は機械整数 U32 で持ちたいが、U32 は不透明なスカラで帰納構造(= case で回す能力)を持ちません。この 2 つを繋ぐのが fromU32 です。

注目すべきは 全域である ことです。逆方向(Nat → U32)は 2³² を超える Nat で破綻するため有界性の証明が要りますが、こちらの方向は「どの u32 も Nat である」── 論理的には fromU32(n) = succ^n(zero) と定義でき、部分性がありません。証明義務ゼロで機械整数を「回数」として使えます。

実装では fromU32(n) の結果は unary に展開されず、担体の u32 をそのまま持ちます。そして iterate(fromU32(n), f, init) のような fold(case)を、runtime と GPU lowering が for ループ として実行します。つまり「論理的な意味は unary Nat の構造的再帰、実行時の姿は機械整数のカウンタループ」という二重写しです。これは将来構想(表現可能性の Repr witness ──「帰納型に GPU-native な担体への埋め込みを与えると、その fold が for に翻訳される」)の最初の具体例でもあり、「functional なプログラムを imperative なループに翻訳する」という言語全体の野心の縮図になっています。
