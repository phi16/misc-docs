# 真実と未完成の意味論：Unison・Hazel

SC0 の哲学のうち 2 つ——「真実は一つ、表現はビュー」（§3）と「不在・失敗・未完成を
正規の状態にする」（§6）——には、それぞれを研究の主題として正面から掘った言語が
存在します。Unison と Hazel です。どちらもグラフィックとは無関係の文脈で、
SC0 と同じ結論の別の面に到達しています（2026 年時点の観察）。

## Unison — 「真実は AST」を配布とリネームに使う

Unison は「**コードは content-addressed であるべき**」という一点から設計された
関数型言語です。

- すべての定義（関数・型）は、その**構造＋依存のハッシュ**（512 bit）で同定されます。
  ハッシュは構造だけから決まり、**名前には依存しません**。
- **名前はハッシュを指すメタデータ**です。リネームは「人間向けのラベルの張り替え」に
  すぎず、瞬時で、何も壊しません。
- コードベースはテキストファイルの集まりではなく、**型検査済みの AST を収めた
  データベース**です。「ビルド」という工程が存在しない。依存関係はハッシュ参照なので、
  同名の型が複数共存でき、diamond dependency 問題が消えます。
- 効果は abilities（algebraic effects）で扱います。

**SC0 との共鳴と対照**：「正準な実体は AST・名前や表示はビュー」という原理は同じです。
ただし使った先が違う——SC0 はこの原理を**テキスト⇄グラフの双方向編集**に使い、
Unison は**配布・依存管理・リネーム**に使いました。同じ原理の直交する応用です。

対照的なのは**書き手の意図の扱い**です。Unison はソーステキストを保存せず、
表示のたびに AST から pretty-print します——フォーマットも徹底的に正規化する側に
振った。SC0 は逆に「意味に効かないが意図に効くもの」（ブロックの書き方・`@`・配置）を
透明な層として保存します。「何を正規化し、何を残すか」という問いに対する
2 つの答えとして、きれいな対照になっています。

## Hazel — 「穴のあいたプログラム」に本物の意味論を与える

Hazel（ミシガン大学 FP Lab・Cyrus Omar ら）は、**typed holes を第一級にした
ライブ関数型プログラミング環境**の研究です。

- 構造エディタの編集計算系（Hazelnut）が、**どの編集状態でも型が付く**ことを
  保証します。「書きかけだから型検査できない」という状態が存在しない。
- 白眉は評価です。**評価はホールを例外として止まらず、素通りして続きます**——
  ホールは「適切な型を持つ不透明な式」として扱われ、その周りの計算は進み、
  結果には未確定部分（indeterminate result）が残る。各ホールに流れ込んだ環境
  （closure）も追跡されるので、「この穴を埋めるとき、そこには何が見えているか」が
  提示できます。
- この理論（Hazelnut Live）は Agda で機械化されています。

**SC0 との共鳴と対照**：SC0 の `?` の哲学——ホールを含むプログラムは正規の状態で、
他の部分のプレビューは続く——はまさにこれです。実装の対応も見えます：SC0 で
引数が具体でないプリミティブが **stuck（neutral）として評価を通り抜ける**のは、
「ホールの周りで評価が進む」の NbE 版ですし、elaborate に失敗した宣言を
`NMember` の stuck メンバとして持つエラー多重化も同族の発想です。

対照は真実の置き場所です。Hazel は構造エディタが真実で、テキスト表現を持たない方向。
SC0 はテキストが真実で、構造編集はその上のビューです。また Hazel の貢献は
理論の厳密さ（機械化された健全性）にあり、SC0 は制作環境としての統合にあります。

## まとめ

「真実は一つ」も「未完成は正規」も、それだけで研究言語が一つ立つ程度に深い主題です。
Unison は前者を配布に、Hazel は後者を編集体験に振り切りました。SC0 はこの 2 つを
（グラフィック制作という文脈で）**同時に**やろうとしている、と位置づけられます。
逆に言えば、困ったときに読むべき先行研究がどちらの主題にもある、ということでもあります
——特に Hazel の「ホールに流れ込んだ closure の提示」は、SC0 の `?` の表示を
豊かにする際の直接の参考になりそうです。
