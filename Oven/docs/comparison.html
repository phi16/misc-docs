Oven ── 言語の記録

他言語との比較 ── 現代の言語の中での立ち位置

Oven は 3 つの伝統の交差点に立っています:依存型・証明支援系の伝統(MLTT・Agda・Idris)、資源を型で数える伝統(線形論理・Rust・Clean)、そして GPU で配列を計算する伝統(Futhark・Dex・シェーダ言語)。それぞれの伝統には成熟した言語がいますが、この 3 つを同時に踏んでいる言語はほとんどありません。この章は、各伝統の代表と Oven を突き合わせて、「何が同じで、どこで袂を分かったか」を記録します。

以下、伝統ごとに掘り下げます。

依存型言語(Agda・Idris 2・Lean)と比べて

共有しているもの は多い:MLTT ベースの依存 Π/Σ、帰納型、definitional equality を NbE で判定する処理系の骨格(elaboration-zoo 系の設計)まで、コアの作りは現代の依存型言語の標準そのものです。Agda 使いが Oven のコードを見れば、telescope・implicit 引数・instance 引数(nominal の自動プールは Agda の instance argument にかなり近い)にすぐ見覚えを感じるはずです。

決定的に違うのは目的です。 Agda・Lean は証明支援系であり、健全性(「証明されたことは本当に正しい」)が存在意義です。Oven は Type : Type を承知で採り、Girard のパラドックスで False が証明できることを受け入れました。この一点で Oven は証明支援系のリーグから 意図的に降りています。依存型は Oven にとって証明の道具ではなく、コンパイルの道具 です ── 配列長を型に載せて単相化でサイズを静的化する、添字の範囲を消去された証明で保証する、GPU に載るかを型で判定する。「証明支援系の道具立てを、証明のためでなくコード生成のために使う」というのが依存型に対する Oven の姿勢です。

全域性の実現方法も対照的です。 Agda は一般再帰を書かせて停止性検査器(構造的減少の解析)が後から検証します。Lean も同様で、well-founded recursion への elaboration が裏で走ります。これらの検査器は強力ですが、それ自体が複雑な機構であり、「なぜ通ったのか/通らないのか」が構文から見えないことがあります。Oven は逆に、再帰を書ける場所を構文で制限しました(⟦w⟧ は再帰パターン変数にしか適用できない)。書けるものは全部全域、検査器は存在しない。表現力は落ちますが(相互再帰や複雑な減少測度は書けない)、GPU に載せる言語では「回数の決まらない計算」はどのみち存在できないため、この制限は GPU 制約と同じ方向を向いています。失うものが最初から失われている、という設計です。

Idris 2 とは QTT の兄弟です。 '0/'1/'ω の 3 値 multiplicity、消去と線形性の統合は Idris 2(とその基盤の Atkey の QTT)から直接来ています。違いは 2 つ。第一に、Idris 2 は一般再帰の言語なので再帰呼び出しをただの関数適用(1 回)と数えますが、Oven は case 展開の再帰なので「再帰 branch は動的回数走る」を使用量規則(2 群 SUM)として自前で持つ必要がありました(→ QTT)。第二に、Oven は multiplicity を第一級の値(Mult : Type)にし、半環演算まで instance に落としました。Idris 2 の量は注釈の世界の住人で、量の多相はありません。なお研究言語まで含めれば、量を型で数える発想は Granule(graded modal types)がより一般的な形(任意の半環でのグレーディング)を追求しており、Oven の 3 値固定はその実用特化版と見ることもできます。

純粋関数型の効果(Haskell・Clean・Koka)と比べて

Haskell との対比が Oven の効果系を一番よく説明します。 Haskell の IO は表面上はモナドですが、GHC の内部では IO a = State# RealWorld -> (# State# RealWorld, a #) ── 世界 token の受け渡し です。ただしこの表現はユーザから隠され、token の一回性はコンパイラだけが知る不変条件です。Oven がやったのは、この内部表現をそのまま表面の意味論にする ことです。[&World] A ≝ '1 World → (World, A) は GHC の内部形とほぼ同じ形をしていて、違いは token の一回性を QTT がユーザレベルの型として強制すること。モナド・do 記法・transformer の階層は全部不要になり、効果の合成は「token が 2 本になる」だけです(→ 効果系)。

この系譜でいちばん近い祖先は Clean です。Clean は一意性型(uniqueness types)で *World を明示的に受け渡しし、モナドなしで IO を実現した言語で、Oven の効果系は「Clean の世界受け渡しを、一意性型でなく QTT の線形性の上に載せ、受け渡しの配管を elaboration で暗黙化したもの」と要約できます。Clean ではユーザが世界を手で持ち回りますが、Oven では token は implicit で、ユーザは print("hello"); print("world") と書くだけです。

代数的効果の系譜(Koka・Effekt)とは、明確に違う道を選びました。 Koka は効果を row 多相で型に載せ、handler で自由に解釈を差し替えます。Oven は effect row を 検討した上で却下 しています(→ 経緯)。理由は、row・存在量化・資源計算の機構が芋づるで膨らみ、「糖衣のために意味論を足さない」に反したこと。代わりに「capability は宣言・推論なし・単一抽象 [&E] までは書ける」という保守的な線を引きました。効果の抽象化の柔軟さでは Koka に遠く及びませんが、効果の意味論が core にゼロ(ただの Π と Σ)である、という対価を得ています。handler に相当するものが「instance 解決で token を供給するだけ」で書けたのは、この設計の配当です。

Rust と比べて ── 線形性・借用・lifetime

Rust は「資源を型で管理する言語」の現在の代表で、Oven の & が Rust の &mut を意識しているのは名前からも明らかです。しかし中身はかなり違います。

Rust の借用は「参照」です。 値はその場に留まり、参照が貸し出され、エイリアスの安全は lifetime と borrow checker(エイリアス解析)が守ります。Oven の & は参照ではありません。 set(&arr, i, v) は「arr を消費して、更新後の arr を返してもらい、同じ名前に再束縛する」の糖衣 ── 値そのものが移動する consume-and-return です。参照が存在しないので、エイリアスという概念自体が型システムに現れず、lifetime が要りません。部分借用も Rust の disjoint borrows(&mut r.a と &mut r.b の非重複をコンパイラが追跡)ではなく、lens(get と putback の純粋な対)です。Oven が純粋・全域だからこそ成立する単純化で、Rust のように任意の命令的コードと共存する必要があれば、この手は使えません。

線形性の厳密さも違います。 Rust の所有権は affine(高々 1 回 ── 黙って drop できる)ですが、Oven の '1 は strict linear(ちょうど 1 回 ── drop にも Consumable の宣言が要る)です。IO token を「握り潰せない」ことが効果の完了保証になるので、この差は飾りではありません。逆に Rust が普通にできて Oven にできないのが 共有読み取り借用(&T を複数箇所へ同時に貸す)です。QTT の threading は「一本の糸を順に持つ」ことしか表せず、コピー不可資源の同時読み取りは fractional permission か region を将来足さない限り書けません(→ 現状)。Rust との比較で最も分が悪いのはここです。

もうひとつの対照は escape 解析 です。Rust は closure が参照を捕捉して逃げることを lifetime で防ぎます。Oven には対応する機構がなく、「closure は '1 を capture できない」「'1 の部分適用はできない」という 2 つの規則から escape 不可能性が定理として出ます(→ カタログ)。機構の少なさをどこまで規則の帰結で賄えるか、という点で両言語は好対照です。

GPU 配列言語(Futhark・Dex)と比べて

目的が一番近いのはこの系譜です。Futhark は純粋関数型のコードを GPU に落とす言語の現在の到達点で、「どんな断片なら GPU に乗るか」の設計は Oven が教科書として参照したものです。しかし並列性の扱いが正反対です。

Futhark は暗黙並列です。 ユーザは map・reduce・scan などの SOAC(second-order array combinator)で書き、コンパイラが flattening・fusion を駆使して並列コードを合成します。races は言語モデル上存在せず、結果は決定的です。Oven は明示並列です。 dispatch(i in size){ … } でスレッドグリッドを直接切り、スレッド ID から添字を計算し、atomic も競合も(compute shader と同様に)ユーザの責任です。これは compute shader のメンタルモデルを保ったまま型を強くしたい、という選択で、「コンパイラが並列化してくれる」安心と「このスレッド配置で走ると分かっている」制御のトレードオフです。creative coding・procedural generation という用途(Shadertoy 的な「ピクセルごとの関数」を書く世界)では、後者のほうが素直だという判断があります。

型の強さでは Oven 側に分があります。Futhark のサイズ型は配列長の整合を追う専用機構ですが、Oven では長さはただの依存型の値です(単相化で静的化)。一方、成熟度・最適化(fusion・タイリング・マルチバックエンド)では比較になりません ── Futhark は 10 年選手の研究プロジェクトで、Oven の lowering は「inline して WGSL を吐く」段階です。

Dex(Google の研究言語)とは「添字を型にする」発想を共有しています。Dex の型付き index set は、Oven の Fin(n) と pull 配列(Fin(n) → A はただの関数)に対応します。Dex は effect system や自動微分まで積んだ野心的な設計でしたが、研究プロジェクトとして休眠しました。依存型 × 配列 × GPU という組み合わせが「誰も安定に届いていない空白地帯」であることの証左でもあります。

シェーダ言語そのもの(GLSL・WGSL・CUDA) と比べると、Oven が足そうとしているものが見えます。これらは高階関数も多相もほぼ持たず、カーネル間のコード共有は文字列インクルードやマクロの世界です。Oven は「普通の関数型言語の抽象(高階関数・typeclass・レコード・依存型)で書き、カーネル境界の特殊化とインライン展開で全部消して、素の WGSL に落とす」ことを狙います(→ host 特殊化)。「抽象は書けるが、実行時には存在しない」── ゼロコスト抽象の GPU 版です。

ステージング言語(MetaOCaml・Terra・Zig comptime)と比べて

「ホストの言語でコード生成し、制限された言語で実行する」という構図だけ見れば、Oven は 2 段階の言語(two-stage language)にも見えます。実際、最初の設計案は 2LTT(Two-Level Type Theory)による明示的なステージ分けでした。MetaOCaml のクォート ⟨e⟩・Terra の Lua/Terra 分離・Zig の comptime は、みなこの「層を構文で見せる」系譜です。

Oven はこれを 却下した 側です(→ 経緯)。理由は一貫して「host 用と kernel 用を構文で書き分けたくない。一つの言語で書きたい」。同じ関数 stepC が host でも GPU でも呼べて、印は付かない。層の分離はユーザの構文からは消え、コンパイラの中(消去・単相化・特殊化・表現可能性検査)に沈められました。ステージングの明示性は「何がいつ計算されるか」を確実にする長所がありますが、Oven はそれを「全域 + 単相化で、コンパイル時に決まるものは必ず決まる」という言語側の性質で代替しています。Zig の comptime が「普通のコードがそのままコンパイル時にも走る」で人気を得たのと、目指す書き味は案外近いところにあります。

creative coding の環境(Processing・Shadertoy)と比べて

最後に、用途側の比較です。creative coding の現在の主流 ── Processing/p5.js、Shadertoy、TouchDesigner、Houdini VEX ── は、ほぼ例外なく 動的か、C 系の弱い型 の世界です。この分野で支配的な価値は「即時のフィードバック」と「書き始めの軽さ」で、強い静的型はむしろ邪魔だと考えられてきました。

Oven はここに真っ向から逆張りしています:依存型と線形性を持つ全域言語で、画像と音とメッシュを作る。賭けているのは、生成的なプログラム(procedural generation・アセット生成)は書き捨てに見えて実は「壊れずに変形し続けたいプログラム」であり、型の強さが効く、という読みです。バッファサイズの不整合や解放忘れが実行時でなく型検査で落ちる Shadertoy、と言えば狙いの雰囲気が伝わるでしょうか。この立ち位置を狙った言語は、知られている範囲でほぼ存在しません(この niche 自体が Oven の最も珍しい点かもしれません)。

ただし現状は正直に:即時フィードバックの点ではまだ cargo run + PNG 出力の段階で、ライブコーディング環境やホットリロードはありません。勝負はこれからです。

まとめ ── どのマスにも先客がいない

各伝統の代表と比べたとき、Oven の立ち位置は消去法的に浮かび上がります:

  • 証明支援系(Agda・Lean)は健全だが、GPU では走らない。Oven は健全性を捨てて実行を取った。
  • シェーダ言語(WGSL・CUDA)は走るが、抽象がない。Oven は抽象を書かせて、コンパイル時に消す。
  • GPU 配列言語(Futhark)は自動並列で安全だが、明示的な制御と依存型がない。Oven は compute shader のモデルを保ったまま型を強くした。
  • Rust は資源管理の王者だが、依存型も純粋性もない。Oven は参照そのものを捨てて、lifetime ごと問題を消した。
  • Haskell/Clean は純粋だが、GPU は他人事。Oven は効果系の設計自体を GPU と host で共有できる形(token threading)にした。

つまり「依存型 + strict linear + 全域 + 明示 GPU + モナドなし効果」という組み合わせのマスには、現在ほぼ誰も座っていません。ただしこれは自慢であると同時に警告でもあります ── そのマスが空いているのは、需要がないからか、難しすぎるからか、まだ誰も試していないからか、Oven 自身が実験で確かめている最中です。設計ノートの流儀に従えば:このマスが本当に住める場所かどうかは、まだ分かっていません。

なぜ統合が「綺麗」でありうるのか ── 制約の合流

このマスに誰もいないことには、コミュニティの分断という社会的な理由もあります。証明支援系の人は GPU を見ず、シェーダの人は型理論を見ず、Houdini のアーティストは自分たちが参照透過な関数型環境(recook = 再評価)を使っているとは思っていない。それぞれの世界の中では、他の世界の道具は「関係のないもの」に見えます。

しかし各世界の芯だけを取り出して並べると、要求は衝突するどころか、多くの場所で同じ一点を指しています。Oven の設計を貫くのはこの合流です:

  • 全域性:Agda の世界では型理論の衛生(論理として無矛盾であるための条件)、GPU の世界では物理的制約(一般再帰が存在しない)。「自由再帰を入れない」という一つの決断が、両方の要求を同時に満たす。
  • '0(消去):型理論側から見れば proof irrelevance(証明は実行に関与しない)、GPU 側から見れば erasure と単相化の根拠(サイズと型はコンパイル時に確定する)。一つの multiplicity が両方の顔を持つ。
  • 線形性:Rust 側から見れば資源管理、Haskell/Clean 側から見れば効果の順序づけ。'1 という一つの量が、バッファの二重解放防止と IO の逐次性を同じ規則で守る。
  • 「値 = 関数」:Shadertoy の「画像は uv の純粋関数」、Houdini の「ジオメトリは手続きの評価結果」、関数型言語の第一級関数。render(n, f) に λ を渡してカーネルへ特殊化する機構は、この 3 つの言い換えを 1 つの実装で受け止めている。
  • per-element 並列:Houdini の wrangle(全ポイントに同じコード)、compute shader のスレッドグリッド、配列言語の map。dispatch(i in size) はこの共通の芯の直接の写しで、だからどの世界の住人にも「知っている形」に見える。

統合が力づくの接合(どれかの世界に他を従わせる)にならずに済んでいるのは、この偶然とは思えない一致のおかげです。逆に言えば、Oven の設計判断で迷ったときの判定基準は「その選択は 4 つの世界のどの芯を写しているか。どれか一つの世界の都合に他を従わせていないか」でした。

その先 ── もっと多くのものが綺麗に表現できるはずだ

この統合実験の仮説は「これで終わり」ではありません。同じ土台の上に、まだ言語として綺麗に表現されたことのないものが載るはずだ、という見立てがあります。いくつか、現在地から自然に延びている方向を記録しておきます:

  • メッシュ・ジオメトリ:Houdini の geometry は「要素数 + attribute の束」であり、依存レコード (n : Nat, pos : Array(n, F32³), …) がまさに欲しがっている形です。トポロジの不変条件(接続の整合性)を '0 の証明として持てれば、VEX には原理的に書けない保証が得られます。Unity アセット生成という当初目標の延長線上です。
  • 時間・シミュレーション:音は既に「時間の関数」として書けます(sound.ov)。アニメーションや時間発展を、線形な状態 threading(iterateEff)と純粋な「時刻の関数」の両方で書けて相互に行き来できるなら、FRP が目指した場所に別の道から届くかもしれません。
  • 微分可能性:全域・純粋・一階に落ちる言語は、自動微分にとってほぼ理想の基質です(Dex が挑んだ場所)。procedural generation と最適化(目標に向けてパラメータを寄せる)が繋がると、生成の書き方自体が変わります。

これらがこの土台に本当に綺麗に載るのかは、例によってまだ分かりません。ただ、「離れて見える世界たちの芯が実は同じ形をしている」という観察が一度成立した以上、同じことが他でも起きると期待するのは不自然ではない ── それがこの実験を続ける理由です。

なお、この章の比較対象の選定と性格づけは執筆時点(2026 年)の状況認識です。各言語は動く標的であり、記述が古びる可能性があります。
