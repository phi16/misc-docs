Oven ── 言語の記録

設計原理 ── 何を選び、何を捨てたか

この章は Oven 全体を貫く設計原則をまとめます。個々の機能はこの原則の帰結として読めます。

根本の緊張:依存型のフル言語は GPU では走らない

Oven の出発点にして、いまも設計全体を支配している問題です。

MLTT + 帰納型 + QTT のフルパワーの言語は、そのままでは GPU にコンパイルできません。 GPU のカーネル(compute shader)に書けるのは、おおまかに「一次の(関数を値として持ち回らない)、データサイズがコンパイル時に決まっている、動的メモリ確保がない、一般再帰がない、値型だけ」のコードです。一方、依存型言語は「型の中に任意の計算が現れ、任意の再帰があり、関数やデータを自由に持ち回る」。真っ向からぶつかります。

採用した方針:一つの言語 + 消去 + 単相化、表せなければエラー

最初に検討された Two-Level Type Theory(メタレベルとオブジェクトレベルを構文で分ける)は「host 用と kernel 用のコードを書き分けたくない。一つの言語で書きたい」という理由で却下されました(→ 経緯)。採用されたのは:

  • 依存型では、配列の長さ n のような「型に出てくる数」は multiplicity '0(消去)にできる。全プログラムを単相化すれば n はコンパイル時に具体値に確定する。配列サイズが静的に決まるという点では、むしろ普通の言語より GPU 向き。
  • ただし消去は必要条件であって十分条件ではない。消した後に「動的な再帰・動的サイズのデータ・実行時まで残る関数値」が残れば GPU に載らない。そこで 「GPU で表現できないものがカーネルに混ざっていたら、コンパイルエラー」(→ 表現可能性)。
  • さらに「回数の決まらないループも、自由な再帰も、そもそも言語に入れない」と決めた。これで上記の (1) 動的再帰は言語レベルで存在しなくなり、言語全体が 全域(total) になりました。型理論として整合的になり、GPU 化の難しさも一段下がる、一石二鳥の決断です。

原則の一覧

1. Σ をあらゆる所に使う(backbone)

「関数の引数の並び(テレスコープ)」と「レコード」を同じ一つの Σ 型で表します。これにより typeclass の辞書・module・closure の環境・GPU dispatch の任意個リソース が、新しい言語機構を足さずに全部 Σ で書けます。Σ = ∃(存在量化)でもあり、依存レコードなので連想型(associated type)も自然に出ます。→ コア型理論

2. 糖衣は必ず QTT の素の構造に展開される

「糖衣構文のために変なものを足すくらいなら、糖衣構文の方を捨てろ」

Oven の syntax sugar は、剥がすと必ず素の Π・Σ・multiplicity になります。新しい意味論を糖衣のために足しません。効果記法 [&X] A → B は ('1 X, A) → ('1 X, B) の糖衣、借用 &T は「'1 で受けて結果と一緒に返す」の糖衣、module は「引数を取ってレコードを返す関数」の糖衣です。この原則が守られている限り、糖衣の展開結果はコア型検査器(oracle)が必ず検証できます。

3. 型は「観測可能な振る舞い」を映す ── 関数型は A → B 一種類

closure の扱いで何度も間違えた末に到達した原則です(→ 経緯):

  • 純粋な λ は、変数を capture していても型はただの A → B。capture を Σ に包む closure conversion はコンパイル時の実装の話で、型には出ない。
  • 効果のある関数も結局 A → B。状態 S を threading する関数は ('1 S, A) → ('1 S, B) ── ただの Π で、ドメイン/コドメインに '1 S が乗っているだけ。別建ての「効果あり関数型」(FnMut 等)は要らない。
  • closure が capture できるのは 'ω の値だけ。'1 資源は常に引数で渡す。これにより関数値はすべて 'ω(何度でも呼べる)になり、効果 token の escape 防止すら新しい規則なしで閉じます(→ 効果系)。

4. 演算子すら特別扱いしない

* は Mult(multiplicity の半環)でも F32 でも「ただの instance」です。1 + 1 が ω になるのも、パーサの特別扱いではなく elaboration での instance 解決の結果です。演算子は mixfix 宣言(infixl 7 _*_)+ nominal 型のクラス + implicit 解決という汎用機構だけで賄われます。→ 表面言語

5. 効果は「線形に借りて返す」一本

モナドはありません。IO・状態・GPU の命令順序は、すべて「線形('1)の token を消費して返す」threading で表されます。State / Writer / IO が [&X] という一つの仕組みに集約されます。→ 効果系

6. race は型で追わない ── compute-shader と同じ割り切り

dispatch 内で多数のスレッドが同じバッファに同時アクセスするのは並列計算の本体です。スレッド間の競合の正しさ(atomic を使う・書き込み先を衝突させない)はプログラマの責任とし、型では追いません。書き込みの disjointness を型で保証しようとした案(WriteSet)は、atomic の存在により「強すぎる」ため撤回されました(→ 経緯)。host 側の純粋性は「dispatch 構文が自由な '1 資源を borrow-lift して返す」ことで保たれます。

7. ad-hoc を嫌う ── 原理から出ない解は「暫定」と明記する

設計ノート(DESIGN.md)の書き出しにある通り、この言語は「これで綺麗にまとまった」と思った直後に穴が見つかることを繰り返してきました。だから:

  • 原理から出た解と、会計上の workaround(例:線形 payload の再帰で尾を '0 にする patch)を区別して記録する。
  • 撤回した案は消さずに残す(同じ穴に落ちないため)。→ 経緯
  • 未解決・不安な点は常に明示する。→ 現状と未解決

8. foundation-first ── core を consistency の oracle にする

糖衣の展開規則(& や暗黙 threading)の正しさは、紙の上で詰め切れないと判断されました(armchair では何度も後から穴が出た、という実証があるため)。方針は:

core(QTT 型検査器)を consistency の oracle にし、desugar の出力は必ず core で型検査し直す。

これにより desugar の最悪ケースは「unsoundness」ではなく「通らない」になります。紙の厳密さは core 仕様(型・使用量・NbE)に集中させ、糖衣層は「書く → core に流す → 落ちるか見る」で経験的に詰めます。

9. 承知の上の割り切り

  • Type : Type:論理的に不健全(Girard のパラドックス)で、正規化の停止保証もない(型検査器が病的入力で発散し得る)。軽い証明・実用上の不変条件チェックには全く困らないため採用。健全性が本当に必要になったら宇宙階層を導入する。
  • QTT で表せないただ一つのもの:「コピーできない資源を複数箇所から同時に読み取り専用で共有する(別名借用)」。threading は本質的に「一本の糸を一人が順に持つ」ため表せない。'ω のデータならコピーすればよいので、実害は限定的と見て後回し。
  • カーネルを値として持ち回れない:dispatch は構文であり closure 値を作らないため、「カーネルのライブラリ」は書けない。creative coding では「カーネルはその場に書く」で回ると判断。

  • elaboration-zoo(András Kovács)── 依存型エラボレータの骨格。Haskell から Rust への移植(GC がないので Rc で値とクロージャのグラフを管理)。
  • Idris 2 ── QTT を実際に実装した処理系。multiplicity・「再帰回数を usage で数えない」設計・erased index の定石。
  • Dex / Futhark ── 純粋関数を GPU にコンパイルする言語。「どんな断片なら GPU に乗るか」の設計の先例。
