Oven ── 言語の記録

Oven とは

Oven は 依存型(MLTT)+ 帰納型 + QTT(数量的型)を核に持つ純粋関数型言語で、書いたコードを GPU で並列実行できる ことを目指す実験的言語です。処理系は Rust で実装されています(コアは外部依存ゼロ)。

一言でいえば:

「依存型を持つ純粋関数型言語で、しかも GPU で並列計算が走って、画像・音・アセットが作れる」

という、互いに引っぱり合う性質の欲張りな組み合わせです。この文書群は、その緊張をどうほどいたか(あるいはまだほどけていないか)の 記録 です。チュートリアルではなく、「この言語がどういう原理で出来ていて、なぜそうなったか」を、設計上の特徴から細かい言語機能までまとめてあります。

何をしたい言語か

  • 並列計算:たくさんのデータに同じ計算を一斉にかける。GPU(compute shader)で走らせる。
  • creative coding:Shadertoy 的・Processing 的に、コードから画像や音を生成する。procedural generation。
  • アセット生成:Unity で使えるメッシュ・テクスチャをコードで吐き出す(将来)。
  • これらを 強い静的型付け・純粋関数(副作用なし)・全域(すべての計算が停止する) の上でやる。

なぜこの組み合わせか ── 4 つの世界の統合実験

この言語の動機には、はっきりした個人的背景があります。作者は Rust を書き、Agda を使い、Shadertoy を使い、Houdini を使う ── 普通は交わらない 4 つの世界を日常的に行き来する人間です。そして、これらの世界は離れて見えて 綺麗に統合できる はずだ、という直観があります。Oven はその直観を確かめる実験です。

  • Agda からは依存型と全域性を ── ただし証明のためでなく、コンパイルの道具として。
  • Rust からは資源の規律を ── ただし参照と lifetime は捨てて、線形性だけを。
  • Shadertoy からは「画像 = 座標の純粋関数」というモデルを ── ただし型を付けて。
  • Houdini からは procedural generation(recook = 再評価という参照透過性、per-point 並列、attribute = レコード)を ── ただし言語として。

各章で見るように、これらの要求は妥協で繋がっているのではなく、多くの場所で 同じ一点を指しています(全域性は型理論の衛生であると同時に GPU の物理的制約であり、'0 消去は proof irrelevance であると同時に単相化の根拠です)。その合流の詳細は他言語との比較の結びで扱います。そして Oven は終点ではなく、「もっといろんなものが綺麗に表現された言語がありうる」という信念の、最初の一歩という位置づけです。

雰囲気:マンデルブロ集合を GPU で描く

examples/showcase.ov の抜粋です。純粋なヘルパ関数(レコード・中置演算子・反復・分岐)をトップレベルで定義し、それを GPU カーネルから呼びます。カーネル境界でヘルパはインライン展開され、iterate(16, …) は静的アンロールされます。

// レコード = 名前付き Σ。型エイリアスはただの定義
Complex  : Type = (re : F32, im : F32);
EscState : Type = (z : Complex, cnt : U32);

// z² + c(中置演算子とレコード射影 ── host でも GPU でも使える普通の関数)
stepC : (c : Complex, z : Complex) -> Complex
  = λ(c, z) (z.re * z.re - z.im * z.im + c.re, 2.0 * z.re * z.im + c.im);

// エスケープ反復:|z| ≤ 2 の間だけ z ← z²+c を進めて数える
escape : Complex -> U32
  = λ(c) (iterate(16, λ(s : EscState)
            case(ltF32(norm2(s.z), 4.0)) {
              true  => (stepC(c, s.z), s.cnt + 1[U32]),
              false => (s.z, s.cnt)
            }, ((0.0, 0.0), 0[U32]))).cnt;

// 8×8 グリッドの各スレッドが 1 画素を計算して out に書く
let '1 out : Buffer(64[U32], Color) = newBuffer(64[U32]);
dispatch(i in (8[U32], 8[U32], 1[U32])) {
  store(out, i.1 * 8[U32] + i.0, toColor(escape(toC(i.0, i.1))))
};
readback(64[U32], out)

out は線形('1)資源で、dispatch が borrow-lift(消費して返す)します。store の効果順序は零幅の GPU token を暗黙に threading することで型に強制されますが、ユーザは token を一切書きません。

設計原理 ── 何を選び、何を捨てたか

この章は Oven 全体を貫く設計原則をまとめます。個々の機能はこの原則の帰結として読めます。

根本の緊張:依存型のフル言語は GPU では走らない

Oven の出発点にして、いまも設計全体を支配している問題です。

MLTT + 帰納型 + QTT のフルパワーの言語は、そのままでは GPU にコンパイルできません。 GPU のカーネル(compute shader)に書けるのは、おおまかに「一次の(関数を値として持ち回らない)、データサイズがコンパイル時に決まっている、動的メモリ確保がない、一般再帰がない、値型だけ」のコードです。一方、依存型言語は「型の中に任意の計算が現れ、任意の再帰があり、関数やデータを自由に持ち回る」。真っ向からぶつかります。

採用した方針:一つの言語 + 消去 + 単相化、表せなければエラー

最初に検討された Two-Level Type Theory(メタレベルとオブジェクトレベルを構文で分ける)は「host 用と kernel 用のコードを書き分けたくない。一つの言語で書きたい」という理由で却下されました(→ 経緯)。採用されたのは:

  • 依存型では、配列の長さ n のような「型に出てくる数」は multiplicity '0(消去)にできる。全プログラムを単相化すれば n はコンパイル時に具体値に確定する。配列サイズが静的に決まるという点では、むしろ普通の言語より GPU 向き。
  • ただし消去は必要条件であって十分条件ではない。消した後に「動的な再帰・動的サイズのデータ・実行時まで残る関数値」が残れば GPU に載らない。そこで 「GPU で表現できないものがカーネルに混ざっていたら、コンパイルエラー」(→ 表現可能性)。
  • さらに「回数の決まらないループも、自由な再帰も、そもそも言語に入れない」と決めた。これで上記の (1) 動的再帰は言語レベルで存在しなくなり、言語全体が 全域(total) になりました。型理論として整合的になり、GPU 化の難しさも一段下がる、一石二鳥の決断です。

原則の一覧

1. Σ をあらゆる所に使う(backbone)

「関数の引数の並び(テレスコープ)」と「レコード」を同じ一つの Σ 型で表します。これにより typeclass の辞書・module・closure の環境・GPU dispatch の任意個リソース が、新しい言語機構を足さずに全部 Σ で書けます。Σ = ∃(存在量化)でもあり、依存レコードなので連想型(associated type)も自然に出ます。→ コア型理論

2. 糖衣は必ず QTT の素の構造に展開される

「糖衣構文のために変なものを足すくらいなら、糖衣構文の方を捨てろ」

Oven の syntax sugar は、剥がすと必ず素の Π・Σ・multiplicity になります。新しい意味論を糖衣のために足しません。効果記法 [&X] A → B は ('1 X, A) → ('1 X, B) の糖衣、借用 &T は「'1 で受けて結果と一緒に返す」の糖衣、module は「引数を取ってレコードを返す関数」の糖衣です。この原則が守られている限り、糖衣の展開結果はコア型検査器(oracle)が必ず検証できます。

3. 型は「観測可能な振る舞い」を映す ── 関数型は A → B 一種類

closure の扱いで何度も間違えた末に到達した原則です(→ 経緯):

  • 純粋な λ は、変数を capture していても型はただの A → B。capture を Σ に包む closure conversion はコンパイル時の実装の話で、型には出ない。
  • 効果のある関数も結局 A → B。状態 S を threading する関数は ('1 S, A) → ('1 S, B) ── ただの Π で、ドメイン/コドメインに '1 S が乗っているだけ。別建ての「効果あり関数型」(FnMut 等)は要らない。
  • closure が capture できるのは 'ω の値だけ。'1 資源は常に引数で渡す。これにより関数値はすべて 'ω(何度でも呼べる)になり、効果 token の escape 防止すら新しい規則なしで閉じます(→ 効果系)。

4. 演算子すら特別扱いしない

* は Mult(multiplicity の半環)でも F32 でも「ただの instance」です。1 + 1 が ω になるのも、パーサの特別扱いではなく elaboration での instance 解決の結果です。演算子は mixfix 宣言(infixl 7 _*_)+ nominal 型のクラス + implicit 解決という汎用機構だけで賄われます。→ 表面言語

5. 効果は「線形に借りて返す」一本

モナドはありません。IO・状態・GPU の命令順序は、すべて「線形('1)の token を消費して返す」threading で表されます。State / Writer / IO が [&X] という一つの仕組みに集約されます。→ 効果系

6. race は型で追わない ── compute-shader と同じ割り切り

dispatch 内で多数のスレッドが同じバッファに同時アクセスするのは並列計算の本体です。スレッド間の競合の正しさ(atomic を使う・書き込み先を衝突させない)はプログラマの責任とし、型では追いません。書き込みの disjointness を型で保証しようとした案(WriteSet)は、atomic の存在により「強すぎる」ため撤回されました(→ 経緯)。host 側の純粋性は「dispatch 構文が自由な '1 資源を borrow-lift して返す」ことで保たれます。

7. ad-hoc を嫌う ── 原理から出ない解は「暫定」と明記する

設計ノート(DESIGN.md)の書き出しにある通り、この言語は「これで綺麗にまとまった」と思った直後に穴が見つかることを繰り返してきました。だから:

  • 原理から出た解と、会計上の workaround(例:線形 payload の再帰で尾を '0 にする patch)を区別して記録する。
  • 撤回した案は消さずに残す(同じ穴に落ちないため)。→ 経緯
  • 未解決・不安な点は常に明示する。→ 現状と未解決

8. foundation-first ── core を consistency の oracle にする

糖衣の展開規則(& や暗黙 threading)の正しさは、紙の上で詰め切れないと判断されました(armchair では何度も後から穴が出た、という実証があるため)。方針は:

core(QTT 型検査器)を consistency の oracle にし、desugar の出力は必ず core で型検査し直す。

これにより desugar の最悪ケースは「unsoundness」ではなく「通らない」になります。紙の厳密さは core 仕様(型・使用量・NbE)に集中させ、糖衣層は「書く → core に流す → 落ちるか見る」で経験的に詰めます。

9. 承知の上の割り切り

  • Type : Type:論理的に不健全(Girard のパラドックス)で、正規化の停止保証もない(型検査器が病的入力で発散し得る)。軽い証明・実用上の不変条件チェックには全く困らないため採用。健全性が本当に必要になったら宇宙階層を導入する。
  • QTT で表せないただ一つのもの:「コピーできない資源を複数箇所から同時に読み取り専用で共有する(別名借用)」。threading は本質的に「一本の糸を一人が順に持つ」ため表せない。'ω のデータならコピーすればよいので、実害は限定的と見て後回し。
  • カーネルを値として持ち回れない:dispatch は構文であり closure 値を作らないため、「カーネルのライブラリ」は書けない。creative coding では「カーネルはその場に書く」で回ると判断。

コア型理論

Oven の意味論的な核です。ざっくり言うと 依存型(MLTT)+ 帰納型 + QTT に GPU の表現可能性検査 を乗せたもの。QTT は次章、表現可能性は GPU 実行で扱い、この章はそれ以外の骨格を説明します。

宇宙:Type : Type

型にも型があります(Nat : Type、Bool : Type)。では Type の型は? Oven は一番単純な Type : Type を採用します。

これは 論理的に不健全 です。Girard のパラドックスにより、原理的には False すら証明できてしまいます(Agda の --type-in-type と同じ状況)。さらに正規化が強正規化でなくなるため、型検査器は病的入力で発散し得ます。それでも採用するのは、軽い証明・実用上の不変条件(「この添字は範囲内」など)には全く困らず、実装も使い勝手も圧倒的に楽だからです。本当に健全性が欲しくなったら宇宙階層(Type0 : Type1 : …)を導入します。発散は割り切って許容し、実用上の保険として timeout/fuel での打ち切りは任意で入れてよい、という立場です。

Type : Type の実利的な副産物として、型が第一級の値 になります。(Env : Type, env : Env, step : (Env, A) → (Env, B)) のように、型をフィールドに持つレコード(透明な存在型)がそのまま書けます。

Π 型(関数)── 適用は全面 curried

関数の型は Π 型で、戻り型が引数に依存できます:(x : A) → B(x)。

適用は全面 curried です(2026-06-11 に Σ-domain 方式から移行・確定)。(x : A, y : B) → C は curried な (x:A) → (y:B) → C であり、f(a, b) は f a b(= (f a) b)です。tight な f(a, b) も並置 f a b も同じ意味になります。

タプルを 1 個受け取りたいときだけ型を (p : (x:A, y:B)) → C と書き、f((a, b)) で渡します(f(a, b) とは別物)。タプルの分解は本体で let (x, y) = p; …(Σ は積であって inductive ではないため、case ではなく分解束縛)。

Σ型 / テレスコープ / レコード

Oven で最も重要な構造です。 「関数の引数の並び(テレスコープ)」と「レコード(名前付きの組)」を、同じ一つの Σ 型(依存和)で表します。

(x : A, y : B)      // 依存した名前付きの並び。後ろの型が前の値に依存できる
(a : Nat, b : Nat)  // 名前付き = レコード型。値は (a = 1, b = 2)、射影は r.a r.b
(Nat, Nat)          // 無名 = タプル。射影は p.0 p.1
()                  // 空 = Unit(型も値も ())
  • Σ = ∃(存在量化) でもあります。MLTT では依存和と存在型は同じ連結子で、別の道具は要りません。
  • 依存レコードなので 連想型 も自然に書けます:(Out : Type, mul : (A,B) → Out) のように、後のフィールドの型を前のフィールドに依存させられます。
  • この「Σ をあらゆる所に使う」方針により、typeclass 辞書・module・closure 環境・dispatch の任意個リソースが、新機構なしで全部 Σ で書けます。

帰納型は data 宣言

帰納型はユーザが data で宣言します(組み込みの Bool/Nat/Fin/Vec/Id も std/prelude.ov に Oven ソースの data 宣言として書かれており、処理系が起動時に取り込みます)。

data Nat : Type {
  zero : Nat,
  succ : (n : Nat) -> Nat,
}

// 線形 payload を入れられる cons-list。r = 要素の量(型に乗るので線形 Vec と純粋 Vec は別の型)
data Vec [r : Mult] (A : Type) : (n : Nat) -> Type {
  vnil  : Vec(zero),
  vcons : (m : Nat, x : 'r A, xs : 'r Vec(m)) -> Vec(succ(m)),
}

// 等式。GADT の典型 ── refl が index y を x に固定する
data Id [A : Type] (x : A) : (y : A) -> Type { refl : Id(x) }
  • parameter(: の左)は全 constructor で共有(uniform)。implicit [...] か explicit (...) かを選べます。
  • index(: の右)は constructor の戻り型で zero/succ(n) のように具体化されます。
  • constructor は GADT スタイルで完全な型を書きます。量注釈 'ρ は constructor の引数にだけ付きます。
  • strict positivity は「inductive 型であることの定義そのもの」 として要求されます。型構成子が共変 functor F であって初めてその initial algebra μF(帰納型)が存在する ── → の左などの負の位置に自己が出る宣言は受け付けません。

型ごとの eliminator(Nat-elim 等)は焼き込みません。分解・再帰は次の case 一本で、その型付け・計算規則(iota)・QTT 合流は宣言から一般的に導かれます。

当初は「帰納型はプリミティブとして固定し、型ごとの eliminator を焼き込む」方針でしたが、QTT の合流規則を型ごとに手で持つ羽目になったため、一般の data + case へ移行しました(→ 経緯)。

反復は case のみ ── 帰納仮説の括弧 ⟦⟧

ユーザの決定として、自由再帰も無限ループも言語に入れません。よって Oven は全域言語です。繰り返し計算は case 構文(構造的再帰)だけが提供します。

case は帰納型の値を constructor で 1 段分解し、各 branch でその部分構造に対する 帰納仮説 ⟦w⟧(その部分構造に対する case の結果)を使えます:

// n + m(⟦k⟧ : 「k に対する case の結果」)
case[λ(k) Nat](n) { zero => m,  succ(k) => succ(⟦k⟧) }

// Bool の分岐(⟦⟧ を使わない case = 非再帰)は同じ構文の特別な場合
case(b) { true => e1,  false => e2 }

// J(等式の eliminator)も case で導出できる。K(UIP)は入れない
J = λ[A](P, d, x, y, p) → case[λ(y, q) P(x, y, q)](p) { refl => d(x) }

⟦w⟧(意味論の denotation bracket。ASCII 代替は [[w]])は その branch の再帰パターン変数 w にしか適用できません。だから書けるのは構造的再帰だけで、停止性検査を別に持ち込まずに 全域性が構文的に自明 になります。生の eliminator の安全性をそのまま、Idris 風の書き味で使える、というのがこの構文の狙いです。

  • motive [P] は省略可能(非依存なら期待型から推論)。
  • iota(計算規則)は一般規則一つ:scrutinee が c(as) に簡約されたら branch c を選び、本体の ⟦w⟧ を「w に対する case の再帰結果」に置換して評価する。型ごとには持ちません。
  • case の QTT 使用量規則(再帰 branch と非再帰 branch の合流)は Oven の独自色が強い部分です。→ QTT の章

生の case は書きづらいので、実際のコードは iterate のようなコンビネータで書きます(iterate 自身が case による普通の定義です):

iterate : [A : '0 Type] (n : Nat, f : A → A, x0 : A) → A
iterate[A](n, f, x0) = case[λ(k) A](n) { zero => x0,  succ(k) => f(⟦k⟧) }

inductive でないもの:postulate

inductive でない組み込みは postulate name : T(型だけを持つ不透明定数)で宣言します。これも std/prelude.ov に Oven ソースとして書かれます。実行時の意味は処理系・ランタイムが供給し、原則 eval では簡約されません。ただし少数の 組み込み簡約つき postulate(数値演算、set/get の in-place 等)だけは実装が計算規則を与えます。

postulate F32 : Type                                  // 不透明な機械スカラ
postulate U32 : Type
postulate Buffer : (n : U32, A : Type) -> Type        // GPU 常駐・線形資源
postulate Array  : (n : U32, A : Type) -> Type        // host 常駐・可変配列
postulate World : Type                                // host IO の効果 token(零幅)
postulate GPU   : Type                                // GPU カーネルの効果 token(零幅)
postulate trustMe : [A : '0 Type] (u : Unit) -> A     // 消去される公理(脱出ハッチ)

trustMe は「面倒な証明義務を埋める」ための公理です。'0(消去)位置で使う限り実行時に残りません。値が要る位置で使うと実行時に stuck するので、本来の用途は証明位置に限られます。

ユーザも自分の抽象定数を postulate で宣言できます。

コアに固有の構成として postulate でなく直接持つのは:Type(宇宙)、Unit(Σ の終端)、第一級 Mult(multiplicity の半環 ── case 評価にすると QTT 検査が循環しうるため組み込み)の 3 つです。

nominal 型(newtype)

nominal R(params) = Body は 名目的型 を宣言します。R(a) は conversion では Body に展開されません(同形の Body を持つ Add(F32) と Mul(F32) が別の型として区別される)。一方、構築・適用・射影には透明で、値は Body の値そのもの(wrapper なし)です。

これは typeclass のクラス宣言に使われます。構造的な Σ レコードでクラスを表すと、同形のクラスが conversion で同一視されて instance 解決が曖昧になる ── その問題を名目性だけで解決する、最小の newtype 機構です。→ 表面言語

型検査の枠組み:双方向 + 使用ベクトル + NbE

  • 双方向(bidirectional):「期待型が分かっていて検査する(checking ⇐)」と「値から型を推論する(synthesis ⇒)」を行き来します。
  • 使用ベクトル:検査と同時に「どの変数を何回使ったか」(Δ)を計算して出力します(QTT のため。→ 次章)。
  • NbE(Normalization by Evaluation):依存型では「Array(2+3, A) と Array(5, A) は同じ型か」のような判定が要ります。項を一旦「意味の世界(値)」に評価してから項に書き戻す(quote)ことで正規形を求めて比較します。実装は elaboration-zoo の Rust 移植が骨格です。

conversion(定義の等しさ)の決定事項:

  • iota:case の branch 選択 + ⟦⟧ 置換、プリミティブの組み込み簡約(数値演算・set/get 等)、Mult の半環演算(1+1 ↝ ω 等)が計算します。scrutinee が neutral なら詰まります。
  • η は Π・Σ(レコード)・Unit でやります。inductive(Bool/Nat 等)ではやりません。
  • multiplicity は型構造の一部 として比較します('1 A→B と 'ω A→B は別の型)。Mult が第一級で半環演算を持つため、NbE が '(1+1) A ≡ 'ω A を計算します。使用量そのものは変換に無関係(計算に効かない)です。
  • GPU カーネルの中身(store/load 等)は計算規則を持たない不透明な定数(neutral)として比較し、命令的な意味は codegen だけに置きます。

メタ変数と implicit 推論

推論で未確定の項は メタ変数 ?m として置き、単一化(unification)が解きます。implicit 引数はメタ変数であり、埋め方は 2 通りです:

  1. 単一化 で構造的に決まる(型パラメータ A など)
  2. 文脈の implicit 値から型で拾う(typeclass の辞書 ── いわゆる instance 解決)

「instance 解決」は専用サブシステムではなく、「implicit 引数 = メタ変数」+「それを曖昧性なく埋める」だけの仕組みです。詳細は表面言語の章で扱います。

QTT ── 使用量を数える型

QTT(Quantitative Type Theory)は、各変数を「何回使うか」(multiplicity)を型で数える型理論です。Oven はこれを 消去(実行時に残さない)と 線形性(資源をちょうど一度使う)の両方に使います。線形性は効果系の土台です。

3 つの multiplicity

記法名前意味典型的な用途
'0消去0 回。型検査には要るが実行時には消える型インデックス・証明・サイズ
'1線形ちょうど 1 回(0 回でも 2 回でもダメ)GPU バッファ・IO token・状態
'ω無制限何回でも普通のデータ(省略時の既定)

構文は型の前に ' を置きます:'0 A、x : '1 A。すべての ' は直後の(原子か括弧の)型に掛かり、→ よりタイトに結合します('1 A → B は ('1 A) → B)。

半環と順序

+ :  0+x=x,  1+1=ω,  ω+_=ω        // 「2」を表す元がないので 1+1 は ω に丸める
· :  0·x=0,  1·x=x,  ω·ω=ω
順序 ⊑ :  反射 + 0⊑ω + 1⊑ω のみ(0 と 1 は比較不能)

0 と 1 が比較不能であることが要点です。これにより '1 は「ちょうど一度」という厳密な線形になります(「高々一度」ではない)。

Mult は第一級の値です(Mult : Type)。半環演算 +/·/⊔ を NbE が計算するため、'(1+1) A ≡ 'ω A が定義の等しさとして成立します。さらに 1 + 1 という 項 の評価も、専用構文ではなく Add(Mult) instance の解決として行われます(パーサは Mult を一切特別扱いしません)。

検査規則

型検査は使用ベクトル Δ(どの変数を何回使ったか)を同時に計算します:

  • 変数:x を使うと (x↦1, ほか↦0)。
  • 適用 f(a₁,…):Δ_f + Σ πᵢ·Δᵢ。各引数の使用量を binder の multiplicity で 掛けて 足します。πᵢ=0 なら 0·Δᵢ=0 ── その引数は実行時に使われない(=消去)。
  • ラムダ:本体で x を ρ 回使うとき ρ ⊑ π を要求。π=1 なら ρ=1 強制。
  • graded let:let 'm x : T = v; t。本体での使用 ρ ⊑ m を検査し、v の使用量は ρ 倍して足します(McBride/Idris 2 の graded let)。これで '1 資源(Buffer)を let でも線形に追えます ── let '1 out = newBuffer(n) の複製はエラーになります。mult は名前の前(let '1 out = …)、型注釈は省略すると値から推論、無印は 'ω です。
  • 型の検査は demand 0:型として検査される位置は使用量を 0 に強制します。型は実行時資源を食いません。
  • 分岐の合流:各枝の使用ベクトルを点ごとの上限 ⊔ で合流。⊔(1,0)=ω なので、線形変数を片枝でしか使わないと ω に化けて後段の '1 検査で弾かれます ── 線形は「全枝でちょうど一度」。

case の使用量規則

ここは Oven 独自色の強い部分です。case[P](v){ c₁(xs)=>b₁, … } の使用量は、branch を ⟦⟧ を使う(再帰)群と使わない(非再帰)群に分け、群内は ⊔-merge、群間は SUM で測ります:

Δ(case) = π_scrut·Δ_scrut + ⊔(⟦⟧ 無しの branch) + ω·⊔(⟦⟧ ありの branch)

なぜこの形か:

  • 群内 ⊔:実行時に通る branch は一つ(排他)。分岐は既存の合流と同じ。
  • 再帰群に ω を掛ける:⟦⟧ を使う branch は展開で動的な回数だけ走ります。外側の '1 を capture すれば ω·1=ω で弾かれる ── 再帰をまたぐ線形状態は ⟦⟧(帰納仮説)を通すしかない、が型から強制されます。
  • 群間が SUM である理由:fold では基底(zero 枝)も step(succ 枝)も 両方 走ります。両者を同じ ⊔ プールに入れると、「基底で 1 回使った線形」と「step で 0 回」が ⊔(1,0)=ω に化け、正当な線形 fold を誤って弾いてしまう ── 実際、以前の eliminator 版の規則(⨆_c u_c·Δcapture)にはこの穴がありました。基底=必ず走る(SUM)・同種枝=排他(⊔)・再帰=動的回数(ω)を分けて初めて健全かつ完全になります。

この規則により、線形資源を基底に入れて ⟦⟧ で threading する効果ループ が型付きます:

// 資源 S を threading しながら n 回反復。succ 枝は ⟦k⟧(前段の結果)を線形に通すだけで
// 外側の '1 を使わない → Δ = {s0:1} で通る
iterateEff : [A : '0 Type, S : '0 Type]
  (n : Nat, body : ('1 S, A) → ('1 S, A), s0 : '1 S, x0 : A) → ('1 S, A)
iterateEff[A,S](n, body, s0, x0) =
  case[λ(k) ('1 S, A)](n) { zero => (s0, x0),  succ(k) => body(⟦k⟧) }

先行との比較:Idris 2 は eliminator を持たず一般再帰 + totality 検査で反復を書き、再帰回数を usage で数えません(本体を 1 回検査・再帰呼び出しは 1 apply)。Oven は反復を case の構造的再帰に限定した代償として ω と群分けを規則として持ちますが、この SUM 規則で表現力は Idris の線形 fold と等価になります。

既知の穴(M0.5 対応予定):一般 inductive で非再帰 constructor が動的回数走る型(例:二分木の葉)では「⟦⟧ 無し = 高々 1 回」の前提が崩れます。組み込みの Bool/Nat/Fin/Vec は基底 constructor が高々 1 回なので健全ですが、ユーザ定義の分岐木には群の決め方の一般化が必要です。

scrutinee の量は payload に流れる

case で潰すと scrutinee の量が constructor payload の binder に流れます(let (a,b)=p でペアの量が成分に流れるのと同じ)。Nat/Bool は payload が純粋なので見えませんが、Vec[1, A](線形 payload)を潰すときに効きます:

  • ⟦⟧ を使わない branch(1 段 peel)では、尾 xs は 1 回しか現れないので 'ρ のままで健全(uncons 相当)。
  • ⟦⟧ を使う branch で線形データを再帰するとき は、iota で再帰位置が「branch 引数 xs」と「再帰結果 ⟦xs⟧」の 2 回現れます。そこで xs 自体は '0(消去)にして、使用を ⟦xs⟧ の 1 回に絞ります。xs は型に名前が要るだけで、実行時の値は ⟦xs⟧ が持つ ──「依存は型だけ・消費は帰納仮説経由」という線形依存型の定石です(Idris 2 で index/predecessor が quantity 0 なのと同じ)。

この「尾を '0 にする」扱いは、原理から出た解ではなく iota の double-use を避ける会計上の workaround である、と設計ノートは自覚的に記録しています(→ 現状と未解決)。線形 payload の自動 '0 化はまだ未実装です(ρ=ω の純粋データは double-use が起きないので現状でも問題なし)。

multiplicity 多相

Mult : Type なので multiplicity 多相はただの依存量化です:

id : [A : '0 Type] (p : Mult, x : 'p A) → A

'p(変数 multiplicity)入りの検査は「使用量 ⊑ p」という制約を生みますが、半環が有限(3 値)なので原理的には全部決定可能 です:f[p₁…pₖ] が valuation v で型付くかは f[v] を具体的に検査するだけなので、3ᵏ を全列挙すれば「通る valuation の集合」が完全に求まります。難しいのは決定可能性ではなく、集合を抽象のまま伝播・表現することと病的に大きい k で、そこは「未実装」として弾く方針です。

現状の実装は「閉じた multiplicity の完全検査 + postulate された多相プリミティブ」です。postulate は body が無いので使用量検査自体が無く、呼ぶ側は具体値に instantiate するためタダで済みます。ユーザ定義の mult 多相関数(列挙チェック)は将来です。

closure は 'ω だけ capture する

関数型を A → B 一種類に保つ要の規則です(→ 設計原理):

  • closure と部分適用が capture できるのは 'ω の値だけ。'1 資源は capture せず、常に引数で渡す。
  • これにより関数値はすべて 'ω(何度でも呼べる)になり、関数型は一様に A → B。
  • 帰結として、'1 引数の部分適用(g = f(buffer) でバッファを握った関数を作る)はできません。「状態を抱えた関数値」が本当に欲しければ、組み込みではなく手書きの Σ (Env : Type, env : Env, step : (Env, A) → (Env, B)) を値として書きます(Type : Type なので Env は第一級フィールド)。

この 2 規則('1 capture 不可・'1 部分適用不可)だけから、効果 token の escape 防止が新機構なしで閉じます。→ 効果系

効果系 ── 借りて返す

Oven は純粋言語ですが、IO・可変状態・GPU への書き込みを書けます。核となる考え方は一つだけです:

副作用も借用も「線形に借りて返す」(&)で表す。

モナドはありません。print や store のような効果は、その世界の token(World・GPU などの不透明な型)を 借りて(消費して)・返す 関数として型が付きます。token は線形('1)なので「一度使ったら次の token に進む」── 効果の順序がデータ依存として型で強制されます。そして token は暗黙に供給されるため、ユーザは書きません。

& の核:consume-and-return

& は型の頭に付く borrow 注釈です。意味は「線形に消費し、結果で返す」:

// あなたが書く型:
set : [A : Type] [n : '0 U32] (&Array(n, A), i : U32, x : A) -> Unit

// 脱糖後(借りた Array を結果タプルで返す):
set : … ('1 Array(n, A), i : U32, x : A) -> (Array(n, A), Unit)

呼び出し側 set(&arr, i, v) は arr を消費し、更新後の配列を 同じ名前に再束縛 します(パーサが let (arr, _) = set(arr, i, v) へ脱糖)。呼び出し以降の arr は更新後を指します。

Rust の &mut に相当しますが、lifetime は要りません。「消費して返す」threading 符号化なので、借用の有効範囲はデータの流れそのもので決まります。安全性を担保するのは linearity です ── token や資源を明示的に名前で書いても構いませんが、二度使えば QTT の線形検査が弾きます。「名前で書けないから安全」ではなく「'1 だから安全」が正しい筋、と設計は明言しています。

2×2:& は括弧と直交する

borrow は「implicit([])か explicit(())か」と独立の装飾です:

非 borrowborrow(&)
explicit ()普通の引数 (x : A)a : &X = 明示借用(可変資源)
implicit []辞書/型 [d : C][&X] = 効果(暗黙借用 token)
  • 明示借用 a : &X:資源を名前で渡す(set(&arr, …))。host の可変 Array がこれ。
  • 暗黙借用 [&X]:資源を型で暗黙解決する(ambient から拾う)。効果 token がこれ。

脱糖の核('1 引数 + 結果へ資源を返す)は両者で同一で、違うのは解決方法(名前で引くか型で引くか)だけです。既存の implicit/explicit の二択を、そのまま borrow に流用した形になっています。

効果 former [&X]

効果は capability 型 X : Type で表します。World(host IO)・GPU(カーネル)・将来の Log・State S など。token は零幅でも(World/GPU)、データ持ちでも(State S)構いません ── 単なる線形値です。

[&X] A        ≝  '1 X → (X, A)
[&X, &Y] A    ≝  '1 X → '1 Y → (X, Y, A)    // 相異型なので独立に threading

prelude の効果プリミティブ:

postulate assert : (b : '1 Bool) -> [&World] Unit
postulate print  : [A : Type] (x : '1 A) -> [&World] Unit
postulate store  : [A : Type] [n : '0 U32] (buf : Buffer(n, A), i : U32, x : A) -> [&GPU] Unit
postulate load   : [A : Type] [n : '0 U32] (buf : Buffer(n, A), i : U32) -> [&GPU] A

World と GPU が 別の型 であることが安全性を担います:host で store を呼ぼうとしても、host の ambient には GPU token が無いので型不一致で弾かれます。かつてこの安全性を担っていた 'GPU modality(型に付く world 印)は全廃されました(→ 経緯)。

assert/print の引数が '1 なのは細かいが実際的な設計です:assert(eqArray(readback(a), readback(b))) のように線形 buffer 由来の値を渡すとき、引数が 'ω だと引数式の使用量が ω 倍にスケールされて線形性違反になってしまうためです。

ambient と threading 規則

elaboration の文脈は「いま使用可能な '1 効果束縛」(ambient)を持ちます。同型の ambient は常に一意です(同型二重取りは禁止 ── 解決の曖昧性を断つため)。

  • entry:[&X] _ ブロックに入ると fresh な w₀ : '1 X を据える(main は World、dispatch body は GPU)。
  • consume + rebind:効果呼び出し c : [&X] A は token を即時供給 → 返る (X, A) を分解し、新しい token を ambient に、値を文の値とする。
  • exit:ブロック値 r と最終 ambient wₙ を組にして返す。
  • case:各枝を同じ入り ambient で elaborate し、同型の出 token を合流(「同じ world を各排他枝へ」)。

つまりユーザが

main : [&World] Unit
main = { print("hello"); print("world") }

と書くと、elaboration が λ(w0) let (w1, _) = print("hello", w0); print("world", w1) 相当の core 項(実際は implicit 供給形)へ縫い上げます。効果の順序は「字面の順」= token のデータ依存の順です。core に出る形は素の Π と Σ の分解束縛の連鎖なので、実行系は効果を知りません。

≤1 効果/文 の規則があります:load を関数引数に直接ネストせず、let v = load(…) で束縛してから使います(1 つの式に効果ある部分式は 1 つまで。順序は ;/let だけが作る)。

多 capability

[&X, &Y] ブロックでは、各効果呼び出しの capability 列を ambient から 型(structural equality)で対応づけ、該当する token だけを消費・再束縛します。それぞれの効果が独立の線形チェーンを成すため、[&World, &Log] Unit のようにビルトイン効果とユーザ効果を同じブロックで合成できます。零幅(World)か実値(Log)かは threading に無関係です ── token は単なる線形値なので。

resolution の統一 ── ω 辞書と linear token は同じ規則

typeclass の辞書(implicit)と効果 token(implicit borrow)を別機構にしません。一つの規則:

implicit/borrow 引数の解決 = wanted 型の「使用可能な束縛/プール項」を文脈から見つけ、usage を消費する。

  • ω 辞書(Mul(A) 等):使用が尽きない=再利用可。型が ground でないことがあるため 遅延 解決(メタ変数 + pending)。
  • linear token('1 X):一度で消費。型は ground(World/GPU)なので 即時 解決。

ω/linear の差は multiplicity から、遅延/即時の差は「型が ground か」から落ちる ── どちらも別扱いではありません。実際に「implicit w0 : X = init を置けば既存の instance 解決が [&X] の token を型で自動供給する」ことが実装で確認されています(discharge が新機構ゼロで書ける、ということ)。

escape は 2 規則から閉じる

threading された token(io 等)がスコープ外へ漏れないことは、closure 設計の 2 規則(QTT の章)だけから出ます:

  1. closure は '1 を capture できない → token を閉包に持ち出せない。
  2. '1 引数の部分適用ができない → let k = print(io0) で token を握れない。

加えて '1 は複製不可(2 回使用は違反)、token は drop 不可(返り型 (X, …) を満たせず握り潰せない)。よって token は 1 本の線形スレッドに閉じ、必ず caller に戻ります。一方 capability 関数([&X] A→B)自体は 'ω 値で token を抱えない(呼ぶたび引数で受ける)ので、自由に持ち回れます。escape 防止のための新しい機構はゼロです。

効果つきの分岐と反復

分岐も反復も case 一本です(専用の if はありません)。branch は '1 を capture できないので、threaded 資源は branch の 引数 で受けます = motive を [&R] 付きの関数型にするだけ:

case[λ(_) [&World] () → ()](b) {
  true  => λ[&World]() print("yes"),
  false => λ[&World]() (),          // token を使わない枝も、[&R] 糖衣が末尾で token を自動で返す
}

「使わない枝で token を素通しする(padding)」は独立の機構ではなく、[&R] の「宣言した capability を末尾で必ず返す」性質に吸収されます。線形性も既存規則のまま:両枝が token を 1 回ずつ使うので ⊔(1,1)=1 で生存します。

反復は motive に threaded 型を載せ、⟦⟧(帰納仮説)に資源を通します(iterateEff。→ QTT)。succ 枝は 'ω なので '1 を capture できず、資源は ⟦⟧ を通すしかない ── これも型から自動で強制されます。

部分借用 &r.field = lens

&r.a とフィールドへ絞って借りられます(設計確定・実装は今後)。これは Rust の(エイリアスと lifetime を気にする)部分借用ではなく、線形 lens(getter と putback の対)です:

Lens(S, A) = (s : '1 S) → ('1 A, ('1 A) → S)   // 焦点 A と「埋め戻し」関数を返す

レコードのフィールドや配列要素には lens が構造的に導出でき、合成もできます(&r.a.b は lens の合成)。呼び出し側の脱糖は「get → 関数で thread → putback で再構成 → 元の名前へ再束縛」。純粋・全域なので線形性と矛盾しません。lens にできる path(フィールド/要素)に限られ、&(任意の式) は書けません。

discharge(handler)

効果はどこかの境界で discharge されます:

  • World(host IO):プログラムのトップレベルが host ブロック(chain に host 効果がある)だと、コンパイラが自動で runHost(λ[w] …) に包みます。runtime の iota が初期 token を供給して走らせ、assert の失敗は panic 報告、最終 token は捨てられます。built-in。
  • GPU:dispatch が body の GPU 効果を discharge します(スレッドごとに fresh token を供給してカーネル実行)。built-in。
  • ユーザ効果(Log / State 等):「explicit な値を ambient token として供給する」は既存機構(implicit w0 : X = init + instance 解決)で既に書けます。効果操作はただの [&X] 関数、可変資源版は &T 借用関数 ── 「ユーザ handler」の大半は既存機能の組み合わせで済むことが分かっています。残っているのはトップレベルで合成ブロック([&World, &Log])を discharge する runner の配線です(runHost は [&World] Unit 専用)。

buffer は効果の外

GPU の Buffer は [&Buffer] にも &Buffer にもしません。カーネル内の buffer は 'ω(並列読み書き自由・race は型で追わない) で、命令の順序づけは GPU token が一手に担います。host→kernel の移動は dispatch の borrow-lift(明示借用の built-in 特例)が処理します。&Array の明示借用が活きるのは host 側の 逐次 可変配列(set/get)です。

// examples/setget.ov の要素:host の可変配列を借用で更新する
let '1 a : Array(4[U32], U32) = newArray(4[U32], 0[U32]);
set(&a, 2[U32], 7[U32]);        // a を消費し、更新後の a を同名に再束縛
let v = get(&a, 2[U32]);        // 読み出しも借用

GPU 実行 ── dispatch と lowering

言語の二枚看板の片方です(もう片方は効果系)。GPU 上で明示的に並列計算を走らせます。

データ所在:Array と Buffer

データが host(CPU)側か device(GPU)側かを型で区別します:

Array  : (n : U32, A : Type) -> Type    // host 常駐・materialized。in-place 可変(&Array 借用の set/get)
Buffer : (n : U32, A : Type) -> Type    // device 常駐。線形資源('1)── 勝手にコピー/破棄できない

newBuffer : [A : Type] (n : U32) -> Buffer(n, A)                    // 出力バッファ確保('1 資源)
readback  : [A : Type] (n : U32, buf : '1 Buffer(n, A)) -> Array(n, A)  // device → host(buffer を消費)

長さ・添字はともに 機械整数 U32 です(unary な Nat の O(n) コストを排除し、GPU の現実に合わせる)。添字は生の U32 で境界証明を持ちません ── 将来、値 i : U32 に消去証明 '0 Lt(i, n) を添える形で境界安全を復活させる構想があります(→ 現状)。

遅延した pull 配列が欲しければ素の関数 Fin(n) → A を書きます。かつて存在した lazy generator(FinArray/build/index)は「build f = f・index xs i = xs i で済む偽装」だったため撤去されました。

dispatch ── 関数ではなく構文

GPU の並列カーネルは専用構文です:

dispatch(i in size) { body };  cont
//   size : U32³(グリッド = スレッド数)、i : U32³(スレッド ID。body 内で束縛)
//   body : GPU の命令的コード([&GPU] 効果)。全スレッドについて並列に走る

let と並ぶ束縛文で、core では Tm::Dispatch(size, body, borrows, cont) という専用ノードです。なぜ関数ではないのか:

  • カーネルは「任意個のリソース(入出力バッファ)」に触りたい。関数にすると closure が '1 資源を capture することになり、「closure は '1 を capture できない」原則と衝突する(capture した線形資源が封印されて戻ってこない)。
  • 明示的にリソースをレコードで渡す形(explicit-R)は動くが冗長。region 機構は過剰。──と回り道した末に、「capture は書く。でも封印しない。そのために構文にする」に落ち着きました(→ 経緯)。
  • 借りる資源の集合が body の中身で決まる = 型が body に依存するので、そもそも関数型を持てない という事情もあります。

borrow-lift

dispatch の型検査は、body が参照する 自由な host 線形('1)変数 を走査して集め、host 側で「1 回消費 → 継続へ fresh に返す」borrow(consume-and-return)を行います。これが borrow-lift です。

let '1 out : Buffer(n, F32) = newBuffer(n);
dispatch(i in (n, 1[U32], 1[U32])) {
  store(out, i.0, f(u32ToF32(i.0)))     // out は自由な '1 変数 → 構文が borrow-lift
};
readback(n, out)                         // out は dispatch 後も生きている
  • host の QTT はカーネル内部の使用回数を数えません。借りた資源を境界で各 1 回消費するだけです。
  • release(out); dispatch { store(out,…) } のような use-after-free は、外側の '1 束縛検査(消費済みの変数を借りに行けない)が弾きます。
  • '0/'ω の自由変数(サイズ・関数)は単相化・コピーで GPU コードに焼き込まれます。
  • 構文なので closure 値が存在せず、カーネルは脱出も封印もしません。代償として「カーネルを値として持ち回る」ことはできません。

カーネル内の効果順序

カーネル内の store/load は [&GPU] 効果です。零幅の GPU token を '1 で threading して順序をデータ依存として型に載せます(→ 効果系)。ユーザは token を書かず store(buf, i, x) とだけ書き、elaboration が縫います。

buffer 自体は 'ω(並列読み書き自由)で、race は型で追いません。スレッド間競合の正しさ(atomic・書き込み先の重複回避)は compute-shader と同じくプログラマの責任です。

かつては「カーネル内は QTT オフの命令的コードで、順序は素のプログラム順」という整理でしたが、これは「評価器が字面順を守ることに意味が依存する = 参照透過でない」ため撤回され、host IO と同型の token threading に統一されました(2026-06-12。→ 経緯)。

表現可能性

GPU で走る断片に現れる型は「GPU でデータとして表現可能」でなければなりません。この検査は dispatch の境界(入出力 + borrow-lift される資源)と、kernel 本体の実行時 binder(λ 引数・let・case パターン・split)で課されます。実装上は型検査文脈の in_kernel: bool フラグ(dispatch body の検査中だけ立つ)が駆動します。

  • representable:スカラ(F32/U32/U8)、Buffer(n, A)(要素は storable)、Σ(struct。Unit は空 struct)、同型スカラのタプル(= ベクトル。下記)、有限 enum。
  • storable(buffer の要素にできる plain データ):スカラ・Σ・Unit のみ。Buffer は不可 ── 実 GPU 同様、buffer に buffer ハンドルを格納させません。これは美観ではなく soundness の要件です:カーネル内で '1 資源を別 buffer に store して host へ別名つきで返せば、線形資源が複製できてしまう ── この抜け道は敵対的レビューで実際に発見され、storable 制限で塞がれました(tests/soundness.rs)。
  • 不可:Nat・Vec・関数型・Type など。case のパターンフィールドにも representable を課すので、Nat/Vec のような再帰型は succ/vcons のフィールド型で自動的に弾かれます(動的回数の再帰の排除)。
  • 有限 enum(全 constructor が引数なし:Bool、data Dir { east, west } 等)は u32 タグとして representable かつ storable です。case は WGSL の switch(Bool は if/else)に lower されます。引数つき sum(tag + payload)は未対応。
  • '0 の消去値(サイズ・型)は自由に境界を越えられます。

将来は binder ごとの検査を Repr(A) witness(「A は GPU-native な担体の retract」という証拠を instance として表明する)に置き換え、representability を「境界 + witness」へ寄せる構想があります。prelude には既に nominal Repr (A : Type) = (Carrier : Type, into : A -> Carrier, out : '0 …, coh : '0 …) が置かれ、witnessed な inductive の fold が GPU の for ループに lower される縦串も実験済みです。

ベクトル型 ── 同型スカラのタプルがそのまま vecN

F32²/F32³/F32⁴ は 別の型ではありません。同型スカラの 2〜4 成分タプル (F32, F32, …) が、GPU lowering でそのままネイティブ vecN<f32> になります(U32 も同様)。

  • 構築はタプル (a, b, c)、成分アクセスは射影 .0/.1/.2(WGSL の .x/.y/.z に対応)。
  • 型位置の無名タプル (F32, F32, F32) は Σ 型に解釈されるので、(x:F32, y:F32, z:F32) と書かなくてもよい。色 (r,g,b) も自然に vec3 になります。
  • 演算はネイティブ WGSL に lower されます:+ - *(成分演算・instance 経由)、dotF32xN/lengthF32xN/normalizeF32xN など。これらは src/builtins.rs::vec_builtins() のレジストリに宣言的にまとまっています。
  • CPU emulation は成分を分解して計算します(値の表現は普通のタプルのまま)。
  • std430 のアラインメント(vec3 のストライドが 16 バイト等)は「WGSL の都合」なので gpu.rs の buffer I/O だけに閉じ込め、コア型・runtime・言語には漏らしません。

narrow 型:U8 と U8⁴(RGBA8)

U8 は整数バイト [0,255] の一級スカラです(算術・比較・変換つき。GPU に u8 は無いので u32 表現 + & 255u マスク)。U8⁴ = (U8,U8,U8,U8) は RGBA8 として 1 個の u32 に bit パック されます(vec4<u32> の 16 バイトではなく 4 バイト)。PNG・テクスチャに native な形です。パックは GPU lowering と読み戻しのデコードだけで行い、CPU emulation は U8 タプルのまま扱います ── std430 と同じ「GPU の都合の局所化」です。正規化色 UNorm8 は別の型として将来入れます。

数値 primitive レジストリ

純スカラの数値 builtin(算術 addF32…divU32・変換 u32ToF32 等・比較 ltF32 等・math sinF32/sqrtF32/clampF32 等)は、単一の表 src/builtins.rs::NUM_BUILTINS に「名前・引数型・戻り型・CPU 計算・WGSL 形」を宣言的に持ちます。prelude の postulate 型はこの表から自動生成され、NbE の畳み込み・CPU emulation・GPU lowering も同じ表を引きます。新しい数値 primitive の追加は表に 1 行 で済みます(かつては 5 箇所の同期が必要でした)。

CPU 計算は WGSL のセマンティクスに合わせます(fract = x−floor(x)、log = 自然対数)。超越関数は実 GPU と libm とで ULP 差がありうるため、GPU テストは許容誤差で比較します。

lowering パイプライン

表面構文 ── parse ──▶ surface AST ── elaborate ──▶ 型付き core Tm
                                                      │
                    ┌─────────────────────────────────┤
                    ▼(CPU 経路)                       ▼(GPU 経路・dispatch body)
              erasure('0 を消す)                lower(型主導)
                    ▼                                  ▼
              Rt(実行時 IR)                      KernelIR(一階・全式に型)
                    ▼                                  ▼
              tree-walking 実行                    WGSL テキスト
             (CPU emulation)                          ▼
                                                  wgpu(feature `gpu`)で実行

要点:

  • GPU lowering は無型の Rt からではなく、型付き elaborated Tm から行います。GPU は全式に型が要るためです(CPU emulation の Rt は無型・高階・構造的再帰ありで、GPU と性質が真逆)。
  • shader になるのは dispatch の body だけで、host 部(newBuffer/dispatch/readback のオーケストレーション)は CPU 側ドライバに残ります。実 GPU 実行時、データは GPU 常駐 ── buffer は storage buffer として確保し、readback のときだけ CPU へ写します。
  • CPU emulation がリファレンス・オラクル です。同じプログラムを CPU 経路(依存ゼロ・既定)と GPU 経路(feature gpu)の両方で走らせ、同じ結果になることをテストが確認します。
  • カーネル境界の inliner がヘルパ関数呼び出しを展開し、静的回数の iterate は(共有つきの)静的アンロールに落ちます。第一級関数は GPU に無いため、特殊化で消えます。

host 特殊化 ── 「値 = 関数。GPU はそれを実行するだけ」

カーネルを関数でパラメタ化する汎用パターンが動きます(examples/sound.ov):

// n サンプルを GPU で並列レンダリング。f はコンパイル時に確定した closure で、
// lowering 時にカーネルへ展開される(第一級関数は GPU に無い ── 特殊化で消える)
render : (n : U32, f : F32 -> F32) -> Array(n, F32)
  = λ(n, f) let '1 out : Buffer(n, F32) = newBuffer(n);
            dispatch(i in (n, 1[U32], 1[U32])) {
              store(out, i.0, f(u32ToF32(i.0) / 8.0))
            };
            readback(n, out);

render(8[U32], λ(t) sinF32(t))

render の関数引数 f は、inliner の host β 簡約(閉じた引数の適用をコンパイル時に展開)によってカーネルへ特殊化されます。「音も画像もアセットも、値 = 関数として書き、GPU はそれを実行するだけ」という言語の狙いの土台です。

共有を保つ quote(指数爆発の回避)

escape(c) = (iterate(...)).cnt のようにラッパ越しに反復を呼ぶと、GPU lowering の quote(eval(…)) が NbE の共有 DAG を木に展開して指数爆発する(反復あたり13倍・30GB 到達)問題がありました。nbe::quote_shared ── eval の Rc-DAG を let 配列に平坦化し、GVN で共有を保ったまま quote する ── で解決済みです。showcase の 16 回反復マンデルブロが CPU/GPU 両経路で完走します。

case→for(witnessed fold)

fromU32 : (n : U32) -> Nat は機械整数を「回数」に橋渡しします(論理的には succ^n(zero) だが、実行時は担体 u32 のまま)。これにより iterate(fromU32(n), f, init) の case(fold)が for ループ に lower されます ── 「functional を for に翻訳する」対象の最初の実例です。どの u32 も Nat なので全域です。

表面言語 ── 構文と糖衣

この章は Oven の書き方(文法)と、それが何に展開されるか(desugar)をまとめます。方針は一貫しています:

すべての糖衣は、剥がすと必ず素の Π・Σ・multiplicity になる。糖衣のために新しい意味論を足さない。

字句

// 行コメント
/* ブロックコメント */

-- はコメントに使いません(+--+ のような演算子の並びと衝突するため)。Unicode 記法を歓迎します(λ・→・'ω・⟦⟧・Σ など)。ASCII 代替も常にあります(\・->・[[w]])。VSCode 拡張は \name + Space での Unicode 入力を提供します(\lam→λ、\to→→、\ih→⟦⟧ など)。

既知の字句の罠:]] は ⟦⟧ の ASCII 代替 [[w]] の閉じと、入れ子の [ の閉じが衝突します。当面はスペースで回避します。

テレスコープ:implicit [...] と explicit (...)

関数の型は「先頭に implicit テレスコープ [...] を 1 つ(省略可)、続いて explicit テレスコープ (...)、`→ 結果」:

map : [A : '0 Type, B : '0 Type] (n : Nat, f : A → B, xs : Array(n, A)) → Array(n, B)

テレスコープ項目の文法:

'p A          // 無名・multiplicity p
x : 'p A      // 名前付き
x y : '1 A    // 複数の名前を同時宣言
A → B         // 単一の無名 explicit 引数は括弧を省ける
  • ' の有無が曖昧性を解消します:(p x : A) は「p と x の 2 宣言」、('p x : A) は「x を量 p で」。
  • implicit 節は先頭に 1 つだけ。implicit は implicit にしか依存できません。だから証明義務は implicit に隠さず explicit に書きます:safeIndex : [A : '0 Type] (n : Nat, xs : …, i : Nat, p : '0 Lt(i, n)) → A。
  • implicit 群もカリー化されています([A, B] ≡ [A][B])。各 implicit は独立したメタ変数として 1 つずつ解決されます。

適用

f(x, y)          // tight。全面 curried なので = 並置 f x y = (f x) y

リテラル ── 型の指標を持つ

リテラルは期待型から解決されます:

期待型が無い文脈(注釈なしの let x = 5)では注釈必須です ──「その場で勝手に既定の型を決める ad-hoc な動作は認めない」という方針によります。elaboration は Tm::Lit を期待型から具体形(Mult の 0/1、Nat の succ^n zero、機械スカラ)へ解決し、以降の評価は解決済みの core 項を使います。

  g(y : Nat) : Nat = y * y;    // 局所関数定義(= g = λ(y) y*y)

演算子と instance

typeclass は「Σ レコードを implicit 引数で渡す」だけで、専用機構はありません。演算子は mixfix 宣言(Agda 流に _ を引数位置に置く)+ fixity 宣言で、演算子は一切特別扱いされません:a op b → _op_(a, b) へ脱糖され、_op_ は instance(辞書)で解決されます。

infixl 6 _+_                // 中置・左結合・優先順位 6
infixl 7 _*_
prefix 9 ~_                 // 前置。`~ x` → `~_(x)`

// クラスは nominal(名目的型)。中身は二項演算の型そのもので、値は演算関数そのまま(wrapper なし)
nominal Mul (A : Type) = (x : A, y : A) → A
_*_[A : '0 Type, d : Mul(A)](x : A, y : A) : A = d(x, y)

// instance は implicit 宣言したものだけが暗黙解決の対象(グローバル探索ではない)
implicit mulF32d : Mul(F32) = mulF32

// パラメトリック instance(前提辞書 da/db を使う)── Haskell の instance Eq a => Eq [a] 相当
implicit eqPair [A B : Type, da : Eq(A), db : Eq(B)] : Eq((a : A, b : B))
  = λ(p, q) da(p.0, q.0) && db(p.1, q.1);

instance 解決の仕組み

本質は「implicit 引数 = メタ変数。それが曖昧性なく埋まりさえすればよい」です:

  • メタの埋め方は 2 つ:(i) 単一化で構造的に決まる(型パラメータ)、(ii) 文脈の implicit 印つき束縛から 型一致で一意に 拾う(辞書)。複数一致は曖昧エラー(coherence)。
  • on-demand 解決:メタの型が ground になった時点で解決を試みます。連想型の戻り値(d.Out)が辞書 d の解決後に射影簡約で解ける ── 遅延一括では原理的に無理な形です。
  • パラメトリック instance:プール値が Π 型なら fresh メタを当てて結果型を単一化し、前提辞書を再帰的に解決します(自己参照の無限ループは深さガードで防止)。
  • 制約引数は自動 instance:nominal 型を持つ束縛([d : Mul(A)] の仮引数等)は自動的に解決プールに入ります。よって総称関数の中で演算子をそのまま書けます:
square [A : Type, d : Mul(A)] (x : A) : A = x * x;   // d(x, x) の明示適用は不要
  • implicit foo; は既存の(非 implicit)束縛を以後の instance プールへ追加します(再エクスポート)。ブロック局所でも効きます。
  • どう埋めたかは解決トレースで内省できます。

クラスが nominal である理由

構造的な Σ レコードでクラスを表すと、同形のクラス(Add(F32) と Mul(F32) ── 中身はどちらも (F32,F32)→F32)が structural conversion で同一視され、instance 解決が曖昧になります。nominal は conversion でだけ不透明で、構築・適用・射影には透明(値は素の演算関数)── 解決の一意性のためだけの最小の名目性です。

結果型を A(homogeneous)にする理由

_*_ の結果を連想型 d.Out にすると、リテラル被演算子(2.0 * 3.0)で型パラメータ A が ground にならず、instance 解決がデッドロックします(被演算子の型が未確定で、結果型も A を固定しない)。結果を A にすれば期待型が A を直接解き、リテラルも辞書も解けます。heterogeneous な連想型版は被演算子の型が確定している場面でのみ使う、という整理です。

ambient prelude

演算子 _+_/_-_/_*_/_/_/_⊔_・クラス Add/Sub/Mul/Div/Lub・Mult の instance は 全プログラムのスコープに常在 します(処理系がユーザソースの前に prepend)。1 + 1 が ω に評価されるのも、この ambient instance の解決結果です。

型理論まわり

⟦w⟧ ── 帰納仮説を書くための括弧

Oven の再帰は、case の branch 内で ⟦w⟧(ASCII では [[w]])と書きます。「部分構造 w に対するこの case 自身の結果」── 数学の帰納法でいう帰納仮説です。

case[λ(k) Nat](n) { zero => m,  succ(k) => succ(⟦k⟧) }   // n + m

なぜこの形か。 全域言語で再帰を書く方法は、大きく 2 つ知られています。ひとつは生の eliminator(Nat-elim のような畳み込み関数)で、安全性は自明ですが、実際に書くと motive やメソッドの受け渡しが煩雑で、人間が日常的に書く形ではありません。もうひとつは Idris や Agda のように一般再帰を許して 停止性検査器 を後付けする方法で、書き味は自然ですが、検査器そのものが複雑な機構になり、「なぜこのプログラムは全域なのか」の根拠が構文から見えなくなります。

⟦⟧ はその中間を狙った選択です。⟦w⟧ は その branch の再帰パターン変数にしか適用できない ── この構文制約ひとつで、書けるのは構造的再帰だけになり、全域性が構文的に自明 になります。停止性検査器は存在しません。意味論としては生の eliminator と等価(安全性はそのまま)でありながら、見た目は「branch の中で再帰結果を参照する」という直観的な形です。denotation bracket(意味論の ⟦⟧)を借りた記法で、「これは項ではなく『意味』を参照している」というニュアンスも込められています。

実装に踏み込むと、core の項は Tm::Ih(idx, w) で、idx は「どの recursor に属する帰納仮説か」を指す recursor スタックへの index です。この index は当初存在せず、「⟦⟧ は最内の case のもの」と暗黙に決めていたのですが、それでは壊れるケースが見つかりました:再帰関数の 値 を quote(正規形へ書き戻し)すると、別の再帰が入れ子に展開されることがあります。たとえば mult(乗算)が本体で plus(加算)を呼ぶと、quote の途中で plus の recursor が mult の recursor の内側に現れ、「最内」の指す先がずれて quote∘eval が恒等でなくなる(実際に無限展開しました)。⟦⟧ を正しい recursor に固定する index を持たせることで解決しています。「束縛の参照は名前でも『最内』でもなく、de Bruijn 的に数えろ」という教訓が、変数だけでなく帰納仮説にも当てはまった、という話です。

→ 定義はコア型理論

case の使用量規則 ── なぜ ⊔ 一本ではだめだったか

QTT の言語で分岐の使用量を合流させる標準的な方法は「各枝の使用量の上限 ⊔ を取る」です。実行時に通る枝は一つなので、これで健全です。Oven も最初、case の全 branch をこの一つの ⊔ プールで測っていました。

これには 穴ではなく、逆向きの問題 がありました:正しいプログラムを弾いてしまうのです。線形資源 s0 : '1 S を fold の初期値に入れ、帰納仮説で threading するループ(iterateEff)を考えると、zero 枝は s0 を 1 回使い、succ 枝は 0 回使います。これを ⊔ すると ⊔(1,0) = ω ── 線形資源が ω に化けて、完全に正当な線形ループが型検査を通りません。

原因を突き詰めると、「分岐」と「fold」では枝の関係が違うことに行き着きます。分岐の枝は排他的ですが、fold の基底と step は両方走ります。両方走るものの使用量は ⊔(どちらか)ではなく SUM(合計)で測るべきです。そこで branch を ⟦⟧ を使うか否かで 2 群に分け:

Δ(case) = π_scrut·Δ_scrut + ⊔(⟦⟧ 無しの branch) + ω·⊔(⟦⟧ ありの branch)

再帰群に ω を掛けるのは、step が動的な回数走るためです。これで「線形資源は帰納仮説を通せば fold を生き延び、closure に capture したら弾かれる」という、望んだ通りの挙動が規則から出ます。

面白いのは Idris 2 との対比です。Idris 2 は一般再帰 + 停止性検査の言語なので、再帰呼び出しはただの関数適用 1 回と数えられ、この問題自体が発生しません(線形 fold が素直に書けます)。Oven は「反復を case の構造的再帰に限定する」選択をした 代償として この群分け規則を持ちますが、SUM 規則によって表現力は Idris の線形 fold と等価になっています。設計の選択が別の場所に請求書を回してくる、その請求書をきちんと払った例です。

実装では typecheck.rs の combine_case がこの式そのものです。実装上の注意がひとつコメントに残っています:⊔ には単位元がありません(⊔(0,1) = ω なので、ゼロから ⊔ を始めると壊れる)。だから各群は「最初の branch の使用量で初期化し、2 個目以降を ⊔」します。また ⟦⟧ の有無の判定(uses_ih)は入れ子の case の branch には降りません ── そこの ⟦⟧ は内側の case に属するからです。

→ 規則の全体は QTT

第一級 multiplicity ── 1 + 1 が ω になるのも instance

多くの QTT 実装で multiplicity は型の注釈に住む特別な存在です。Oven では Mult : Type ── multiplicity は普通の値であり、'p の p に変数も式も書けます。

なぜ第一級にしたか。 直接の動機は multiplicity 多相です。たとえば map は、純粋なデータ('ω)にも線形な資源の列('1)にも使いたい。multiplicity が言語の外の注釈だと、この多相のために別の量化機構が要ります。Mult がただの型なら、mult 多相はただの依存量化 (p : Mult, x : 'p A) → A になり、新しい機構がゼロ で済みます。半環が 3 値で有限なので、多相関数の検査も原理的には全 valuation の列挙で決定可能 ── 「特別な solver が要るのでは」という当初の心配は、有限性を活かせば杞憂だと分かりました。

そして第一級にした以上、半環演算 +/·/⊔ も言語の中の演算です。ここで Oven らしい徹底が入ります:1 + 1 と書いたときの + は、パーサにも型検査器にも特別扱いされていません。ambient prelude の Add(Mult) instance(中身は組み込みの addMult)が、F32 の加算と全く同じ経路 ── mixfix 脱糖 → instance 解決 ── で選ばれ、NbE が半環を畳んで ω になります。「乗法 * を特別扱いせず、multiplicity の半環すら instance で賄う」は明示的な設計方針でした。動機は一貫性です:* が文脈によって「言語の一部」だったり「ライブラリ」だったりする言語は、ユーザに 2 つのルールを覚えさせます。Oven はルールを 1 つにしました。

実装では core に MultT/M0/M1/MW と演算ノード MAdd/MMul/MJoin があり、NbE の iota が畳みます。multiplicity は 型構造の一部として conversion で比較される ため、'(1+1) A ≡ 'ω A が定義の等しさとして成立します。一方、使用量(どの変数を何回使ったか)は conversion に一切効きません ── 「量は型の形には出るが、計算には出ない」という分離が保たれています。

→ QTT・表面言語

trustMe ── 消去される公理という脱出ハッチ

postulate trustMe : [A : '0 Type] (u : Unit) -> A

任意の型 A の値を出す公理です。当然、論理としてはこれ一つで崩壊します。それでも置いてあるのは、証明義務を「あとで」にできる言語のほうが実用で生き残る からです。たとえば並列 reduce は演算の結合性に正しさが依存するので、結合性の証明 '0 Assoc(op) を引数に取る設計です。しかし「reduce を使うたびに結合性を証明せよ」では誰も使いません。trustMe() で埋めて先へ進み、必要になったら本物の証明に差し替える ── 証明の負債を型に見える形で残しながら、開発は止めない、という運用です。

この公理が壊れにくいのには理由があります。使ってよい場所が '0(消去)位置 ── 実行時に値が要らない証明の位置 ── である限り、trustMe の値は erasure で消え、実行時コストも実行時の嘘もゼロです。逆に値が本当に要る位置で使うと、trustMe には計算規則がないので評価が stuck して(GPU なら lowering エラーとして)すぐ露見します。「証明位置では安全に嘘をつけて、値位置では嘘がつけない」という性質が、機構なしで公理の悪用を防いでいます。Type : Type の不健全性を承知で採用した言語なので、「証明の健全性は絶対」ではなく「証明は実用上の不変条件チェック」という割り切りとも整合しています。

モナドなしの効果 ── なぜ token threading なのか

Haskell 系の純粋言語で効果といえばモナドです。Oven はモナドを持たず、効果を「零幅の token を線形に借りて返す」で表します:

[&X] A  ≝  '1 X → (X, A)

なぜモナドでないか。 第一に、Oven には QTT が すでに あります。線形性は「資源を一度だけ正しく使う」ことを型で言える機構で、これは効果の順序づけそのものです。モナドを足すと、順序づけの機構が 2 つ(bind の入れ子と線形性)になり、しかも GPU カーネルへ lowering する際に高階の bind 構造を解体する仕事が増えます。[&X] A の実体はただの Π と Σ なので、効果のための意味論は core にゼロ ── 実行系も lowering も効果を知りません。

第二に、この形は host と GPU を同型に扱えます。print は World token を、store は GPU token を借りて返す ── 同じ形です。実は GPU 側には一度「カーネル内は 1 スレッドが上から順に実行する命令的コードなのだから、順序は素のプログラム順でよい(linearity 不要)」という整理が存在しました。これは撤回されます。「評価器が字面の順序を守ること」に意味が依存するなら、eval・inline・正規化で順序が動き得る ── つまり 関数の純粋性(参照透過性)を売り渡している。純粋性のために [&X] を導入したのに、GPU だけ例外にしては本末転倒だ、という理屈です(→ 経緯)。結果として「効果の順序はすべて token のデータ依存で表す。零幅 token なら実行時コストはゼロ」に統一されました。

第三に、モナドが得意とする「効果の抽象化・合成」の大部分が、この設計ではただの機能の組み合わせで出ます。State も Writer も IO も「[&X] の X が違うだけ」。効果多相は [&E](E は型変数)というただの依存量化。複数効果は [&X, &Y]。monad transformer に相当する階層は最初から存在しません。

実装では core に Tm::Eff(caps, A) という former があり、eval で '1 X → (X, A) に unfold されます。おもしろいのは、シグネチャの宣言型では Eff のまま保たれる(eval されない)ことです。elaboration は「この呼び出しは効果か」を、callee の宣言型の codomain が構文的に Eff かどうかで検出します ── unfold してしまうと素の Π と区別が付かなくなるからです。効果と判定された文は、token を implicit で注入し、返る (X, A) を Split(Σ の分解束縛)で開いて token を差し替える、という形に脱糖されます。ユーザが store(out, i, x); let v = load(in, i) と書くだけで、この配管がすべて暗黙に縫われます。

辞書と token が同じ規則で解決される

typeclass の辞書(Mul(F32) の instance)と効果 token('1 World)は、見た目も役割も全然違いますが、Oven では 同じ一つの解決規則 で埋まります:「implicit/borrow 引数の解決とは、wanted 型に合う『使用可能な束縛』を文脈から見つけて usage を消費すること」。

これは美観のための統一ではなく、差分がすべて 既存の概念から導出される ことに気づいた結果です。辞書は 'ω なので何度でも引ける、token は '1 なので一度で消費される ── これは multiplicity の差にすぎません。辞書は型がまだメタ変数を含むことがあるので遅延解決、token は型が常に ground(World/GPU)なので即時解決 ── これも「型が ground か」という条件から機械的に決まります。つまり「instance 解決」と「効果 token の供給」を別のサブシステムにする理由が、調べてみたら何もなかった。

この統一の配当は handler の実装時に現れました。ユーザ効果の discharge(handler が効果ブロックに初期状態を供給する)を実装しようとしたら、新しい機構が何も要らなかった のです。implicit w0 : X = init と書けば、既存の instance 解決が [&X] ブロックの token を型で拾って供給します。「効果 handler の土台は、typeclass の instance 解決そのものだった」というのは、設計時には意図していなかった収穫です。

escape 防止に専用機構がない

線形な token や借用した資源が closure に隠れて生き延びる ── 効果系の設計で必ず塞ぐべき穴です。Rust はこれを lifetime で、多くの効果系は handler のスコープ規則で塞ぎます。Oven には escape を防ぐための規則が存在しません。それでも漏れないことが、closure の 2 規則から演繹できます:

  1. closure は '1 を capture できない(capture は 'ω のみ)
  2. '1 引数の部分適用ができない

token を閉包に入れる経路が (1) で、let k = print(io) のように部分適用で握る経路が (2) で塞がれ、複製は '1 の 2 回使用として、握り潰しは「返り型 (X, …) を満たせない」として、いずれも既存の QTT 検査に引っかかります。よって token は 1 本の線形スレッドに閉じ、必ず caller に返ります。

重要なのは、この 2 規則が escape のために 導入されたのではない ことです。これらは「関数型を A → B 一種類にする」ために(FnMut を捨てる過程で)確定した規則で、escape 防止はその副産物でした。逆にいえば、「closure に借用を capture させたい」という要求を一度でも受け入れると、region や effect row のような重い機構が芋づるで必要になる ── 実際に設計はその 2 つを作りかけて捨てています(→ 経緯)。「借用は capture させず引数で渡す」という一つの原則を守り抜くと、escape 問題ごと消滅する、というのがこの言語で最も気持ちのよい定理のひとつです。

部分借用は Rust の borrow ではなく lens

set(&arr.field, …) のようにレコードの一部だけ借りたい、という要求は自然です。Rust はこれを部分借用(disjoint borrows)で解きますが、その裏には「&mut r.a と &mut r.b は重ならない」を追跡するエイリアス解析と lifetime があります。

Oven の答えは Haskell の lens です。&r.a は「r を消費して、焦点 a と『埋め戻し関数』を返す」に脱糖されます:

Lens(S, A) = (s : '1 S) → ('1 A, ('1 A) → S)

get で分解し、焦点を関数に通し、putback で再構成して元の名前に再束縛する ── 全過程が純粋な関数適用です。エイリアスという概念自体が現れないので、解析も lifetime も要りません。「Oven の & はそもそも参照ではなく consume-and-return の糖衣である」という一貫した見立てが、部分借用まで素直に延長された形です。lens は合成できるので &r.a.b も 2 つの lens の合成で済みます。制約はひとつ:lens が構造的に導出できる path(フィールド・配列要素)に限られ、&(任意の式) は書けません。

dispatch はなぜ関数ではないのか

GPU カーネルの起動 dispatch(i in size){ body } は、Oven で数少ない「本物の構文」です。関数でも eliminator でもありません。ここには長い回り道があります(→ 経緯)。

カーネルは任意個のバッファ('1 資源)に触りたい。最初の案は「触る資源を全部レコードに束ねて引数で渡す」(explicit-R)で、これは 正しく動きます。しかし手で束ねるのは冗長で、「ふつうに closure として out や in を capture して書きたい」という書き味の要求がありました。ところが capture を許すと、'1 資源が closure の環境に取り込まれて 封印 されます ── 使い終わっても返ってこない。これを救うために region システム(バッファを region 所有にして時間 token を threading する)まで検討されましたが、複雑さが過剰で撤回。

最終的な洞察は「capture は書く。でも closure 値を作らなければ封印は起きない」でした。dispatch を構文にすれば、body はその場にインラインで書かれるだけで、関数値として存在しません。値にならないものは脱出も封印もしない。body が参照する自由な '1 変数は、構文が borrow-lift ── 消費して継続に返す ── します。外から見れば「借りて、走らせて、返した」だけです。

もうひとつ、構文であることには消極的でない理由があります。borrow-lift する資源の集合は body の中身(どの自由変数を使うか)で決まります。つまり dispatch の「型」が body に依存する ── これはもはや関数型で書けません。関数にできないから構文にした、という必然です。

実装では core に Tm::Dispatch(size, body, borrows, elem_tys, cont) という 5 つ組のノードがあります。borrows は elaboration が body を kernel モードで型検査したときに集めた自由 '1 変数のリスト。継続 cont は「借用が返ってきた後」の世界なので、redirect_cont が de Bruijn index の付け替え(借用された変数への参照を fresh な binder へ張り替え、他の外側参照をシフトする)を行います。線形性の帳簿はこの refresh を通して繋がるので、release(out); dispatch { store(out, …) } のような use-after-free は普通の '1 検査として弾かれます。

ベクトル型が「無い」── タプルがそのまま vecN

GPU 言語には必ず vec3<f32> があります。Oven に「ベクトル型」という新しい型はありません。F32³ は ただのタプル (F32, F32, F32) の表記 で、GPU lowering がこれをネイティブ vec3 にします。

なぜ型を足さなかったか。 新しい型を core に足すと、影響は型検査だけでは済みません。conversion の規則、NbE の値表現、runtime の値、pretty-printer、パーサ ── 言語のすべての層に「vec という新概念」が波及します。一方、よく見ると vecN は「同型スカラの 2〜4 成分の組」であり、Σ 型として既に表現できる構造 です。だったら「同型スカラのタプルは GPU lowering で vecN になる」という 解釈 を lowering に置くだけでよい ── 言語の意味論には何も足さない。構築はタプル構文、成分アクセスは既存の射影 .0/.1/.2(WGSL の .x/.y/.z に対応)、色 (r,g,b) を作れば自然に vec3 です。CPU emulation は成分を分解して計算するだけで、値表現の変更もありません。

この設計のもうひとつの柱は 「WGSL の都合を言語に漏らさない」 です。GPU の std430 レイアウトでは vec3 のストライドが 16 バイトになる等、メモリ上の姿には GPU 固有の事情があります。これをコア型や runtime に持ち込むと、「タプル = vec」という綺麗な同一視が壊れます。そこでアラインメントの処理は gpu.rs の buffer I/O(実 GPU との境界)だけに閉じ込めました。言語から見える意味論は常に「ただのタプル」です。

ベクトル演算(+・dot・length・normalize)は src/builtins.rs::vec_builtins() のレジストリに宣言的に並んでいて、それぞれ CPU の成分計算と WGSL のネイティブ呼び出し(dot()/length()/normalize())の両方を持ちます。演算の追加はレジストリのループに 1 行です。

U8⁴ ── RGBA8 を u32 1 個にパックする

画像の 1 画素は RGBA 各 8 bit、合計 32 bit というのが標準です。Oven では U8⁴ = (U8, U8, U8, U8) がこれに当たり、GPU 上では 1 個の u32 に bit パック されます。

背景には 2 つの決定があります。まず U8 を一級のスカラ型として立てたこと。「色は F32 を 255 倍すればいい」でも動きますが、PNG やテクスチャの native な形式は整数バイトであり、正規化色(UNorm8)と整数バイト(U8)は 意味の違う別の型 だ、という判断がありました(UNorm8 は将来の別型)。GPU には u8 スカラが無いので、実行上は u32 で担いで算術に & 255u のマスクを入れます。

次にパッキング。ベクトルの一般則に従えば U8⁴ は vec4<u32> = 16 バイトになりますが、RGBA8 の意義は 4 バイトに詰まっていることです。そこで lowering に GTy::PackedU8(n) という表現を持たせ、構築は bit シフト、射影は bit 抽出、読み戻しは unpack にしました。ここでも「GPU の都合の局所化」が守られています:パックは GPU lowering と readback のデコードだけで行い、CPU emulation は U8 のタプルのまま 計算します。言語の意味論はどちらの経路でも同一で、メモリ上の姿だけが違う、という分離です。

実装の細部にひとつ教訓が残っています。値が「自分は U8 だ」と知っている必要があったこと(Scalar::U8 という担体の区別)。u32 で担いだまま型情報を落とすと、lowering が (U8,U8,U8,U8) を見ても vec4<u32>(16 バイト)と区別できず、誤判定します。消去と単相化の言語でも、リテラルの「幅」は値に自己記述させる必要がありました。

発見の経緯が示唆的です。dispatch の設計(「境界は線形な借用・内部は race 非検査」)が本当に健全か、敵対的にレビューしたときに、具体的な攻撃が見つかりました:カーネル内(当時の整理では線形性の検査が無い)で '1 の buffer ハンドルを 別の buffer に store し、borrow-lift で host へ返すと、host は同じ資源を指す名前を 2 つ持つことになる ── 線形資源の複製です。複製できれば二重解放も use-after-free も型を通ります。

「境界の線形規律さえ守れば内部は自由」という dispatch の設計思想は、この修正で「境界を 迂回する経路が無いこと も検査対象」に補強されました。同種の穴が他にないかは、未解決として今も監視対象です。

これは当初、'GPU modality(型に付く「GPU で走る」という印)の売りとして導入された性質です。「とりあえずコンパイルしてみて、最後に GPU に載らなかったらエラー」という方式は、エラーが lowering の内部表現の言葉で、しかも問題の根源から遠い場所に出ます。型の印で層を分ければ、「まさに違反した構文の場所」でローカルに報告できる ── 2LTT の「GPU 断片の隔離」という発想の、実用上いちばん嬉しい配当がこの診断品質でした。

再帰型の弾かれ方も綺麗です。Nat を名指しで禁止するルールはなく、case のパターンフィールドに representable を課すと、succ のフィールド型 Nat が再帰的に検査されて自動的に弾かれます。一方、全 constructor が引数なしの有限 enum(Bool や data Dir { east, west })は同じ検査を通り、u32 タグとして GPU に載ります(sig::is_finite_enum)。当初は「enum も手動で U32 エンコードせよ」でしたが、タグ化は機械的なのでコンパイラが引き受けました。

CPU emulation が GPU のオラクル

Oven のプログラムは 2 つの経路で実行できます。既定の CPU emulation(依存ゼロ・tree-walking)と、feature gpu の実 GPU 実行(wgpu)です。両者は独立の実装で、テストは両経路の結果一致を検証します。

なぜ 2 経路を維持するのか。 GPU 実行は本質的に検証しづらいからです。結果はドライバ・GPU 世代・浮動小数の実装に依存し、失敗はシェーダコンパイルエラーや黙った誤答として現れます。「言語の意味論として正しい答え」を GPU 自身に語らせることはできません。そこで、言語の全機能が動く、依存ゼロで決定的な実行系を先に作り、それを正とする 方針が採られました(M0 の目標が「GPU より先に CPU で画像を計算する」だったのはこのためです)。GPU バックエンドを書く仕事は「オラクルと同じ答えを出すこと」という明確なゴールを持つ機械的な作業になります。

実装上、2 経路は消費する中間表現からして違います。CPU 経路は erasure 後の 無型 の実行時 IR Rt(高階 OK・構造的再帰 OK)を tree-walking し、GPU 経路は 型付き の core Tm から一階の KernelIR へ lower します(GPU は全式に型が要るため)。性質が真逆の 2 つの消費者を同じ core から派生させていて、共有しているのは数値プリミティブの意味(NUM_BUILTINS の同じ表を両者が引く)だけです。CPU 側の数値計算は意図的に WGSL のセマンティクスに合わせてあり(fract = x−floor(x)、log = 自然対数)、それでも避けられない超越関数の ULP 差だけをテストの許容誤差が吸収します。

表面言語まわり

演算子が全部「ただの instance」

a * b は _*_(a, b) に脱糖され、_*_ は「Mul(A) の辞書 d を implicit で取り、d(x, y) を呼ぶだけの普通の関数」です。パーサが知っているのは fixity 宣言(infixl 7 _*_)だけで、* の意味はスコープ内の instance が決めます。

動機は徹底した一貫性です。演算子に組み込みの意味を持たせると、「組み込みの *」と「ユーザの演算子」の 2 種類のルールができ、さらに「Mult の * は型検査の一部、F32 の * はライブラリ」のような層の混在が生じます。Oven はここを 1 つに潰しました:乗法 * は Mult でも F32 でも「ただの instance」。multiplicity の半環演算すら特別な構文を持ちません(→ 第一級 multiplicity)。

この一般化を成立させるために解いた実際的な問題が 2 つ記録に残っています。ひとつは リテラルとのデッドロック。2.0 * 3.0 の型検査では、被演算子はリテラルで型が未確定、instance も未解決 ── クラスの結果型を連想型(d.Out)にすると、型パラメータ A を確定させる手がかりがどこにも無く、推論が膠着します。そこで標準の演算子クラスは結果型を A(homogeneous)にしました。期待型(F32 が欲しい文脈)が A を直に解き、リテラルも辞書も連鎖的に解けます。もうひとつは 総称関数内の演算子。square [A, d : Mul(A)] (x : A) = x * x の本体で * を使うには、仮引数 d が instance プールに入っている必要があります。ここは「nominal 型を持つ束縛は自動的に instance になる」という規則(pool_if_nominal)で解決され、Agda の instance 引数に相当するものが「クラス = nominal 型」から自然に出ました。

lexer にも一点だけ支えがあります。記号の連なり(+ - * < > …)を 1 つの Op トークンにまとめ、_op_/op_ を通常の識別子として組み立てる ── 演算子そのものを定義・参照できるのはこのためです。

nominal ── 名目性だけを足した最小の newtype

typeclass のクラス本体は nominal 型です:

nominal Add (A : Type) = (x : A, y : A) -> A
nominal Mul (A : Type) = (x : A, y : A) -> A

Add(F32) と Mul(F32) の中身はどちらも (F32, F32) → F32 で、構造的には同じ型です。Oven の conversion は構造的なので、素の Σ でクラスを表すと 加算の instance が乗算の解決候補になってしまう ── instance 解決は型一致で辞書を拾うので、同形クラスの共存が即座に曖昧エラーになります。これが nominal を導入した理由の全てです。名前で型を区別する(名目的な)壁を、この一箇所のためだけに立てました。

面白いのは透明性の設計です。普通の newtype(Haskell の newtype、Rust のタプル構造体)は構築と分解にラッパの出し入れが要ります。Oven の nominal は conversion でだけ不透明で、それ以外には完全に透明 です:d : Mul(A) はラップなしの素の関数値で、d(x, y) と直接呼べます。実装では typecheck.rs の peel_nominal が「構築・除去(適用・射影)のときだけ body へ展開し、conversion では決して展開しない」という片側だけの unfold を行います。「instance 解決が曖昧にならない」という一点のためにどれだけ小さい機構で済むか、を突き詰めた結果が「conv だけ見えない壁」でした。

なお、初期実装ではタグ付きレコードで区別する ad-hoc な方法を使っていて、後に nominal 型として原理的に整理し直した経緯があります。「動くけれど原理から出ていない解を、原理のある形に置き直す」という、この開発で繰り返されるパターンのひとつです。

module ── レコードを返すただの関数

module Vec3 (n : U32) {
  zero : U32 = 0[U32];
  scale (s : U32, v : U32) : U32 = mulU32(s, v);
}
Vec3(3[U32]).scale(2[U32], 5[U32])

ML 系言語のパラメータ付きモジュール(functor)に見えますが、専用機構は存在しません。module M (params) { … } は let M = λ(params) let f = …; let g = …; (f = f, g = g) ── 引数を取って名前付きレコードを返す関数 への純粋な糖衣です。

これが可能なのは、言語の 2 つの基礎的な選択の配当です。第一に Type : Type:型がただの値なので、レコードのフィールドに型を入れられ、モジュールが型を輸出することも(必要なら)普通の依存 Σ で書けます。第二に Σ backbone:「名前付きの束」という概念がレコードとして既にあり、モジュールのために新しい名前空間機構を作る理由がありません。内部が nested let なので後の定義が前の定義を参照できる(共有される)ことも、糖衣の展開形から自明に出ます。

「モジュールシステム」は言語設計の中でも際立って重くなりがちな部分(ML の functor・シグネチャ・sealing はそれ自体が研究分野です)ですが、依存型があるとその大部分が「関数とレコード」に還元される ── Oven はその教科書的な事実を、実際に専用機構ゼロで実装した形です。open(無修飾の取り込み)だけは構文の仕事なので、将来の課題として残っています。

tight/loose ── 空白が意味を持つ適用

f(x, y) と f (x, y) は違う意味です。前者(tight:f と ( が密着)は curried 適用 (f x) y、後者(loose:空白あり)はタプル (x, y) を 1 個渡す適用です。

空白に意味を持たせるのはリスクのある選択で、それでも採ったのには経緯があります。Oven の適用は当初、引数テレスコープを Σ として一括で渡す方式(Σ-domain)でした。Σ backbone の思想には合うのですが、implicit 推論と衝突します:型パラメータ A と辞書 d を 1 つの Σ に束ねると、単一化が「テレスコープの Σ」と「辞書そのものの Σ 型」を構造的に区別できず、instance 解決が壊れました。それで適用は全面 curried へ移行(このとき実装が 146 行減っています)。しかし「関数がタプルを受け取る」形は依然として正当な型なので、curried 適用とタプル適用の 両方を書き分ける記法 が必要になり、tight/loose の区別に落ち着きました。

つまりこれは美観の選択ではなく、「curried(推論に必要)とタプル(Σ backbone に必要)の両立」という制約の解です。f(a, b) = f a b = 並置、と教われば規則自体は単純ですが、f (x, y) の空白 1 個が意味を変えることには慣れが要ります。設計もそれは自覚していて、パーサ詳細の未確定項目として記録されています。

リテラルは型の指標 ── 既定型を持たない

0 は文脈によって Nat の zero、F32 の 0.0、Mult の '0 になります。期待型がリテラルを解決し、期待型が無い場所(注釈なしの let x = 5)では エラー です(5[Nat] のように注釈します)。

多くの言語はここで既定型を持ちます(Haskell の defaulting、Rust の i32 フォールバック)。Oven がそれを拒否したのは、「その場で勝手に既定の型を決める」のが ad-hoc だから、という明確な方針によります。defaulting は「なぜ i32 なのか」に原理的な答えがなく、しかも推論の他の部分と相互作用して驚きを生みます(Haskell の defaulting 規則の複雑さは有名です)。書き手に 1 つ注釈を要求するほうが、暗黙の規則を 1 つ覚えさせるより安い、という判断です。

実装として面白いのは、Tm::Lit が 「elaboration で消える契約」の項 であることです。パーサは 0 を Lit のまま core に入れ、型検査が期待型を見て M0 や succ^n zero や機械スカラ Scalar へ置き換えます。解決後の木に Lit は残らず、万一 eval や erasure に届いたら panic で契約違反が顕在化します。名前付き射影 ProjN(r.field ── 型を見ないと位置に解決できない)も同じ「型検査で消える surface 項」で、「parse の時点では決められないものは、専用ノードで型検査まで運ぶ」という一貫したパターンになっています。

assert の引数が '1 である理由

postulate assert : (b : '1 Bool) -> [&World] Unit

Bool を「1 回だけ使う」と宣言する意味はあるのか、と一見不思議な型です。これは QTT の適用規則から来る、実際的な設計です。

適用 f(a) の使用量は「引数式 a の使用量 × binder の multiplicity」で計算されます。もし assert の引数が 'ω だと、引数式の中で使われた資源の使用量が ω 倍 されます。テストの典型形 assert(eqArray(readback(a), readback(b))) では、引数式が線形 buffer a, b を消費(readback)しています。ω 倍されると「線形資源を ω 回使った」ことになり、完全に正当なこのコードが線形性違反で弾かれてしまう。引数を '1 にすれば使用量は 1 倍のまま通ります。

この型が入る前、自己検証テストは複数の条件を and で束ねた 1 つの式にしていて、まさにこのスケーリング問題に踏んでいました(and : (Bool, Bool) → Bool の引数が 'ω で、線形 readback が弾かれる)。assert を効果つき・'1 引数の文として導入したことで解消しています。「引数の multiplicity は『callee が何回使うか』だけでなく『引数式に何を書けるか』を決める」という、QTT の言語に固有の API 設計の一面です。

Bool も Nat も処理系にハードコードされていない

Bool/Nat/Fin/Vec/Id は、処理系の Rust コードに焼き込まれた特別な型ではなく、std/prelude.ov に Oven の data 宣言として 書かれています。処理系は起動時にこのファイル(include_str! で埋め込み)をパースしてシグネチャを作ります。Buffer や store のような真のプリミティブも同様に postulate 宣言としてこのファイルにあります。

こうなったのは初めからではありません。M0 の当初方針は逆で、「inductive の一般機構は作らない。組み込み型と eliminator をプリミティブ表に焼き込む」でした。転換の直接の理由は QTT です:型ごとの eliminator は、型ごとに使用量の合流規則(どの引数が '0/'ρ/'π か)を手で持つことを意味し、これが誤りの温床になりました(実際に旧規則には線形 fold を弾く穴があった)。data 宣言から constructor・case・iota・QTT 合流を 一般規則で導出 するほうが、規則が 1 つで済み、しかも検証も 1 回で済みます。

一般機構ができれば、組み込み型を特別扱いする理由は消えます。prelude を Oven ソースにしたのはその帰結で、副産物として言語の dogfooding(data/postulate/nominal 宣言・借用記法・効果 former が、処理系の起動のたびに実データでパースされる)にもなっています。数値プリミティブはさらに一段自動化されていて、postulate addF32 : … のような宣言は prelude にすら書かれず、src/builtins.rs::NUM_BUILTINS の表(名前・型・CPU 計算・WGSL 形)から自動生成されます。数値関数の追加は表 1 行です。

quote_shared ── 30GB のメモリ爆発から生まれた quote

NbE の quote(値を項に書き戻す操作)は、素朴には値の木構造を辿ります。しかし eval が作る値は Rc で共有された DAG です。共有を無視して辿ると、DAG は木に展開されます ── 指数爆発の古典的な形です。

これが実際に火を噴いたのが showcase(マンデルブロ)でした。escape(c) = (iterate(16, …)).cnt のように反復をラッパ関数越しに呼ぶと、GPU lowering のインライン展開が quote(eval(…)) を通り、共有されていた反復の中間状態が反復ごとに複製されます。計測では 1 反復あたり項サイズ 13 倍、16 反復でメモリ 30GB に達して完走しませんでした。普通のプログラムがコンパイルできないのは言語として致命的です。

解決が nbe::quote_shared です。通常の quote と違い、eval の Rc-DAG を辿りながら 同一ノード(ポインタ等価)を検出して let 束縛の列に平坦化 し、2 回目以降の出現を変数参照にします(GVN:同じ計算に同じ名前を与える)。出力は「let の連鎖 + 本体」という形の項で、共有が構文上の共有(let)として保存されます。健全性の注意点として、分岐の下で評価された値をどこまで持ち上げてよいかがあり、branch 評価のキャッシュで扱っています。この修正で showcase は CPU/GPU 両経路とも完走し、回帰テスト(反復カーネルの項サイズが爆発しないこと)が置かれました。

「正規化は正しいがサイズが爆発する」は依存型処理系の定番の罠で、Oven の場合は GPU lowering(全展開が避けられない)がそれを増幅しました。「意味論の正しさ(quote∘eval = id)と計算量の正しさ(共有の保存)は別の要件」という教訓の実物です。

fromU32 ── 機械整数から「回数」への全域な橋

postulate fromU32 : (n : U32) -> Nat

型理論の Nat は succ(succ(…zero)) という unary 表現で、「n 回繰り返す」という 概念 の担い手です。しかし実行時に unary の数を持つのは O(n) の無駄で、GPU では論外です。一方、実行時の数は機械整数 U32 で持ちたいが、U32 は不透明なスカラで帰納構造(= case で回す能力)を持ちません。この 2 つを繋ぐのが fromU32 です。

注目すべきは 全域である ことです。逆方向(Nat → U32)は 2³² を超える Nat で破綻するため有界性の証明が要りますが、こちらの方向は「どの u32 も Nat である」── 論理的には fromU32(n) = succ^n(zero) と定義でき、部分性がありません。証明義務ゼロで機械整数を「回数」として使えます。

実装では fromU32(n) の結果は unary に展開されず、担体の u32 をそのまま持ちます。そして iterate(fromU32(n), f, init) のような fold(case)を、runtime と GPU lowering が for ループ として実行します。つまり「論理的な意味は unary Nat の構造的再帰、実行時の姿は機械整数のカウンタループ」という二重写しです。これは将来構想(表現可能性の Repr witness ──「帰納型に GPU-native な担体への埋め込みを与えると、その fold が for に翻訳される」)の最初の具体例でもあり、「functional なプログラムを imperative なループに翻訳する」という言語全体の野心の縮図になっています。

依存型言語(Agda・Idris 2・Lean)と比べて

共有しているもの は多い:MLTT ベースの依存 Π/Σ、帰納型、definitional equality を NbE で判定する処理系の骨格(elaboration-zoo 系の設計)まで、コアの作りは現代の依存型言語の標準そのものです。Agda 使いが Oven のコードを見れば、telescope・implicit 引数・instance 引数(nominal の自動プールは Agda の instance argument にかなり近い)にすぐ見覚えを感じるはずです。

決定的に違うのは目的です。 Agda・Lean は証明支援系であり、健全性(「証明されたことは本当に正しい」)が存在意義です。Oven は Type : Type を承知で採り、Girard のパラドックスで False が証明できることを受け入れました。この一点で Oven は証明支援系のリーグから 意図的に降りています。依存型は Oven にとって証明の道具ではなく、コンパイルの道具 です ── 配列長を型に載せて単相化でサイズを静的化する、添字の範囲を消去された証明で保証する、GPU に載るかを型で判定する。「証明支援系の道具立てを、証明のためでなくコード生成のために使う」というのが依存型に対する Oven の姿勢です。

全域性の実現方法も対照的です。 Agda は一般再帰を書かせて停止性検査器(構造的減少の解析)が後から検証します。Lean も同様で、well-founded recursion への elaboration が裏で走ります。これらの検査器は強力ですが、それ自体が複雑な機構であり、「なぜ通ったのか/通らないのか」が構文から見えないことがあります。Oven は逆に、再帰を書ける場所を構文で制限しました(⟦w⟧ は再帰パターン変数にしか適用できない)。書けるものは全部全域、検査器は存在しない。表現力は落ちますが(相互再帰や複雑な減少測度は書けない)、GPU に載せる言語では「回数の決まらない計算」はどのみち存在できないため、この制限は GPU 制約と同じ方向を向いています。失うものが最初から失われている、という設計です。

Idris 2 とは QTT の兄弟です。 '0/'1/'ω の 3 値 multiplicity、消去と線形性の統合は Idris 2(とその基盤の Atkey の QTT)から直接来ています。違いは 2 つ。第一に、Idris 2 は一般再帰の言語なので再帰呼び出しをただの関数適用(1 回)と数えますが、Oven は case 展開の再帰なので「再帰 branch は動的回数走る」を使用量規則(2 群 SUM)として自前で持つ必要がありました(→ QTT)。第二に、Oven は multiplicity を第一級の値(Mult : Type)にし、半環演算まで instance に落としました。Idris 2 の量は注釈の世界の住人で、量の多相はありません。なお研究言語まで含めれば、量を型で数える発想は Granule(graded modal types)がより一般的な形(任意の半環でのグレーディング)を追求しており、Oven の 3 値固定はその実用特化版と見ることもできます。

純粋関数型の効果(Haskell・Clean・Koka)と比べて

Haskell との対比が Oven の効果系を一番よく説明します。 Haskell の IO は表面上はモナドですが、GHC の内部では IO a = State# RealWorld -> (# State# RealWorld, a #) ── 世界 token の受け渡し です。ただしこの表現はユーザから隠され、token の一回性はコンパイラだけが知る不変条件です。Oven がやったのは、この内部表現をそのまま表面の意味論にする ことです。[&World] A ≝ '1 World → (World, A) は GHC の内部形とほぼ同じ形をしていて、違いは token の一回性を QTT がユーザレベルの型として強制すること。モナド・do 記法・transformer の階層は全部不要になり、効果の合成は「token が 2 本になる」だけです(→ 効果系)。

この系譜でいちばん近い祖先は Clean です。Clean は一意性型(uniqueness types)で *World を明示的に受け渡しし、モナドなしで IO を実現した言語で、Oven の効果系は「Clean の世界受け渡しを、一意性型でなく QTT の線形性の上に載せ、受け渡しの配管を elaboration で暗黙化したもの」と要約できます。Clean ではユーザが世界を手で持ち回りますが、Oven では token は implicit で、ユーザは print("hello"); print("world") と書くだけです。

代数的効果の系譜(Koka・Effekt)とは、明確に違う道を選びました。 Koka は効果を row 多相で型に載せ、handler で自由に解釈を差し替えます。Oven は effect row を 検討した上で却下 しています(→ 経緯)。理由は、row・存在量化・資源計算の機構が芋づるで膨らみ、「糖衣のために意味論を足さない」に反したこと。代わりに「capability は宣言・推論なし・単一抽象 [&E] までは書ける」という保守的な線を引きました。効果の抽象化の柔軟さでは Koka に遠く及びませんが、効果の意味論が core にゼロ(ただの Π と Σ)である、という対価を得ています。handler に相当するものが「instance 解決で token を供給するだけ」で書けたのは、この設計の配当です。

Rust と比べて ── 線形性・借用・lifetime

Rust は「資源を型で管理する言語」の現在の代表で、Oven の & が Rust の &mut を意識しているのは名前からも明らかです。しかし中身はかなり違います。

Rust の借用は「参照」です。 値はその場に留まり、参照が貸し出され、エイリアスの安全は lifetime と borrow checker(エイリアス解析)が守ります。Oven の & は参照ではありません。 set(&arr, i, v) は「arr を消費して、更新後の arr を返してもらい、同じ名前に再束縛する」の糖衣 ── 値そのものが移動する consume-and-return です。参照が存在しないので、エイリアスという概念自体が型システムに現れず、lifetime が要りません。部分借用も Rust の disjoint borrows(&mut r.a と &mut r.b の非重複をコンパイラが追跡)ではなく、lens(get と putback の純粋な対)です。Oven が純粋・全域だからこそ成立する単純化で、Rust のように任意の命令的コードと共存する必要があれば、この手は使えません。

線形性の厳密さも違います。 Rust の所有権は affine(高々 1 回 ── 黙って drop できる)ですが、Oven の '1 は strict linear(ちょうど 1 回 ── drop にも Consumable の宣言が要る)です。IO token を「握り潰せない」ことが効果の完了保証になるので、この差は飾りではありません。逆に Rust が普通にできて Oven にできないのが 共有読み取り借用(&T を複数箇所へ同時に貸す)です。QTT の threading は「一本の糸を順に持つ」ことしか表せず、コピー不可資源の同時読み取りは fractional permission か region を将来足さない限り書けません(→ 現状)。Rust との比較で最も分が悪いのはここです。

もうひとつの対照は escape 解析 です。Rust は closure が参照を捕捉して逃げることを lifetime で防ぎます。Oven には対応する機構がなく、「closure は '1 を capture できない」「'1 の部分適用はできない」という 2 つの規則から escape 不可能性が定理として出ます(→ カタログ)。機構の少なさをどこまで規則の帰結で賄えるか、という点で両言語は好対照です。

GPU 配列言語(Futhark・Dex)と比べて

目的が一番近いのはこの系譜です。Futhark は純粋関数型のコードを GPU に落とす言語の現在の到達点で、「どんな断片なら GPU に乗るか」の設計は Oven が教科書として参照したものです。しかし並列性の扱いが正反対です。

Futhark は暗黙並列です。 ユーザは map・reduce・scan などの SOAC(second-order array combinator)で書き、コンパイラが flattening・fusion を駆使して並列コードを合成します。races は言語モデル上存在せず、結果は決定的です。Oven は明示並列です。 dispatch(i in size){ … } でスレッドグリッドを直接切り、スレッド ID から添字を計算し、atomic も競合も(compute shader と同様に)ユーザの責任です。これは compute shader のメンタルモデルを保ったまま型を強くしたい、という選択で、「コンパイラが並列化してくれる」安心と「このスレッド配置で走ると分かっている」制御のトレードオフです。creative coding・procedural generation という用途(Shadertoy 的な「ピクセルごとの関数」を書く世界)では、後者のほうが素直だという判断があります。

型の強さでは Oven 側に分があります。Futhark のサイズ型は配列長の整合を追う専用機構ですが、Oven では長さはただの依存型の値です(単相化で静的化)。一方、成熟度・最適化(fusion・タイリング・マルチバックエンド)では比較になりません ── Futhark は 10 年選手の研究プロジェクトで、Oven の lowering は「inline して WGSL を吐く」段階です。

Dex(Google の研究言語)とは「添字を型にする」発想を共有しています。Dex の型付き index set は、Oven の Fin(n) と pull 配列(Fin(n) → A はただの関数)に対応します。Dex は effect system や自動微分まで積んだ野心的な設計でしたが、研究プロジェクトとして休眠しました。依存型 × 配列 × GPU という組み合わせが「誰も安定に届いていない空白地帯」であることの証左でもあります。

シェーダ言語そのもの(GLSL・WGSL・CUDA) と比べると、Oven が足そうとしているものが見えます。これらは高階関数も多相もほぼ持たず、カーネル間のコード共有は文字列インクルードやマクロの世界です。Oven は「普通の関数型言語の抽象(高階関数・typeclass・レコード・依存型)で書き、カーネル境界の特殊化とインライン展開で全部消して、素の WGSL に落とす」ことを狙います(→ host 特殊化)。「抽象は書けるが、実行時には存在しない」── ゼロコスト抽象の GPU 版です。

ステージング言語(MetaOCaml・Terra・Zig comptime)と比べて

「ホストの言語でコード生成し、制限された言語で実行する」という構図だけ見れば、Oven は 2 段階の言語(two-stage language)にも見えます。実際、最初の設計案は 2LTT(Two-Level Type Theory)による明示的なステージ分けでした。MetaOCaml のクォート ⟨e⟩・Terra の Lua/Terra 分離・Zig の comptime は、みなこの「層を構文で見せる」系譜です。

Oven はこれを 却下した 側です(→ 経緯)。理由は一貫して「host 用と kernel 用を構文で書き分けたくない。一つの言語で書きたい」。同じ関数 stepC が host でも GPU でも呼べて、印は付かない。層の分離はユーザの構文からは消え、コンパイラの中(消去・単相化・特殊化・表現可能性検査)に沈められました。ステージングの明示性は「何がいつ計算されるか」を確実にする長所がありますが、Oven はそれを「全域 + 単相化で、コンパイル時に決まるものは必ず決まる」という言語側の性質で代替しています。Zig の comptime が「普通のコードがそのままコンパイル時にも走る」で人気を得たのと、目指す書き味は案外近いところにあります。

creative coding の環境(Processing・Shadertoy)と比べて

最後に、用途側の比較です。creative coding の現在の主流 ── Processing/p5.js、Shadertoy、TouchDesigner、Houdini VEX ── は、ほぼ例外なく 動的か、C 系の弱い型 の世界です。この分野で支配的な価値は「即時のフィードバック」と「書き始めの軽さ」で、強い静的型はむしろ邪魔だと考えられてきました。

Oven はここに真っ向から逆張りしています:依存型と線形性を持つ全域言語で、画像と音とメッシュを作る。賭けているのは、生成的なプログラム(procedural generation・アセット生成)は書き捨てに見えて実は「壊れずに変形し続けたいプログラム」であり、型の強さが効く、という読みです。バッファサイズの不整合や解放忘れが実行時でなく型検査で落ちる Shadertoy、と言えば狙いの雰囲気が伝わるでしょうか。この立ち位置を狙った言語は、知られている範囲でほぼ存在しません(この niche 自体が Oven の最も珍しい点かもしれません)。

ただし現状は正直に:即時フィードバックの点ではまだ cargo run + PNG 出力の段階で、ライブコーディング環境やホットリロードはありません。勝負はこれからです。

まとめ ── どのマスにも先客がいない

各伝統の代表と比べたとき、Oven の立ち位置は消去法的に浮かび上がります:

  • 証明支援系(Agda・Lean)は健全だが、GPU では走らない。Oven は健全性を捨てて実行を取った。
  • シェーダ言語(WGSL・CUDA)は走るが、抽象がない。Oven は抽象を書かせて、コンパイル時に消す。
  • GPU 配列言語(Futhark)は自動並列で安全だが、明示的な制御と依存型がない。Oven は compute shader のモデルを保ったまま型を強くした。
  • Rust は資源管理の王者だが、依存型も純粋性もない。Oven は参照そのものを捨てて、lifetime ごと問題を消した。
  • Haskell/Clean は純粋だが、GPU は他人事。Oven は効果系の設計自体を GPU と host で共有できる形(token threading)にした。

つまり「依存型 + strict linear + 全域 + 明示 GPU + モナドなし効果」という組み合わせのマスには、現在ほぼ誰も座っていません。ただしこれは自慢であると同時に警告でもあります ── そのマスが空いているのは、需要がないからか、難しすぎるからか、まだ誰も試していないからか、Oven 自身が実験で確かめている最中です。設計ノートの流儀に従えば:このマスが本当に住める場所かどうかは、まだ分かっていません。

なぜ統合が「綺麗」でありうるのか ── 制約の合流

このマスに誰もいないことには、コミュニティの分断という社会的な理由もあります。証明支援系の人は GPU を見ず、シェーダの人は型理論を見ず、Houdini のアーティストは自分たちが参照透過な関数型環境(recook = 再評価)を使っているとは思っていない。それぞれの世界の中では、他の世界の道具は「関係のないもの」に見えます。

しかし各世界の芯だけを取り出して並べると、要求は衝突するどころか、多くの場所で同じ一点を指しています。Oven の設計を貫くのはこの合流です:

  • 全域性:Agda の世界では型理論の衛生(論理として無矛盾であるための条件)、GPU の世界では物理的制約(一般再帰が存在しない)。「自由再帰を入れない」という一つの決断が、両方の要求を同時に満たす。
  • '0(消去):型理論側から見れば proof irrelevance(証明は実行に関与しない)、GPU 側から見れば erasure と単相化の根拠(サイズと型はコンパイル時に確定する)。一つの multiplicity が両方の顔を持つ。
  • 線形性:Rust 側から見れば資源管理、Haskell/Clean 側から見れば効果の順序づけ。'1 という一つの量が、バッファの二重解放防止と IO の逐次性を同じ規則で守る。
  • 「値 = 関数」:Shadertoy の「画像は uv の純粋関数」、Houdini の「ジオメトリは手続きの評価結果」、関数型言語の第一級関数。render(n, f) に λ を渡してカーネルへ特殊化する機構は、この 3 つの言い換えを 1 つの実装で受け止めている。
  • per-element 並列:Houdini の wrangle(全ポイントに同じコード)、compute shader のスレッドグリッド、配列言語の map。dispatch(i in size) はこの共通の芯の直接の写しで、だからどの世界の住人にも「知っている形」に見える。

統合が力づくの接合(どれかの世界に他を従わせる)にならずに済んでいるのは、この偶然とは思えない一致のおかげです。逆に言えば、Oven の設計判断で迷ったときの判定基準は「その選択は 4 つの世界のどの芯を写しているか。どれか一つの世界の都合に他を従わせていないか」でした。

その先 ── もっと多くのものが綺麗に表現できるはずだ

この統合実験の仮説は「これで終わり」ではありません。同じ土台の上に、まだ言語として綺麗に表現されたことのないものが載るはずだ、という見立てがあります。いくつか、現在地から自然に延びている方向を記録しておきます:

  • メッシュ・ジオメトリ:Houdini の geometry は「要素数 + attribute の束」であり、依存レコード (n : Nat, pos : Array(n, F32³), …) がまさに欲しがっている形です。トポロジの不変条件(接続の整合性)を '0 の証明として持てれば、VEX には原理的に書けない保証が得られます。Unity アセット生成という当初目標の延長線上です。
  • 時間・シミュレーション:音は既に「時間の関数」として書けます(sound.ov)。アニメーションや時間発展を、線形な状態 threading(iterateEff)と純粋な「時刻の関数」の両方で書けて相互に行き来できるなら、FRP が目指した場所に別の道から届くかもしれません。
  • 微分可能性:全域・純粋・一階に落ちる言語は、自動微分にとってほぼ理想の基質です(Dex が挑んだ場所)。procedural generation と最適化(目標に向けてパラメータを寄せる)が繋がると、生成の書き方自体が変わります。

これらがこの土台に本当に綺麗に載るのかは、例によってまだ分かりません。ただ、「離れて見える世界たちの芯が実は同じ形をしている」という観察が一度成立した以上、同じことが他でも起きると期待するのは不自然ではない ── それがこの実験を続ける理由です。

なお、この章の比較対象の選定と性格づけは執筆時点(2026 年)の状況認識です。各言語は動く標的であり、記述が古びる可能性があります。

型検査コアと実行時 IR の分離

型検査・NbE の値表現(value.rs ── Rc 共有のクロージャ/環境)と、実行のための IR(runtime.rs の Rt)は別物です。erasure は 型を見ない純構造の変換 で、elaborator が適用ノードに消去情報('0 ビット)を載せておき、erasure はそれを読むだけです。この分離により実行が O(画素) になり、分離前と比べて 42 倍の高速化が計測されています。

NbE の実装メモ

  • 骨格は András Kovács の elaboration-zoo の Rust 移植。GC がないので値とクロージャは Rc のグラフで持ちます。
  • ⟦⟧(帰納仮説)は quote 時の recursor スタックで正しく復元されます(Tm::Ih(idx, w))。再帰関数値を辞書として quote する経路(mult が plus を呼ぶ等)で quote∘eval が壊れる問題を、この recursor index で修正した経緯があります。
  • quote_shared:eval の Rc-DAG を let 配列に平坦化し、GVN で共有を保って quote する変種。GPU lowering がラッパ越しの反復で指数爆発するのを防ぎます(→ GPU 実行)。
  • メタ変数の文脈はスレッドローカルに持ちます(Env を改変せずに済み、テストがスレッドごとに独立)。
  • 深い let チェーン・深い構造体の Drop は反復処理化されており、巨大配列でもスタックオーバーフローしません。

診断

ユーザ・エディタに出るエラー文字列は 英語 です(コード内コメントは日本語)。multiplicity は Display で '0/'1/'ω と表示されます。型エラーは 1 宣言につき複数収集されます。

経緯 ── 捨てた案の記録

Oven の設計は「これで綺麗にまとまった」と思っては穴が見つかる、の繰り返しで進んできました。捨てた案を消さずに残すのは、同じ穴に二度落ちないためです。この章は主要な撤回・転換を、当時の理由とともに記録します(一次資料は DESIGN.md)。

2LTT ── 層を構文で分ける案

案:Two-Level Type Theory。メタレベル(コンパイル時・フルパワーの依存型)とオブジェクトレベル(実行時 = GPU・制限された世界)を構文として分け、⟨A⟩ のような印で繋ぐ。理論的には綺麗な解。

却下の理由:「host 用と kernel 用のコードを構文的に書き分けたくない。一つの言語で、区別なく書きたい」。

その後:2LTT の発想そのもの(GPU で走る部分の隔離)は、'GPU modality として一度復活し(下記)、最終的には「dispatch 境界 + 表現可能性検査」だけに落ち着きました。「捨てたはずの案が形を変えて戻り、また消えた」二段の変遷です。

'GPU modality ── 誕生と全廃

案:'GPU T という型の印(modality)で「GPU で走る層」を隔離する。2LTT のオブジェクトレベルを、構文の層ではなく型の印として復活させたもの。「エラーが違反した場所にローカルに出る」という利点もあった。当初は「'GPU の内部は QTT オフ(線形性なし・命令的)」という整理も伴っていた。

全廃の理由(効果系 Phase 5、2026-06-14):

  1. 「GPU 内は QTT オフ・順序はプログラム順」という整理が撤回された(下記)。効果順序は host IO と同型の token threading で付けることになり、「QTT オフ」という modality の意味が消えた。
  2. 残った意味は「表現可能性を強制する phase」だけになり、純コードに 'GPU を書かせるのは「使える場所を減らすだけ」で利点が無くなった。

現在:純コードは world 多相(印なし)。GPU カーネル断片はただの純粋関数 A → B です。host/GPU の区別は dispatch 境界 + 表現可能性検査(実装上は in_kernel フラグ 1 個)だけが担い、store を host で誤って呼べない安全性は token の型(World ≠ GPU)が担います。

「カーネル内の順序はプログラム順」の撤回

案:カーネルの中身は 1 スレッドが上から順に実行する命令的コードなので、store/load の順序は素のプログラム順で保証すればよい(linearity 不要)。

撤回の理由(2026-06-12):これは 関数の純粋性を売っている。評価器が字面順を守ることに意味が依存する = eval/quote/inline/conversion で順序が動きうる = 参照透過でない。[&IO] を導入した動機そのものに反する。

現在:GPU の効果順序も host IO と同型の 零幅 token threading で付けます。buffer は 'ω(race・atomic は自由)のまま、順序だけを token の '1 チェーンが担います。

FnMut / apply ── 別建ての関数型

案:効果のある λ のために FnMut(A, B) = (Env : Type, env : Env, code : (Env, A) → (Env, B)) を、純粋な A → B と並ぶもう一つの組み込み関数型として立てる。呼び出しは apply、closure 値自体を '1 で threading する。

廃止の理由:

  • 「効果のある関数」は素の A → B で表せる(('1 S, A) → ('1 S, B) はただの Π)。
  • 「closure は 'ω だけ capture・'1 は引数で渡す」を徹底すると関数値は全部 'ω になり、関数と状態を束ねる FnMut の存在理由が消える。
  • creative coding の流儀(state-as-data:状態は Array(Particle) として持ち純粋関数で map)に、state-as-closure は合わない。

現在:関数型は A → B 一種類(確定)。状態を抱えた値が本当に要るなら手書きの Σ で書く ── foundation ではなくライブラリのパターン。

設計ノートの言葉:「以前『すべての closure は言語レベルの Σ 型』『env を ∃ で隠す必要がある』と何度も書いたが、全部誤りだった。純粋 closure は capture していてもただの A → B。」

WriteSet / disjoint merge

案:GPU カーネルの書き込みを「各スレッドが書き込み集合(WriteSet)を返す純粋関数」とモデル化し、dispatch がそれらを disjoint(重複なし)に merge する。書き込みが純粋な「結果の組み立て」になり、副作用が消える。

撤回の理由:GPU には atomic 演算があり、複数スレッドが同じ場所に正しく書き込むパターンが実在する。disjointness の要求は強すぎるし、検査も高コスト。

現在:カーネルは本当に effectful だと認め、race は型で追わない(compute-shader と同じ割り切り)。

effect row / Row kind / Res(ρ)

案:dispatch のカーネルが任意個のバッファを捕捉するのを型で表すため、「捕捉する借用の行(row)」を第一級の kind にし、closure を存在量化・dispatch を全称量化で多相にし、Res(ρ) で返すべき資源を計算する。

撤回の理由:「糖衣構文のために変なものを足すくらいなら、糖衣構文の方を捨てろ」に真っ向から反する重い機構だった。捨てた後に「任意個 = レコード 1 個に束ねる(既にある Σ で済む)」という解が見つかった。

教訓:closure に借用を捕捉させ、それを高階関数経由で取り戻そうとすると機構が爆発する。借用は closure に捕捉させず、引数として渡す。 ── これがその後の設計全体(dispatch の borrow-lift・ループの step・escape 防止)を貫く原則になりました。

なお effect row 自体(capability の個数の多相)は現在も却下のままです。単一・抽象の capability [&E](E は型変数)は今の依存量化で書けるため、「effect 多相は無いが単一抽象 [&E] はある」が正確な現状です。

region / lifetime

案(dispatch の capture 問題の試み 3):バッファを region 所有の 'ω ハンドルにし、「現在の瞬間」を表す線形トークンを threading して順序を作る。「効果 = 時間トークンの threading、linearity = 時間は分岐しない、dispatch = 時間の fork-join」という世界観。

撤回の理由:withRegion を λ で書くとその λ がまた永続バッファを capture して封印が再発する。region を新規ブロック構文にせざるを得ず、ネスト・region 多相の複雑さを抱え込む。過剰。

現在:dispatch を構文にして borrow-lift する、で解決(→ GPU 実行)。なお「コピー不可資源の同時読み取り共有」だけは QTT の threading で原理的に表せないため、region か fractional permission が将来必要になる可能性は残っています。

dispatch の形の変遷

  1. explicit-R(関数):触る全バッファをレコード R に束ねて引数で渡す。正しく動くが冗長 ──「ふつうに capture して書きたい」。
  2. capture(closure):'1 資源が closure に封印されて戻ってこない。「closure は '1 を capture できない」原則と衝突し破綻。
  3. region:上記の通り過剰で撤回。
  4. 構文 + borrow-lift(確定):capture のように書けるが closure 値を作らないので封印しない。借りる資源の集合が body 依存 = 関数型を持てない、という点でも構文であることが本質的。

綴りも dispatch(size) λ(i){}(関数形)は「そこに任意の関数を置けるかのような嘘の見た目」として退けられ、dispatch(i in size){ body }(並列 for 形)で確定しました。

eliminator 焼き込みから data + case へ

当初:帰納型はプリミティブとして固定し、型ごとの eliminator(Nat-elim/Bool-elim/Vec-case …)を処理系に焼き込む。「定義の一般機構は作らない」が M0 の方針だった。

転換の理由:QTT の合流規則(どの引数が '0/'ρ/'π か、⊔ と SUM の群分け)を型ごとに手で持つ羽目になった。一般の data 宣言から constructor・case・iota・QTT 合流を導出する方が、規則が一つで済む。

現在:帰納型はユーザ(と prelude)が data で宣言し、分解・再帰は case + ⟦⟧ 一本。専用 eliminator は全廃(J も case で導出)。strict positivity を「inductive であることの定義」として要求します。

同時期に「効果ありの分岐を自動で elaborate する分岐 padding」も撤回されました ── 全 branch に同じ [&R] を付ければ、使わない枝の素通しは [&R] 糖衣の末尾自動 return に吸収され、独立の機構が要らないためです。

Σ-domain 適用から全面 curried へ

当初:関数の引数テレスコープを Σ として一括で渡す(f(a, b) は組 (a, b) の適用)。

転換(2026-06-11):全面 curried へ移行(f(a, b) = (f a) b)。タプルを渡したいときだけ f((a, b))。全 190 テスト green のまま実装が 146 行減り、implicit のカリー化(各 implicit が独立のメタ変数)とも整合しました。型パラメータと辞書が別々に解決できることは instance 解決の前提です(Σ にまとめると「テレスコープの Σ」と「辞書そのものの Σ」が構造的に区別できず破綻する)。

FinArray / build / index の撤去

当初:遅延 pull 配列のためのプリミティブとして FinArray/build/index を持っていた。

撤去の理由(効果系 Phase 6):build f = f・index xs i = xs i ── つまり 素の関数 Fin(n) → A の偽装 で、実体がゼロだった。必要なら関数を直接書けばよい。materialized な可変配列は Array + newArray/set/get が別に担います。

まとめ:繰り返し現れた教訓

  • 借用は capture させず、引数で渡す(FnMut・effect row・region・dispatch、すべてに共通の核)。
  • 糖衣のために意味論を足さない。重い機構を作りかけたら、まず「既にある Σ / QTT で書けないか」を疑う。
  • 「順序」や「安全性」を評価器の挙動(字面順・名前の不可視性)に頼らない。型('1・token の型)に載せる。
  • 紙の上で「綺麗にまとまった」は信用しない。core を oracle にして実装で確かめる。

未解決・不安(疑い続けるところ)

設計ノートが「まだ考え切れていない」と明示しているものです:

  1. &/ブロック threading の desugar の全体像。個別規則(入力は表面順・返りは thread-first、& は Π の直接テレスコープのみ、≤1 効果/文、lens、case は [&R] motive)は確定したが、parse 時の借用脱糖と typecheck 時の効果 threading が別実装のままで、一本化が残っている。再束縛のスコープ(shadowing)の厳密な扱いも。
  2. case 使用量規則の一般化:非再帰 constructor が動的回数走る型(二分木の葉)では「⟦⟧ 無し = 高々 1 回」の前提が崩れる。組み込み型は健全だが、ユーザ定義の分岐木に穴。群の決め方を「高々 1 回か動的回数か」へ一般化する必要。
  3. 線形 payload × 帰納 family:「再帰時に尾を '0 にする」は既知の patch の再現であって原理から出た解ではない、と自覚されている。case(尾 'ρ)と再帰(尾 '0)の 2 系統割れ・Vec の「Nat で回す」が一般 inductive に一般化しない、など。一般 inductive の eliminator 生成を形式化する段で設計し直す可能性が高い。文献的にも(Idris 2 含め)未解決寄りの領域。
  4. dispatch の特権性の健全性:「境界は線形な借用・内部は race 非検査」が host の純粋性を壊していないことの完全な論証。具体的な抜け道(buffer 経由の線形資源複製)は 1 件発見・修正済み ── 敵対的レビューは今後も必要。
  5. '1 読み取り壁:実値の状態 token(State S)を ω 的な算術で読む問題。Idris 2 の QTT 設計を参照予定。
  6. world 境界をまたぐ量の精密化:'0 消去値の越境などの端。
  7. NbE の発散:Type : Type の帰結として受容済みだが、timeout/fuel をいつ入れるか。
